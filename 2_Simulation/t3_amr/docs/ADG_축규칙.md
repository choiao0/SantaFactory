# ADG 축 규칙 — 지금 이렇게 돌아간다 (2026-09-14)

읽는 사람: t3_amr · FMS(B트랙).
이 문서는 **자체 완결**이다. 필요한 정의·수치·코드를 전부 여기 적는다.
날짜 없는 파일명인 것은 **현행 문서**라서다 — 구조가 바뀌면 이 파일을 고친다.

## 0. 한 장 요약

ADG(Action Dependency Graph)는 "A 의 이 동작이 B 의 저 동작보다 먼저" 라는
**순서**만 담은 그래프다. 시각표가 아니라서 실행이 늦어져도 안전이 유지된다.

pitch 1.0 에서는 회전하는 로봇의 코가 자기 칸을 벗어난다. 그래서 예약에
**두 등급**을 둔다.

```
hard 칸   상대 로봇의 **몸**이 못 들어온다      강한 제약
soft 칸   상대 로봇의 **축**만 못 들어온다      약한 제약 — 몸은 지나가도 된다
```

앞 칸을 통째로 hard 로 막으면 동시 회전 조합이 크게 준다. "몸은 와도 되고
축만 오면 안 된다" 로 완화하면 동시성을 덜 잃는다.

**규칙은 4칸이다.** 회전 `(h0 → h1)`, `d1 = DIRS[h0]`, `d2 = DIRS[h1]` 일 때

```
f0 = (r+d1)          앞 칸 — 옛 헤딩 쪽
f1 = (r+d2)          앞 칸 — 새 헤딩 쪽
mA = (r+d1-d2)       섞임 대각
mB = (r-d1+d2)       섞임 대각
```

**그리고 이 규칙이 ADG 순환을 없앤다** — pitch 1.0 · 20시드에서 순환
10개 → 0개 (§6).

## 1. 왜 이게 필요한가

### 기하

```
구동축 -> 앞면   front_len   0.390 m
구동축 -> 뒷면   rear_len    1.110 m
폭               width       0.800 m
```

**구동축이 앞쪽에 치우쳐 있다.** 회전은 구동축을 중심으로 일어나므로 앞뒤가
쓸고 가는 반경이 3배 가까이 다르다.

```
코 반경   hypot(0.390, 0.400) = 0.559 m
뒤 반경   hypot(1.110, 0.400) = 1.180 m
```

칸 반폭이 `pitch/2` 다. 코 반경이 그보다 크면 회전 중 코가 이웃 칸을 침범한다.

```
경계 = 2 x 0.559 = 1.1173 m

  pitch 1.2   0.600 > 0.559   안 벗어난다.  규칙 불필요
  pitch 1.0   0.500 < 0.559   벗어난다.    규칙 필요
```

**1.2 가 안전한 것은 우연이 아니라 이 값 위에 있어서다.**

### 규칙이 없으면

pitch 1.0, 로봇 A 를 (5,5)에 두고 8개 회전 전부, 주변 7×7 × 헤딩 조합 전부,
회전을 위상까지 32단계 샘플링해 차체 거리를 쟀다.

```
                              쌍/배치        접촉          최악 여유
B 가 정지                   1,376         0           +41.4 mm
A·B 동시 회전                 322      회전당 8          0.0 mm  <- 여기
정지 두 대가 이웃              344         0          +200.0 mm
```

**문제는 동시 회전 하나다.** 가만히 있는 이웃과는 1.0 에서도 안 닿는다.

### 여유의 천장

```
lateral_gap = pitch - width = 1.000 - 0.800 = 200.0 mm
```

옆 칸에 나란히 선 두 대의 간격은 격자가 정한다. **어떤 예약 규칙으로도 이보다
넓힐 수 없다.** 규칙이 할 수 있는 최선은 회전 케이스를 200 까지 끌어올리는 것이다.

## 2. 규칙 — 왜 4칸인가

후보 넷을 같은 설정으로 쟀다 (pitch 1.0, 8회전 최악값).

| 규칙 | soft 에 넣는 칸 | 합법쌍 | 접촉 | 최소 여유 | `hard ∪ soft` |
|---|---|---:|---:|---:|---|
| (규칙 없음) | — | 322 | 64 | 0.0 mm | 4칸 |
| 앞2 | f0, f1 | 314 | 0 | 41.4 mm | 6칸 |
| **4칸** | f0, f1, **mA, mB** | **302** | **0** | **200.0 mm** | **8칸** |
| 5칸 | + 코 | 300 | 0 | 200.0 mm | 9칸 = 3×3 전체 |
| 6칸 | + 코 + 뒤 | — | — | — | 폐기 (§2-3) |

### 2-1. 앞2 는 여유가 모자란다

`41.4 mm = pitch − 폭/2 − 코 반경 = 1.000 − 0.400 − 0.559`

앞 칸만 막으면 코가 이웃 칸에 **들어간 채로** 스쳐 지나가고 그 틈이 41.4 mm 다.
섞임 대각까지 막으면 코가 이웃 칸에 아예 안 들어가고 200 mm 가 된다.

**집행 오차 실측이 이걸 기각시킨다.** 12대 · 463.8초 · 30 Hz 물리 시뮬 녹화에서

```
로봇당 예산 = 설계 여유 / 2      (여유는 두 대가 나눠 먹는다)
  앞2        41.4 / 2 =  20.7 mm
  4칸·5칸   200.0 / 2 = 100.0 mm

로봇당 최악 오차                  중앙   p95   최대
  회전 중 (구간 최대)             41.8  65.9  74.3   <- 기준
  직진 중                          0.2   8.5  71.1

앞2       20.7 예산 vs 74.3   ->  3.6배 초과.  기각
4칸·5칸  100.0 예산 vs 74.3   ->  통과 (예산의 74%)
```

### 2-2. 코 대각은 근거가 없다

코를 넣어도 **여유가 1 mm 도 안 오른다.** 합법쌍만 302 → 300 으로 준다.
그리고 `hard ∪ soft` 가 9칸 = **3×3 전체**가 되어, 회전하는 로봇 한 대가
이웃 **전부**의 축을 잠근다.

FMS 스윕에서 그게 확인됐다 — 5·6칸에서 교착이 나던 시드(42·7·44·101)가
4칸에서 전부 완주했다.

### 2-3. 뒤 대각은 몸 칸이다 — 넣으면 안 된다

`뒤 = (r−d1−d2)` 는 **로봇 몸이 실제로 쓸고 가는 칸**이다. 8개 회전 전부에서
그렇다. 축이 뒤로 1.110 m 긴 차체가 90° 돌면 꽁무니가 그 대각을 지난다.

각 칸이 실제 스윕 안에 드는 횟수:

```
pitch      f0     f1     코     mA     mB     뒤
 0.90     8/8    8/8    0/8    0/8    0/8    8/8
 1.00     8/8    8/8    0/8    0/8    0/8    8/8
 1.10     8/8    8/8    0/8    0/8    0/8    8/8
 0.80     8/8    8/8    0/8    7/8    7/8    8/8
```

`soft` 는 "상대 **몸**은 와도 되는 칸" 이다. 우리 몸이 지나는 칸을 거기 넣으면
정의가 깨진다. 우리 구현(`hard = 실제스윕 − soft`)에서는 `hard` 가 4칸 → 3칸
으로 줄어 상대 몸이 들어온다 — **접촉 96건, 여유 0.0 mm.**

`_check_soft` 가 이걸 잡는다 (§4).

## 3. 두 팀이 같은 규칙을 보게 하는 법

규칙 정의는 **계획기가 단일 소스**다 (`3_FMS/sim_engine/pibt/geometry.py`).
우리는 그 함수를 그대로 부른다.

```python
# RobotGeom.front_cells — 우리 쪽
if not self.front_swing:
    return frozenset()
import pibt.geometry as geo
return frozenset(geo.front_cells(s0[0], s0[1], s0[2], s1[2]))
```

**여기서 규칙을 다시 구현하면 안 된다.** 정의가 두 벌이 되는 순간 "계획기
4칸 / ADG 2칸" 같은 어긋남이 검사로 안 잡힌다.

### soft 의 의미 — 세 경우를 다 적어야 한다

"(가) 더하기 / (나) 빼기" 두 갈래만으로는 **스윕 밖 칸의 처리**가 안 정해진다.

```
soft 칸 = "상대 로봇의 축이 못 들어오는 칸"

  그 칸이 실제 스윕 **안**이면   몸 금지 -> 축 금지로 **완화**      (f0, f1)
  그 칸이 실제 스윕 **밖**이면   원래 없던 **순수 추가 제약**       (mA, mB)
  몸이 진짜 지나는 칸이면        **넣으면 안 된다**                 (뒤)
```

FMS 는 (가) 더하기, 우리는 (나) 빼기다. **서술이 반대인데 결과는 같다** —
pitch 0.80~1.20 전부, 8회전 전부에서 `hard` 집합이 일치함을 확인했다.

```
FMS   hard = 축 + 뒤 + 스윙 3칸 (모델 스윕).  안 깎는다      "전부 추가"
우리   hard = 실제 스윕 - (guard ∩ 실제 스윕)                  "f0·f1 은 완화"
```

### pitch 게이팅은 규칙 함수 안에

1.2 에서는 규칙이 필요 없다. 그 판정이 **계획기 안**에 있어야 두 층의 기준이
하나다.

```python
geo.configure(front_swing=True, front_diag=True,
              robot_dims=(0.390, 1.110, 0.800), pitch=1.0)
# front_needed(): 2 x hypot(앞, 폭/2) <= pitch 면 front_cells() 가 ∅
```

**`robot_dims` 를 빼면 게이팅이 통째로 건너뛰어진다** — 계획기 `configure` 가
`if front_swing and robot_dims is not None:` 이기 때문이다. 우리 검사가 그
경우를 잡는다 (§4).

## 4. 구현 — 무엇이 어디에 있나

### 동작 하나가 들고 있는 네 가지 칸 집합

```
cells    실제 스윕 — 차체 사각형을 굴려 얻은 칸. **건드리지 않는다**
guard    규칙이 준 칸 그대로 (교집합 이전).  간선을 걸 때 쓴다
soft     guard ∩ cells.  hard 를 깎을 때만 쓴다
hard     cells - soft.  상대 **몸**이 못 들어온다
axle     {출발 칸, 도착 칸}.  상대가 여기 축을 두면 안 된다
```

**`guard` 와 `soft` 를 가른 것이 핵심이다.** 규칙이 내놓는 칸 중 일부는 실제
스윕 **밖**이다 (pitch 1.0 의 mA·mB 가 0/8). 교집합한 결과를 간선 조회에도
쓰면 4칸이 조용히 2칸으로 퇴화한다.

```
계획기가 보는 규칙   {f0, f1, mA, mB}     4칸
교집합만 쓰면        {f0, f1}             2칸 — 경고 없이
```

### 간선 두 종류

```
규칙 ①  몸끼리      같은 hard 칸을 쓰는 동작들을 _key 순서로 줄 세운다
규칙 ②  축 vs 앞칸   p 의 guard 에 q 의 axle 이 있으면 순서를 건다
```

`_key(action, cell) = (tick, 놓아줄 쪽 먼저, agent)` — 칸마다 전순서라
두 종류 간선의 합집합에 순환이 안 생긴다. `topological_order()` 가 그걸
말로 믿지 않고 실제로 확인한다.

### 검사 — 틀린 설정으로 못 돌게 한다

`_check_soft` (동작마다)

```
(1) 자기 축이 자기 guard 에 있으면        자기 바퀴 칸을 안 잡는다
(2) guard 에 **몸 칸**이 있으면           6칸의 「뒤 대각」이 여기서 걸린다
(3) 출발 칸이 hard 에 없으면
```

`_check_front_swing` (계획마다)

```
(1)  front_swing 이 계획기와 같은가
(1b) front_diag 가 계획기와 같은가        2칸/4칸 구별. 둘 다 front_swing=True 다
(2)  pitch 게이팅이 정말 걸렸나           robot_dims 를 빠뜨린 경우를 잡는다
(3)  켰는데 guard 가 전부 비었나
```

검사가 실제로 작동하는지 8회전으로 확인했다.

```
규칙   통과  거부
앞2      8    0
4칸      8    0
5칸      8    0
6칸      0    8    <- 「뒤 대각」에서 걸린다
```

## 5. 계획 틱이 무엇인지 — 두 경로가 다르다

`-194` 에서 계획기에 `MOVE_TICKS = 4, TURN_TICKS = 5` 가 생겼다. 그런데
**`MOVE_TICKS` 는 `kernel/core.py`(FmsKernel) 전용**이다.

```
FmsKernel      전진 MOVE_TICKS(4) 틱 · 회전 TURN_TICKS(5) 틱
step_h/run_h   전진 **1틱** · 회전 TURN_TICKS(5) 틱      <- 우리가 쓰는 쪽
```

`run_h` 도 `lifelong` 도 `step_h` 를 직접 부른다. 우리 경로에서 바뀐 것은
**회전이 1틱에서 5틱이 된 것**뿐이고, 같은 일에 드는 틱은 회전 빈도만큼만
는다 — 실측 1.3~1.6배.

> 한때 `TICKS_PER_CELL = MOVE_TICKS` 로 지평·`max_steps`·`tick_s` 를 전부
> 4배 환산했는데 틀렸다. 특히 `tick_s = pitch/v_max` 는 원래 맞던 값이라
> 나누면 안 된다. 지금은 되돌렸고, `max_steps` 만 회전 5틱을 감안해 늘렸다.

## 6. 결과 — 규칙이 순환을 없앤다

1.0 에서는 **단조 증명을 쓸 수 없다.** 전제가 둘인데

```
전제 1   guard ⊆ 실제스윕
전제 2   axle ∩ guard = ∅
```

4칸의 mA·mB 가 실제 스윕 밖(0/8)이라 전제 1 이 깨진다. 유일하게 만족하는
앞2 조차, 1.0 의 옛 규칙(전부 hard)이 이미 순환이라 함의가 공허하다.
**그래서 측정이 유일한 근거다.**

pitch 1.0 · 12대 · cross · 20시드:

```
규칙 꺼짐 (대조군)   비순환 10 · 순환 10 · 계획 실패 0
4칸 규칙 켜짐        비순환 19 · 순환  0 · 계획 실패 1
```

**순환을 안 만드는 정도가 아니라 있던 10개를 없앤다.** 원인 분석이 이걸
예측했다 — 순환은 계획기(3칸 모델)와 ADG(실제 스윕)가 다른 칸을 보기
때문이고, 규칙을 켜면 두 층이 같은 칸을 본다.

```
front_cells((5,5,1)->(5,5,0)) = [(4,6), (5,6), (6,4), (6,5)]
soft 간선 38~118개 — 규칙 ② 가 실제로 걸린다
```

이 값은 **몽키패치 없이** 잰 것이다 (2026-09-15, jupyter04). FMS 가 계획기에
목표 상태 대기 벌점 면제를 넣은 뒤(`pibt/heading.py:24`) `FIXLIVE` 를 끄고
20시드를 다시 돌렸고, 수정안을 얹어 잰 옛 값과 **숫자까지 같았다.**
결론이 우리 우회에 기대지 않는다.

```
라이브락 재현 (tools/goal_oscillation.py · pitch 1.0 · 12대 · 600스텝)
  수정 전   시드 1-4 중 3 정체 (1·2·4)
  수정 후   시드 1-6 전부 완주      <- 지금

  ★ 두 측정의 시드 범위가 다르다. 겹치는 1-4 로만 보면 정체 3 -> 0 이고,
    멀쩡하던 시드 3 은 167 틱으로 틱 수까지 같다.
```

### 단서 하나

**시드 4** 가 계획 단계에서 막힌다 — `{4:(45,100,2), 11:(45,99,2)}` 로
두 대가 이웃 칸에서 대치한다. 규칙이 만든 것이고(꺼진 상태에서는 완주),
FMS 가 exp16 에서 본 것과 같은 부류다. **ADG 순환과는 별개 항목**이고
해소 규칙(B4) 영역이다.

있는 결론이다.

집행 정확도 게이트는 **통과했다 — 다만 빠듯하다.** 로봇당 예산 100 mm 에
실측 최악 74.3 mm 로 74% 를 쓴다. 그리고 이건 1.2 격자 실측이라, 1.0 에
규칙을 넣어 회전과 정지·출발이 늘면 나빠지는 방향이다.

## 8. 틱 모델이 이산 시뮬과 어긋나 있다 (2026-09-15 확인)

두 시뮬은 **같은 함수**를 쓴다 — `step_h` · `candidates_h` · `dist_map_h` ·
`Replanner` · `Stagnation` · `front_cells` 를 전부 `3_FMS/sim_engine` 에서
그대로 import 한다. 그런데 **틱 모델이 다르다.**

```
              전진 1칸      회전 90°    거리장 turn_cost
우리          1틱           5틱         5.0   ( = turn_ticks )
이산 커널     MOVE_TICKS 4틱 5틱        1.25  ( = 5 / 4 )
```

각자 자기 모델과는 맞다. 문제는 **거리장이 달라 경로가 갈린다**는 것이다.
같은 시드·같은 맵에서 pitch 1.2 기준 228틱 vs 197틱으로 서로 다른 계획이
나온다. 그리고 `kernel/core.py:877` 의 `rb["busy"] = move_ticks - 1` 이
우리 쪽에는 없어, 전진이 칸을 쥐는 시간도 다르다 — 다중 로봇 경합 해소가
어긋나는 두 번째 경로다.

### 우리 쪽이 회전을 과대평가한다

`pibt/geometry.py` 의 물리 팀 실측(2026-09-13)이 기준이다.

```
90° 회전 1.511 s   ·   연속 주행 전진 1.195 s/칸   ->  비율 1.264  ->  4 : 5
```

우리 모델을 초로 환산하면 (pitch 1.0, tick_s = 1.1111 s)

```
              회전 1회    전진 1칸
실측          1.511 s     ~1.2 s
현행          5.56 s      1.11 s     <- 회전이 실측의 3.7배
맞춤(전진4틱) 1.39 s      1.11 s
```

### 맞추면 어떻게 되나 — 실측

전진을 4틱으로 쪼개고 `turn_cost` 1.25, `horizon`·`order_gap` 을 함께 4배로
해 **벽시계 350초·주문 도착률을 통일**하고 쟀다 (pitch 1.0 · 12대 · fms).

```
시드   현행 move1·tc5.0   비용만 move1·tc1.25   맞춤 move4·tc1.25
  1          8                  9                    12
  2          7                  6                    15
  3          9                  8                    15
  합        24                 23                    42
```

**비용만 바꾸는 것은 효과가 없다** (24 vs 23). 실행 모델을 안 바꾸고 거리장만
싸게 만들면 계획과 실행이 어긋날 뿐이다. 이득의 출처는 명확하다 — 현행에서
회전 1회가 예산 5칸을 먹는데 맞추면 1.25칸이다.

### 대가와 단서

```
horizon 315 -> 1260 · order_gap 15 -> 60 · 도구 max_steps 전부 x4
metrics.tick_seconds()  pitch/v_max -> pitch/(v_max x move_ticks)
기준값 전부 무효 — ADG 지문 · 이 문서의 측정표
```

★ `MOVE_TICKS=4` 는 **pitch 1.2 실측 기준**이다 (전진 1.2 m). 회전 시간은
거리와 무관하게 1.511 s 로 고정인데 전진만 짧아지므로, 1.0 에서는 회전이
상대적으로 더 비싸다. 그대로 쓰면 근사이고 1.0 에서 재측정이 필요하다.

★ `pibt/heading.py:5` 가 `MOVE_TICKS` 를 **import 만 하고 안 쓴다.** 상류에서
한 줄이면 되는 자리로 보인다. 도구와 주행이 갈리지 않으려면 FMS 와 함께 가야
한다 — 우리 `lifelong.py` 만 바꾸면 `run_h` 를 쓰는 도구들과 어긋난다.

> 한때 "틱 4배 환산" 을 했다가 철회한 적이 있는데(§5), 그때는 **실행 모델은
> 그대로 둔 채 상수만 늘리고** `tick_s` 까지 나눠서 없던 버그를 만들었다.
> 여기서 말하는 것은 `busy` 진행 자체를 바꾸는 것이고, 위 표가 그 차이다.
