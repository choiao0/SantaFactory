# 견적 워커

백엔드가 RabbitMQ `sim.request` 큐에 넣은 시뮬 요청 1건을 꺼내 `sim_v2_tasks.py`를 한 번 돌리고,
KPI를 `sim.result` 큐에 넣는 상주 프로세스. 계약은 백엔드 명세
[시뮬 엔진 연동 API 명세서 v0.3](../../5_Docs/Web/시뮬엔진연동API명세서.md)이고, 이 문서는 그 명세를
우리 커널 인자와 SUMMARY 키에 어떻게 붙이는지만 적는다. 설계 이슈 S15P21A106-155.

## 자리와 형태

- 코드: `infra/worker/estimate_worker.py` 한 파일. θ 탐색 워커(`run_study.py`)와 같은 폴더라
  두 이미지가 같은 방식으로 `/opt/worker`에 복사하고 `PYTHONPATH`에 넣는다.
  **이미지·compose를 나눈다(S15P21A106-157).** -155에서는 "새로 만들지 않는다"였는데, 그때 전제가
  "같은 호스트에 3_FMS를 마운트해서 돌린다"였다. EC2에 워커만 올리기로 하면서 그 전제가 사라졌다 — 아래 "배포".
- 시뮬은 **서브프로세스**로 부른다(`python sim_v2_tasks.py …`, `SIM_NO_PLOT=1`, wall-clock 타임아웃).
  [실행 계약 v2.3 §3](../contracts/SIM_RUN_CONTRACT.md#3-종료-코드)이 정한 호출 방식이고,
  시뮬이 assert로 죽어도 워커는 살아 다음 건을 받는다. θ 탐색 워커 `objective.py`와 같은 방식.
- 상주는 `infra/compose.estimate.yml`의 `estimate-worker` 서비스
  (`fms-estimate-worker:latest`, `restart: unless-stopped`). 개발 중에는
  `python infra/worker/estimate_worker.py`로 로컬에서 켠다. 포트는 열지 않는다(큐 소비자).
- 로컬 확인용 단발 모드 `--once <요청.json>`: 큐 없이 요청 파일 → 결과 JSON을 stdout에 찍는다.
  번역기·변환기 검증은 이걸로 하고 브로커는 마지막에 붙인다.

## 큐 규칙 (명세 §1-3 그대로)

| 규칙 | 구현 |
|---|---|
| prefetch 1 | `basic_qos(prefetch_count=1)` |
| ack는 결과 발행 후 | `basic_publish(sim.result)` → `basic_ack` |
| 실패도 결과로 발행 | 검증 실패·시뮬 비정상 종료·타임아웃 전부 `status: failed`, `error` 문자열, `kpi: null` |
| 같은 run_id 재전달 | 그대로 다시 돈다(결정론). 중복은 백엔드가 버림 |
| 모르는 필드 무시 | 필요한 키만 읽는다 |
| 브로커 끊김 | 연결 실패 시 5초 후 재시도 루프. 컨테이너 재시작 정책이 나머지를 맡는다 |

접속: `RABBITMQ_URL`(예 `amqp://user:pw@rabbitmq:5672/`) 하나. 없으면 `RABBITMQ_HOST/USER/PASSWORD`로 조립.
큐는 백엔드가 선언한다(durable). 워커는 선언하지 않는다.

## 요청 → 시뮬 인자

백엔드가 실제로 보내는 값(`EstimateService.baseRequest`, 2026-09-08 develop 기준): `seed` 고정 42,
`horizon_s` 21600, `shifts` `in,in,out,out,out,out`, 간격 2개 = 창고 일 평균 ÷ 작업창, `amr.count`만 채운 AMR,
`inbound`·`outbound` **빈 리스트**, 창고 식별자 없음.

## SUMMARY → 결과 KPI

| kpi | SUMMARY | 비고 |
|---|---|---|
| `orders_total` | `n_orders` | horizon 모드 = 실제 생성된 주문 수 |
| `orders_completed` | `orders_done` | |
| `inbound_total` | `inbound_total` | **SUMMARY 키 추가**(`stream.n_inbound`) |
| `inbound_completed` | `tasks_in` | |
| `makespan_s` | `makespan_steps` × DT | = horizon |
| `lead_time_mean_s` / `lead_time_p90_s` / `queue_time_mean_s` | `order_lead_mean_s` / `order_lead_p90_s` / `queue_mean_s` | 주문 키 우선, 구 SUMMARY는 `lead_*` 폴백 |
| `throughput_orders_per_h` / `throughput_tasks_per_h` | `orders_per_h` / `tasks_per_h` | |
| `amr_utilization` | `util_incl_service` | 아래 결정 |
| `conflict_wait_ratio` | `conflict_wait` | |
| `distance_total_m` | `distance_m` | **SUMMARY 키 추가**(`totals()["drive"]` × CELL_M) |
| `charge_downtime_s` | 0 | 배터리 꺼짐. ⑩에서 `charging_steps` × DT |

SUMMARY 키 2개 추가는 값 불변·키 추가만이라 `check_results_identity`(CSV 열 기준 비교)에 걸리지 않는다.
계약은 v2.4(추가만)로 올린다.

`amr_utilization`은 `util`(v1 호환: 대기 이중 계산, 서비스 제외) 대신 `util_incl_service`
(주행+대기+서비스+회전 ÷ 대수×T)를 쓴다. 백엔드는 이 값 × 100을 목표 가동률 %와 비교하므로 "로봇이 실제로
바쁜 비율"이 맞다. 백엔드 판정이 쓰는 값은 `orders_total`·`orders_completed`·`amr_utilization` 셋뿐이고
나머지는 저장·표시용이다.

| 상황 | 결과 |
|---|---|
| 필수 키 없음, `count` 범위 밖, `horizon_s` 없음 | 시뮬 안 돌리고 `failed`, error에 사유 |

## 검증

- `infra/worker/test_estimate_worker.py`: 명세 §1-1 예시 JSON → argv, SUMMARY 예시 → kpi 14키, 검증 실패 3건.
  브로커 없이 돈다.
- `--once` 로 실제 시뮬 1회(6대·1h)를 끝까지 돌려 kpi가 나오는지.
- 결과 불변 확인: 기준값 3개·`check_results_identity --quick`(SUMMARY 키 추가 뒤).
- **자립 확인(-157)**: 마운트 없이 `--once` 1회. 이게 통과해야 EC2에 3_FMS 트리가 없어도 된다는 뜻이다.
  같은 요청을 `THETA_PATH=`(중립)로도 돌려 KPI가 달라지는지 본다 — 같으면 θ가 안 실린 것이다.
  2026-09-08 실측(6대·1h·시드 101): θ 61건/117 tasks_per_h vs 중립 58건/114. 실림 확인.
- **브로커 왕복 실사 — 2026-09-08 완료(-157).** -155 시점에는 개발 PC에 Docker가 없어 미실시였고,
  가짜 pika로 "발행 → ack" 순서만 테스트로 고정해뒀었다. 실제로 돌린 결과:
  `sim.request` 발행 → 워커 소비·시뮬 1.2 s → `sim.result` 발행 → 백엔드가 받아
  `모르는 run 결과 무시: runId=smoke-157-e2e` 로그(모르는 run_id는 `applyResult`가 경고만 남기고 버린다),
  양쪽 큐 잔량 0. 네트워크·자격증명·이미지·ack 순서가 전부 확인된다.
- **주문 자체 생성(-158)**: `python -m pytest -q` 12개(생성 2개는 실제 프로파일·마스터로 결정론 확인) + `order_gen` unittest 7 + `--once` 1회(위 실측표).
  이미지에서는 `COPY order_gen/` 이 들어갔는지 `docker run --rm fms-estimate-worker:latest ls /app/order_gen/master` 로 본다(EC2 담당자).
- **아직 안 한 것**: `POST /api/estimates` 로 도는 진짜 경로. 견적 1건이 1~28대 run을 한꺼번에 발행하므로
  개발 PC에서 돌리면 시뮬 28회 + DB 행이 생긴다. 프론트 연결 시점에 같이 확인하는 편이 낫다.

## 배포 (S15P21A106-157)

**EC2에 올리는 것은 워커뿐이고 FMS 트리는 올리지 않는다.** 그래서 시뮬 코드를 마운트가 아니라
이미지에 굽는다 — 컨테이너 하나가 호스트에 아무것도 없어도 돈다.

| 파일 | 역할 |
|---|---|
| `infra/estimate.Dockerfile` | 배포 이미지 `fms-estimate-worker:latest`. `sim_engine`·`map`·`contracts`·`infra/out`을 `/app` 아래 굽는다 |
| `infra/compose.estimate.yml` | 배포 스택 `fms-estimate`. 볼륨 없음 |
| `.dockerignore` | 컨텍스트가 3_FMS 전체라 필요 |

`sim.Dockerfile`은 건드리지 않았다. 거기 구우면 θ 이미지 안에 마운트가 덮는 시뮬 사본이 생겨,
마운트 없이 돌렸을 때 에러가 아니라 **옛 사본이 조용히 도는** 상태가 된다.

배치가 계약이다. `map_loader.py:24`가 `map`을, `from_theta.py:25`가 `contracts`를 각각 `sim_engine`의
형제로 찾는다. `/app` 아래 그 배치를 지켜서 코드 수정이 없다. `SIM_ENGINE_DIR`은 이미지 ENV로 못 박는데,
안 주면 `estimate_worker.py:26`의 폴백이 `/opt/worker` 기준 3단계 위 = `/sim_engine`을 가리킨다.

```
docker build -f 3_FMS/infra/estimate.Dockerfile -t fms-estimate-worker:latest 3_FMS
cd 3_FMS/infra && docker compose -f compose.estimate.yml up -d --build
```

백엔드 compose(`name: santafactory`)와 같은 호스트이므로 네트워크 `santafactory_default`를 external로
붙여 `rabbitmq` 호스트명으로 접속한다. 4_Web 스택이 먼저 떠 있어야 한다. 기본 5개 병렬(`deploy.replicas`, -182). 줄일 때 `WORKER_REPLICAS=N`.
서버를 분리하면 `RABBITMQ_URL`만 바꾸면 되지만, 브로커가 `127.0.0.1:5672` 바인딩이라 그쪽을 먼저 열어야 한다.

주의: `infra/.env`에 `RABBITMQ_USER`/`RABBITMQ_PASSWORD`(4_Web/.env와 같은 값)를 넣는다.
**θ 스택과 파일을 나눴으므로 `POSTGRES_PASSWORD`는 더 이상 필요 없다.**

이미지를 EC2로 옮기는 방법은 셋이다. EC2에서 빌드(저장소는 빌드 타임에만 필요 — Jenkins 워크스페이스에
이미 있다), `docker save`/`load`(약 500 MB 전송), 레지스트리 push/pull(Jenkins 스테이지로 자동화할 때).
Jenkins는 `4_Web/docker-compose.yml`만 보므로 이 스택은 자동으로 뜨지 않는다.

## 병렬 처리와 조기 종료 (S15P21A106-182)

### 지금까지: 직렬

워커는 `prefetch 1` + BlockingConnection 으로 한 건을 끝내고 결과를 발행한 뒤에야 다음 건을 꺼내고, 컨테이너는 하나만 떴다(CPU 1.0).
백엔드는 견적 1건에 1~28대 run 을 **한꺼번에** 큐에 넣으므로(`SimulationService.publishRuns`), 뒤 run 은 앞 run 들이 전부 끝나야 돌기 시작한다.
1~28대 전체 ≈ 개별 실행 시간의 합이라 이 PC 기준 10분 안팎, 백엔드 `run-timeout` 30분에는 들어오지만 명세가 목표로 둔 "견적 1회 90초"와는 거리가 멀었다.

### 바꾼 것: 워커 5개 병렬 (우리 몫, 이 이슈)

| 항목 | 변경 | 근거 |
|---|---|---|
| `infra/compose.estimate.yml` | `deploy.replicas: ${WORKER_REPLICAS:-5}` | 브로커가 큐의 run 을 5개 컨테이너에 1건씩 분배. 컨테이너당 1코어(OMP 1)라 총 5코어 |
| `Jenkinsfile` FMS 스테이지 | 기동 확인을 "컨테이너 전부 running" 으로 | 전에는 `ps -q` 결과 1개를 가정해 5개면 `docker inspect` 가 깨짐 |
| `estimate_worker.py` | 로그 접두에 컨테이너 id 12자 | 5개 로그가 섞여도 어느 워커인지 보이게. 로컬(`HOSTNAME` 없음)은 그대로 |

**바뀌지 않은 것.** `prefetch 1`(명세 §1-3 그대로 — 여러 워커가 놀지 않게 하는 규칙이 이제 실제로 효력을 냄), 결과 발행 뒤 ack, 큐 메시지 형식, 시뮬 결정론(run 마다 시드 고정이라 어느 워커가 돌려도 같은 값).
코어가 모자라면 `WORKER_REPLICAS=3` 처럼 줄인다. **EC2 코어 수 확인 필요** — 백엔드·DB·브로커와 같은 호스트면 전체 코어에서 2개쯤 남기고 워커에 준다(담당자 확인 항목).

**한 run 의 실행 시간 (이 PC, v3 기본값, 6 h horizon, 하루 500건 자체 생성, capacity 6, 토트당 5 s).**

| 대수 | 4 | 8 | 12 | 16 | 20 | 24 | 28 |
|---|---|---|---|---|---|---|---|
| 초 | 3.1 | 5.9 | 13.2 | 15.5 | 19.8 | 27.4 | 36.5 |

1~28대 전체를 직렬로 돌리면 합계 ≈ 8~9분, 5개 병렬이면 가장 긴 배치가 결정하므로 ≈ 2분. EC2 코어가 이 PC 보다 느리면 그 배수만큼 늘어난다.

**실브로커 실측 (2026-09-10, 이 PC Docker Desktop 22코어, RabbitMQ + 워커 컨테이너, 1~28대 28건 한꺼번에 발행).**

| 워커 수 | 28건 전부 도착까지 | 5·10·15·20·25대 도착 시각 |
|---|---|---|
| 1 (직렬, 기존) | **407.6 s** | 12 · 43 · 102 · 195 · 316 s |
| 5 (병렬, 이 이슈) | **121.7 s** | 4 · 14 · 30 · 54 · 94 s |

3.3배. 5배가 안 되는 이유는 run 시간이 대수에 따라 3~37 s 로 크게 달라 마지막 배치(24~28대)의 긴 run 이 꼬리를 만들기 때문이다 —
큰 대수부터 발행하면 꼬리가 앞으로 와서 더 줄어들지만, 조기 종료(아래)와 상충하므로 지금은 오름차순을 유지한다.
28건 KPI 는 병렬·직렬이 **전부 동일**(결정론 확인), 실패 0. 컨테이너 5개가 각각 CPU 97~99 %(1코어) 를 썼다.

### 다음: 5개씩 발행하고 개선이 없으면 멈춤 (백엔드 몫, 제안)

지금은 백엔드가 대수 목록을 전부 발행하고 **전부 끝나야** 판정한다(`finalizeIfComplete`). 워커가 5개이므로 백엔드가 **5개씩 배치로** 발행하면
한 배치 = 벽시계로 그 배치의 가장 큰 대수 1회 시간이고, 배치마다 판정을 미리 돌려 더 볼 필요가 없으면 남은 대수를 발행하지 않을 수 있다.
큐 메시지 형식·워커는 그대로다.

1. **배치.** 대수 목록(지금과 같이 1 → 상한, 1대 간격)을 앞에서부터 `estimate.batch-size`(기본 5 = 워커 수)개씩 끊는다. `create()` 는 첫 배치만 발행하고
   `SimScenario` 행도 그 배치만 만든다(남은 대수는 아직 행이 없음 → 새 상태값 불필요).
2. **배치 완료 판정.** `applyResult`·`sweepTimeouts` 뒤, 지금 열린 배치의 run 이 전부 `isFinished()` 이면 누적 결과(`hasKpi` 인 것)로 `evaluator.evaluate()` 를 돌린다.
3. **멈추는 조건 — 하나라도 맞으면 종료.**
   - (a) 누적 결과에 목표를 만족하는 대수(`satisfies`: 처리율·가동률·예산)가 있다. 대수가 커질수록 비용만 늘어 권장은 그 첫 대수로 확정된다.
   - (b) `findKnee` 가 무릎을 찾았고 이번 배치의 최대 대수 ≥ 무릎 + `amr-count-margin` + 1. 무릎 뒤로는 처리율 증가분이 꺾여 더 돌려도 권장이 바뀌지 않는다.
   - (c) 이번 배치에서 **연속 두 대수의 처리율이 모두 100 %** — 포화. 더 늘려도 처리율은 못 오르고 가동률만 떨어져 판정에 도움이 안 된다(단, `notDiscriminating` 판정은 지금처럼 전체 기준으로).
   - (d) 대수 목록을 다 썼다.
4. **계속하는 경우.** 다음 배치의 행을 만들고 발행한다. 견적 상태는 계속 `RUNNING`, SSE 이벤트는 지금과 같다.
5. **실패 처리.** 배치 안에 FAILED/TIMEOUT 이 있어도 "끝난 것" 으로 보고 배치를 닫는다. 판정은 지금처럼 KPI 있는 run 만 쓰고 `anyFailed` 로 PARTIAL 표기.

**효과 추정(하루 500건, 위 실행 시간).** 6대에서 처리율 100 % 가 나오는 부하라 (c) 로 2번째 배치(6~10대)에서 멈춘다 — 28회 → 10회, 벽시계 ≈ 2회분(4대 배치 3 s + 10대 배치 약 12 s).
하루 1,000건은 무릎 20대 근처라 (b) 로 5번째 배치(21~25대)에서 멈춘다 — 28회 → 25회, 벽시계 ≈ 5회분 ≈ 1분 40초. 부하가 낮을수록 절감이 크다.

**주의.** 리드타임 기준이 판정에 들어가기 전에는 (a)·(c) 가 6대처럼 적은 대수에서 멈춘다(견적_워커.md "백엔드와 맞출 것" 6). 리드타임 상한을 넣으면 (a) 는 "리드타임도 만족" 으로, (c) 는 "리드타임 p90 개선폭 < 5 %" 로 바꾸면 된다.
우리 쪽 후속: horizon 6 h → 1 h(20·28대는 결과 거의 같음 실측), 2단계 격자(4대 간격 → 무릎 근처 1대 간격). 둘 다 배치와 독립이라 나중에 얹을 수 있다.

## 주문 자체 생성 (S15P21A106-158)

백엔드는 `inbound[]`·`outbound[]` 를 **계속 빈 리스트로 보낸다**(2026-09-09 백엔드 결정). 그래서 "어떤 주문을 돌릴지"는
워커가 정한다 — 이미지 안의 주문 생성기(`order_gen/`, -153)로 요청의 기존 필드만 써서 만든다. **새 요청 필드는 없다.**
명세 v0.4 에는 "outbound 가 비어 있으면 워커가 창고 정보로 주문을 생성한다" 한 줄만 추가한다.

| 생성기 입력 | 요청에서 가져오는 값 | 없으면 |
|---|---|---|
| 하루 출고 주문 수 `--orders` | `warehouse.outbound_avg` | 500 (프로파일 원본 규모) |
| 시드 `--seed` | `seed` | 42 (기존과 같음) |
| 분포 `--profile`, 마스터 `--master` | 이미지 안 고정(`profiles/order_rules.json`, `master/santafactory_sample.json`) | — |
| 도착 모양 `--release` | 고정 `wave` (참조 창고처럼 몰림) | — |
| 시간창 | `[warehouse.outbound_start, outbound_start + horizon_s)` 로 자름(`slice_orders`) | 07:00 시작 (프로파일 피크) |

**시각 매핑(채택).** 생성기 시각은 참조 창고 분포(07시 38 %, 07~13시 73 %)를 따르고 창고의 출고 시간대(예 13:00~18:00)와
어긋난다. 백엔드는 "하루 물량이 출고 창 안에 전부 들어온다"는 전제로 간격을 계산하므로, 같은 전제로 맞추려면 생성된 하루치의
시각 구간(첫 주문~마지막 주문)을 출고 창 `[outbound_start, outbound_end)` 로 **선형 비례 매핑**한 뒤 자른다. 몰림 모양은 유지되고
밀도(건/시간)는 백엔드 간격 계산과 일치한다. 출고 시간대가 없으면 매핑 없이 07:00 부터 자른다.
기각한 대안 = 매핑 없이 07:00 부터 horizon 만큼(밀도가 백엔드 전제의 약 60 %). 함수는 `order_gen/slice_orders.py::rescale_orders`.

**우선순위.** `outbound[]` 가 오면 그대로(-156) → 없으면 자체 생성 → 환경변수 `WORKER_GEN_ORDERS=0` 이면 예전 간격 모드(비교·회귀용).
입고는 명시 모드에서도 기존 간격·`in` 창 그대로 돈다(의도, 커널_시뮬_구조 §명시 주문 모드). `amr.capacity` 는 null 이라 왕복 분할 안 켬(현행).

**결과 해석.** `orders_total` = 창 안에 들어온 주문 수(horizon 밖은 버리고 `orders_skipped`). 웨이브라 처리율은 적은 대수에서도
100 % 에 닿기 쉽다 — 첫 비교(07~09시 208건)에서 6대가 처리율 100 %·리드타임 1954 s. **리드타임 판정 기준이 백엔드에 없으면
권장 대수가 과소**로 나온다(백엔드와 맞출 것 6).

**구현.** `estimate.Dockerfile` 에 `COPY order_gen/ /app/order_gen/`(워커 기본 `ORDER_GEN_DIR` = `<3_FMS>/order_gen` 이라 ENV 불필요);
워커 `_generate_orders(req)`(생성 → 매핑 → 자르기) + `_orders_file(req)`(요청 outbound[] 우선, 임시 파일); `_orders_flags` 는 주문 파일 유무만 본다.
테스트: 워커 2(출고 창 매핑·결정론 / 기본 창·우선순위) + 생성기 unittest 1(매핑). 시뮬 CLI 는 손대지 않아 기준값 3개·동일성 12행 불변.
**워커 기본 결과는 바뀐다**(간격 → 명시).

**실측(2026-09-09, `--once`, 백엔드 실제 형태 요청: 6대·6h·seed 42·outbound_avg 500·출고 13:00~18:00).**

| 모드 | orders_total | 완료 | 리드 평균 / p90 | 가동률 | 시간 |
|---|---|---|---|---|---|
| 자체 생성(기본) | 500 (창 안 500/500) | 500 | 3847 s / 5449 s | 0.789 | 4.0 s |
| 간격(`WORKER_GEN_ORDERS=0`) | 406 | 367 | 876 s / 1539 s | 0.853 | 3.9 s |

처리율만 보면 6대가 100 % 라 "충분"이지만 리드타임이 64분이다 — 백엔드 판정에 리드타임 상한이 없으면 권장 대수가 과소로 나온다(아래 6).

## 미룬 것 (2026-09-08 결정: 프론트–백–시뮬 연결을 먼저)

1. **속도 단일 인자 `--speed`** — DT = 1.0/speed 로 시간 축만 스케일. 커널 무변경, 5파일 약 20줄, speed 1.0이면 비트 동일.
   워커는 `amr.speed_loaded`를 넘기기만 하면 된다. 결과 불변 작업이라 아무 때나.
2. **적재/공차 속도 이원화** — PIBT "매 틱 전 로봇 한 칸" 전제를 깨는 이동 계층 결과 변경(L). 남은과업 ⑭.
   두 속도 차가 20 % 안이면 단일 속도로도 견적 오차는 그 절반 이하.
3. 배터리 필드 → `--battery` 매핑(⑩), 명시 `inbound[]` 재현(출고 `outbound[]` 는 -156 에서 연결됨).

## 백엔드와 맞출 것

1. **`estimate.max-amr-count: 8`.** 명세 예시 간격(출고 22.5 s·입고 48 s)에서 12대가 이미 포화라 8대까지만 돌리면
   전 대수 처리율 100 % 미달 → 권장 없음(`THROUGHPUT_SHORT`)만 나온다. 우리 존 용량 28까지 올리거나 예산 기반
   상한을 그대로 두되 28을 하드캡으로.
2. **시드 42 고정.** 42는 θ 탐색 시드다. 평가 시드 101을 권한다(값 하나 바꾸면 됨).
3. `amr_utilization` = 서비스 포함 가동률이라는 정의 공유.
4. `horizon` 6h → 1h 단축과 2단계 격자는 보류 중(2026-09-08 논의). 워커는 요청의 `horizon_s`를 그대로 쓰므로 영향 없음.
5. 명세 §1-1: `inbound[]` 는 V1 무시, `outbound[]` 가 비어 있으면 **워커가 창고 정보(`outbound_avg`·출고 시간대·`seed`)로 주문을 생성**. `amr.capacity` 단위는 토트 수, `amr.tote_units`를 추가한다. 로봇 시드 `capacity: 200`은 6으로 바꾼다.
6. **리드타임 판정 기준.** 웨이브 주문에서는 처리율·가동률만으로 6대가 뽑힌다(리드 33분). `lead_time_p90_s` 상한을 판정에 추가 요청.
7. **배치 발행 + 조기 종료(-182).** 워커 5개에 맞춰 대수를 5개씩 발행하고 배치마다 판정, 개선이 없으면 남은 대수 미발행. 위 "병렬 처리와 조기 종료" 절의 조건 (a)~(d). 큐 형식·워커 변경 없음.
