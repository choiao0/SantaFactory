# 커널·시뮬 구조

이 문서는 현재 `sim_engine`의 구조와 실행 의미를 날짜별 설계·구현 기록에서 주제별로
재배열한 것이다. 코드 동작을 새로 정의하지 않으며, 실행 계약의 권위 문서는
[`contracts/SIM_RUN_CONTRACT.md`](../contracts/SIM_RUN_CONTRACT.md)다.

## 현재 구조

```text
sim_engine/
├── sim_v2_tasks.py          # 계약 진입점, CLI 셸
├── simpy_harness.py         # 같은 커널을 SimPy 시계로 실행
├── fms_kernel.py            # kernel/ 재수출 파사드
├── pibt_core.py             # pibt/ 재수출 파사드
├── map_loader.py            # 맵·스테이션·충전 존 단일 로더
├── from_theta.py            # wallA 토폴로지와 θ→비용
├── order_stream.py          # 주문 도착·분해, 커널 밖 WMS 역할
├── kernel/
│   ├── core.py              # FmsKernel, 배차·상태·이동·워치독
│   ├── battery.py           # SoC·도크·강제/기회 충전
│   ├── metrics.py           # 카운터·summary·STALL 덤프
│   └── states.py            # 상태·계급 상수
├── pibt/                    # cell·geometry·heading·hgraph·liveness
├── cli/                     # common·report·export_isaac·plot
├── sweeps/                  # B0″·고부하·θ Fleet Sweep
├── checks/                  # 데모·거리장·기준선·배터리 검사
└── results/                 # 현재 기준선·평가 산출물·리플레이 도구
```

`sim_v2_tasks.py`, `pibt_core.py`, `fms_kernel.py`의 이름은 외부 호출과 import를 보존하기
위한 계약 경계다. 구현은 하위 패키지로 분리됐지만 기존 경로는 파사드로 유지한다.

## 계층과 책임

| 계층 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| `FmsKernel` | 로봇 상태, 배차, PIBT 이동, 충전 존 복귀, 서비스, 배터리, 지표, 워치독 | 시계, 주문 난수, 파일·stdout |
| `OrderStream` | 주문·입고 도착 시각, 주문 분해, v1compat 체인, 완료 카운터 | 로봇 이동·배차 |
| CLI 셸 | 인자, 맵·θ 로드, 틱 시계, 종료, SUMMARY, 그림·npz·Isaac 파일 | 이동 의사결정 |
| SimPy 셸 | SimPy 시계, 도착 프로세스, 고정 시간 종료 | 별도 이동 알고리즘 |

커널과 셸을 분리한 목적은 같은 결정 로직을 CLI, SimPy, 이후 MQTT 데몬에서 재사용하는
것이다. 주문 생성·분해는 시뮬 WMS의 역할이므로 `OrderStream`에 남고, WMS는 커널에
`from→to` 태스크만 제출한다.

## 틱 루프

틱 `t`의 앞부분은 `pos(t)`를 보고, 이동 뒤에는 `pos(t+1)`을 본다.

```text
셸: 이 틱의 도착 태스크를 kernel.submit_task()
커널 dispatch(t):
  1. 서비스 만료와 후속 태스크 콜백
  2. 충전 종료·강제 충전
  3. waiting FIFO 배차
  4. 기회 충전
  5. 남은 FREED 로봇의 홈 복귀
셸: 유한/고정 시간 종료 조건 확인
커널 move(t):
  6. PIBT 한 스텝으로 pos(t) → pos(t+1)
  7. 충전 존 지표와 복귀 목표 재선택
  8. 도착 감지와 서비스 시작
  9. 행동·SoC·지표·워치독 갱신
```

배차를 이동 앞에 두므로 새 태스크가 같은 틱에 움직일 수 있다. 도착은 이동 후 위치로
판정한다. 서비스 타이머는 도착 틱에는 감소하지 않고 다음 틱부터 감소한다.

### 틱 인덱싱

- 이동은 `pos(t) → pos(t+1)`이며 도착 시각은 `t+1`이다.
- 도착 시각 `t_arr`에 서비스 타이머를 `SERVICE_STEPS`로 설정한다.
- `t_arr + SERVICE_STEPS`의 dispatch에서 0이 되어 그 틱 move부터 다시 움직인다.
- 무장애 거리 `d1`, `d2`인 두 구간의 완료는 `t+d1+d2+2S`로 기존 이벤트 모델과 같다.

## 로봇 상태머신

```text
IDLE_HOME ──배차──> TO_PICKUP ──도착──> SERVICING_PICKUP
    ^                                      │ 만료
    │                                      v
    └──도착── TO_HOME <──배차없음── TO_DROPOFF ──도착──> SERVICING_DROPOFF
                                      완료 ──> FREED ──> 재배차 또는 TO_HOME

IDLE/FREED/TO_HOME ──충전 판단──> TO_CHARGE ──도착──> CHARGING ──종료──> FREED
```

| 상태 | 목표·행동 | 배차·우선순위 |
|---|---|---|
| `IDLE_HOME` | 현재 홈 유지 | 배차 가능, 계급 3 |
| `TO_PICKUP` | 태스크 `frm` | 계급 2 |
| `SERVICING_PICKUP` | 현재 칸 강제 stay | 배차 불가, 계급 0 |
| `TO_DROPOFF` | 태스크 `to` | 적재, 계급 1 |
| `SERVICING_DROPOFF` | 현재 칸 강제 stay | 만료 시 완료, 계급 0 |
| `FREED` | 즉시 재배차 또는 홈·충전 | 배차 가능 |
| `TO_HOME` | 선택된 충전 존 칸 | 이동 중 재배차 금지, 계급 3 |
| `TO_CHARGE` | 예약 도크 | 계급 2 |
| `CHARGING` | 도크 칸 강제 stay | 계급 0 |

서비스 중 로봇에는 현재 상태만 0인 강제 stay 거리장을 준다. θ에 따라 대기 비용이 커져도
서비스 로봇이 걸어 나가지 않는다.

## 태스크 흐름

### main

- 입고: `inbound_buf[i] → aisle_buf[a]`, 한 건당 한 태스크다.
- 출고: 주문의 라인 수 `k∈{1,2,3}`, 기본 분포 `0.5/0.3/0.2`다.
- 상품마다 통로를 중복 허용으로 고르고 같은 통로 라인은 토트 하나로 합친다.
- 각 토트는 `aisle_buf[a] → packing[p]`로 직행한다.
- 같은 주문의 packing은 하나로 고정하고 모든 태스크가 끝나면 카운터로 주문 완료를 판정한다.
- induction·consol·qc·vas·returns는 현재 main 흐름에서 사용하지 않는다.
- 피커 작업 시간과 빈 토트 공급, 입고 검수는 0 또는 생략으로 단순화돼 있다.

### v1compat

주문 하나를 supply→retrieve→pack의 세 태스크 직렬 체인으로 만든다. 주문 도착 때 기존과
같이 난수 4회를 미리 소비하고, 같은 틱 주문은 ID 순으로 처리한다. 이 모드는 A* 시절과
PIBT의 이동계층만 비교하기 위한 패리티 경로이며 칸 모델·고정 홈을 사용한다.

## 배차 규칙

기본 배차는 waiting FIFO를 순회하며 태스크 `frm`까지 맨해튼 거리가 가까운 로봇을 고른다.
동률은 가장 작은 로봇 ID다.

- 배차 가능: `IDLE_HOME`, 하역 완료 직후의 `FREED`.
- 배차 불가: `TO_HOME`, 임무 수행 중, 충전 중, 강제 충전 대상.
- 하역 완료 로봇은 현재 도킹 칸에서 즉시 다음 태스크를 받을 수 있다.
- 정적으로 도달할 수 없는 `frm`은 배차하지 않고 맵 오류 경고를 낸다.
- 헤딩 거리 `dmap_h`로 바꾸는 계획은 결과 변경 과제로 남아 있다.

## 커널 인터페이스

현재 공개 경계의 의미는 다음과 같다.

```python
cfg = KernelConfig(...)
kernel = FmsKernel(
    free, station_cells, edge_cost, wait_cost,
    homes, zone_mask, n_robots, cfg,
)
kernel.submit_task(task)
kernel.dispatch(t)
kernel.move(t)
summary = kernel.summary(n_orders, sim_hours)
```

`task`는 ID, 주문 ID, 종류, 출발·도착 이름과 좌표, 생성·배차·완료 시각을 가진다.
커널은 `robots`, `tasks_done`, `waiting`, `visit_count`, `dir_flow`, 존 통계와 내보내기
로그를 상태로 유지한다. 유한 모드 종료와 고정 시간 종료는 셸이 결정한다.

v1compat의 다음 체인 태스크는 서비스 만료 콜백에서 같은 틱 배차 전에 커널로 다시
제출된다. 콜백을 나중에 처리하면 2317/186.4 패리티가 깨지므로 호출 시점도 계약의 일부다.

## SimPy 사건층

SimPy 하네스는 다른 시뮬레이터가 아니라 같은 커널의 선택 셸이다.

### 고정 시간과 교대

- `--horizon=T`는 마지막 틱 `T-1`의 이동까지 수행하고 `t==T`에 끝난다.
- 처리량 분모는 마지막 완료 시각이 아니라 T다.
- T 안에 완료된 태스크만 리드타임 표본이며 미완료는 `open_tasks`로 남긴다.
- `--shifts=in,out,out`은 T를 3등분해 앞 1/3에는 입고만, 뒤 2/3에는 출고만 발생시킨다.
- 교대 경계에서도 진행 중·대기 중 태스크는 계속 처리한다.
- 도착 프로세스의 같은 시각 이벤트는 `URGENT`로 예약해 틱 프로세스보다 먼저 제출한다.

### 배터리와 충전 도크

배터리 계산은 행동에 의존하므로 SimPy 바깥 프로세스가 아니라 커널의 매 틱 갱신에 있다.

| 파라미터 | 기본 | 의미 |
|---|---:|---|
| `runtime_h` | 8.0 h | 주행 70%·정지 30% 혼합 가동 시간 |
| `charge_h` | 1.5 h | 만충 시간 가정 |
| 주행·회전 소모 | `1/22,320` SoC/틱 | 주행과 회전 동일 |
| 정지 소모 | 주행의 1/4 | 대기·서비스·유휴 |
| `soc_low/go/leave` | 20/80/95% | 강제·기회 진입·종료 |
| `n_chargers` | 6 | `charger[0..k)` 도크 |
| 초기 SoC | 30~100% | 주문 스트림과 분리한 시드 |

강제 충전은 SoC가 낮은 순, 빈 도크는 맨해튼 최근접으로 예약한다. 도크가 없으면
`soc_yield=(low+go)/2` 이상인 충전 로봇 중 SoC가 가장 높은 로봇을 퇴거시킬 수 있다.
임무 중 low 아래로 내려가도 현재 태스크는 끝내고, 0%는 정지시키지 않고
`soc_empty_steps`로 기록한다.

## iw.hub 파라미터와 해석

8시간 가동은 iw.hub 스펙이고 1.5시간 충전 및 상태별 소비 비율은 확인이 필요한 가정이다.
초기 SoC는 별도 RNG(`[seed, 0x145]`)로 생성해 배터리 on/off가 같은 주문을 받게 한다.

실측에서 24대·6시간·간격 15는 배터리 없음 337.3 tasks/h, 배터리 있음 약 337 tasks/h로
차이가 약 −0.1%였고 도크 가동률은 81%였다. 28대에서는 95%였다. 간격 7.5 과부하에서는
기회 충전이 줄고 강제 충전·퇴거가 실제로 발생했다. 견적 레버는 8시간 이상과 충전기 수
스윕으로 확인한다는 과제로 남아 있다.

## Isaac 내보내기와 리플레이

`SIM_EXPORT_ISAAC=1`이면 `sim_engine/isaac_export_<tag>/`에 `scene.json`과
`trajectories.json`을 만든다. 환경변수가 없으면 기록 자체를 하지 않아 결과와 성능을
바꾸지 않는다.

`trajectories.json`은 기존의 `[t,x,y]` 좌표를 유지하면서 다음 키를 추가했다.

- `headings`: 틱별 yaw.
- `actions`: `rotate`, `reverse`, `wait`, `service`, 배터리 모드의 `charge`.
- `model`: `heading` 또는 `cell`.
- `scene.json`의 `zones`, `grid`, `station_cells`.

`results/fleet_replay.html`은 이 두 파일을 로컬 브라우저에서 선택하거나 드래그해 1 m 격자,
2칸 차체, 방향, 동작색, 충전 존, 스테이션, 완료 태스크를 재생한다. Isaac 쪽은 headings가
있으면 그 yaw를 쓰고, 실행 기준점과 스팟턴 규약을 맞춘다.

## Lifelong MAPF 관점

sim_v2는 태스크 완료 뒤 새 목표를 받고 매 틱 PIBT를 결정하므로 구조적으로 Lifelong MAPF다.

| 요소 | 현재 구현 | 정합 또는 후속 |
|---|---|---|
| 평가 | 유한 주문 makespan, 선택적으로 고정 T | `--horizon`으로 T 안 완료 수 측정 |
| 목표 할당 | FIFO × 맨해튼 최근접 | 헤딩 거리 `dmap_h`는 후속 |
| 유휴 처리 | 충전 존 + 도킹 이탈 우선 | 현행 유지 |
| 가이던스 | θ→`edge_cost`·`wait_cost` | A트랙 Optuna/모델과 연결 |

## ROS·Isaac 연동 순서

1. sim_v2 내보내기를 Isaac에서 재생해 헤딩·스팟턴·후진과 물리 간섭을 확인한다.
2. 같은 커널을 SimPy 셸에서 고정 시간·교대·배터리 조건으로 검증한다.
3. 커널 액션을 VDA 5050 order/action으로 바꾸는 어댑터 규격을 합의한다.
4. MQTT 데몬 셸과 Isaac T4를 연결한다.

시뮬을 ROS로 전환하는 것이 아니라 결정 커널은 유지하고 벽시계·메시지 I/O 셸을 추가한다.
실행 계층은 셀 중심 스팟턴, 후진, 틱 배리어를 보장해야 한다.
