# 설계 결정 — 회전 모델링·상태 우선순위·멀티라인 주문 (2026-08-31)

시각화(궤적 플레이어) 리뷰에서 나온 3가지 논점과 결정.

## 1. 로봇 회전이 즉각적인 문제 → **지표만 추가, 방향 상태 확장은 V2 보류**

- 관찰: 시뮬레이션·시각화에서 로봇이 회전을 즉시 함. 실제 AMR은 회전에 시간이 걸림.
- 배경: AI입출력명세서 §11-5가 이미 의도적으로 미룬 사항 — 통행 비용이
  "칸 + 나가는 방향" 형태라 회전 벌금(들어온 방향×나가는 방향 쌍)을 표현 불가.
  회전 실측 시간은 Isaac Sim에서 측정해 보정하기로 명세에 못박혀 있음.
- 제대로 하려면 PIBT 상태를 (r,c) → (r,c,방향)으로 4배 확장 + 제자리 회전 틱 소모.
  dist_map·충돌 판정 전부 복잡해지는 큰 공사라 MVP 단계에서 부적절.
- **결정**:
  1. 지금은 궤적에서 **회전 횟수 지표**만 센다 (태스크당 평균 회전수).
  2. t1_teleop 가감속 실측값과 곱해 회전 오버헤드가 fleet size 결론을 바꾸는지 계산.
  3. 유의미하게 크면 그때 방향 상태 확장을 V2로 결정.
- 추가 리스크 메모: 로봇 0.641×1.44m → 회전 대각선 1.58m. 폭 1칸 통로에서
  제자리 회전이 물리적으로 불가할 수 있음. Isaac V&V 항목에 포함할 것.

## 2. 목적지행 vs 복귀 구분 → **상태 기반 PIBT 우선순위로 반영**

- 관찰: 스모크 테스트는 전원이 단순 이동이지만, 실제로는 태스크 수행 이동과
  홈 복귀 이동이 섞임 (기존 sim_v1_tasks.py에 dispatch/go_home 상태 흐름 이미 존재).
- **결정**: 이벤트 루프 통합 시 로봇 상태를 PIBT 우선순위에 반영 —
  **적재 이동 > 픽업하러 가는 중 > 홈 복귀** 순. 복귀 로봇이 자연히 양보하게 되고,
  MVP에서 관찰된 밀치기 왕복(진동)도 완화 기대.

## 3. 멀티라인 주문 (주문 1건 = 상품 여러 개) → **방법 1 채택, 방법 2는 별도 이슈**

- 관찰: 현재 spawn_chain은 주문 1건 = 통로 1곳 = 토트 1개로 단순화.
  실제 주문은 상품이 여러 통로에 흩어져 있음.
- 하드웨어 근거: 선정 AMR이 "다중 토트 랙을 얹는 형태" (AMR 모델 선정 문서 요구사항 1).
- **방법 1 (채택)** — 나눠서 가져오고 합류:
  주문 1건 = 통로 k곳(1~3 분포), 토트 k개를 각각 회수, **consol 스테이션에서
  전부 모이면(AND-join) 패킹 태스크 생성**. consol 스테이션의 원래 설계 의도로 추정.
  태스크 생성기만 수정하면 되는 작은 변경 → 이벤트 루프 통합 이슈에 포함.
  주의: 주문당 태스크 수가 3개 고정이 아니게 됨 → tasks/h vs orders/h 지표 구분 필요.
- **방법 2 (보류 → 로드맵 확정, 2026-08-31)** — 멀티스톱 픽업(배칭):
  API 계약 결정으로 최종 제품 필수 기능이 됨(백엔드AI_API계약_검토 §2).
  구현 시점은 원래 계획대로 실험 트랙 종료 후:
  로봇 1대가 통로 여러 곳을 순회하며 토트 여러 개 적재. 처리량 레버가 크지만
  배차가 소형 VRP가 되어 스코프 큼 + 로봇당 토트 캐파 확정 필요(팀 결정 대기).
  θ 적용(B1) 이후 별도 이슈로 — 배칭 on/off 자체가 비교 실험 거리.
- A트랙 연계: 멀티라인 분포(주문당 라인 수)는 task_profile 채널에 영향 →
  분포 확정 시 A트랙과 1회 합의 필요.
