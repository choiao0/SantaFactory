# 백엔드 ↔ AI(시뮬) API 계약 초안 검토 (2026-08-31)

상태: **백엔드팀 논의용 초안** — 합의 후 확정본으로 갱신할 것.

## 0. 이 API가 부르는 시뮬의 위상 — 중요 전제

이 API 뒤의 시뮬레이션은 **모든 실험이 끝난 뒤의 최종 서빙용**이다:
B트랙 벤치마크(A* vs PIBT, B-1e)와 A트랙 θ 학습·조정이 전부 완료되어,
**최종 학습된 AI 모델이 내놓는 θ(통행 규칙 파라미터)가 적용된 상태**로 돈다.

```
백엔드 견적 요청 (창고 조건 + AMR n대 + 주문)
      ↓
[서빙 시뮬] 조건 → 최종 θ 모델 호출 → from_theta() → PIBT 시뮬 → KPI
      ↓
백엔드 응답 (KPI) — 백엔드가 n을 바꿔가며 반복 호출해 최적 대수 산출
```

따라서 이 계약은 실험용 시뮬(sim_v1/v2, fleet_sweep)의 현재 기능이 아니라
**최종 시뮬이 갖출 기능 기준**으로 작성한다. 역으로, 계약에 남기는 필드는
곧 최종 로드맵 약속이 된다 (아래 §2).

## 0-1. 시나리오 스케일 결정 (2026-08-31) — 분 단위 축소

서빙 시나리오는 하루(시각 창)가 아니라 **분 단위 미니 시나리오**(입고 N분 +
출고 M분)로 확정. 사유: Isaac Sim 연동 시연이 대략 실시간이라 하루 단위면
재생에 실제 하루가 걸림.

- API 시간 필드 의미 변경 필요: `inbound_start/end` "HH:MM" 대신 분 단위 창
  (예: `inbound_duration_min`, `outbound_duration_min` 또는 상대 분 오프셋).
  `inbound_avg`/`outbound_avg`도 그 창에 맞는 건수로 재정의.
- **밀도 대표성 주의**: 창만 줄이고 건수를 대충 잡으면 안 됨 — 대당 도착률
  (주문/분/로봇)을 실제 운영 가정과 비슷하게 유지해야 견적(필요 대수)이
  대표성을 가짐. 스케일 규칙을 백엔드와 합의할 것.
- 격자 시뮬 계산 자체는 하루도 1~2분에 돌므로 이 축소는 순전히 Isaac 시연
  제약에 의한 결정 (계산 성능 문제 아님).

## 1. 제안된 요청 스키마 (백엔드 초안)

```jsonc
{
  "run_id": "est_77_n3",          // 견적 77번의 AMR 3대 회차
  "seed": 42,
  "warehouse": {
    "worker_count": 4,
    "inbound_start": "01:00",  "inbound_end": "09:00",
    "outbound_start": "13:00", "outbound_end": "18:00",
    "inbound_avg": "480", "outbound_avg": "500"
  },
  "amr": {
    "count": 3, "speed": 1.2, "battery": 100.0,
    "consumption": 0.02, "charge_time": 3600, "capacity": 8
  },
  "orders": [
    { "order_id": 1001,
      "lines": [
        { "product_id": "7",  "rack_id": "A2", "qty": 1 },
        { "product_id": "11", "rack_id": "A9", "qty": 3 },
        { "product_id": "15", "rack_id": "B4", "qty": 1 } ] }
  ]
}
```

구조 자체는 좋다: run_id 회차 식별, 백엔드 주도의 n 스윕, 주문 라인 단위 상세.

## 2. 계약 = 최종 로드맵 약속이 되는 필드들

계약에 남기려면 아래 기능이 최종 시뮬 로드맵에 반드시 포함돼야 한다.
(포함 못 하면 필드를 빼는 게 맞음 — "받되 무시"는 서빙 계약에선 금물)

| 필드 | 요구되는 시뮬 기능 | 현황 |
|---|---|---|
| `battery`/`consumption`/`charge_time` | 배터리 소모·충전 모델 + 충전 정책(몇 %에 복귀?) | 미구현. 정책 필드(`charge_threshold`) 추가 필요 |
| └ `consumption` 단위 **확정(2026-08-31)** | **주행 1m당 소모량** (예: 0.02 → 100/0.02 = 5,000m 주행 가능). 정지·대기·서비스 중 소모는 0으로 단순화 | 계약에 단위 명시 완료 |
| `capacity` | 멀티스톱 배칭(방법 2) — 1회 다중 적재 | 보류 상태였음 → 로드맵 복귀 필요 |
| `worker_count` | 피커 작업 시간 모델 (현재 0으로 단순화) | 미구현 |

## 3. 정의 필요 — 합의 안 되면 양쪽이 다르게 해석하는 것들

1. **응답 스키마 — v1 초안 확정 (2026-08-31), 백엔드 전달 완료.**
   전달용 정리본: https://claude.ai/code/artifact/bc84883b-43e1-4a3f-ba16-7c7dfb36ffa4
```jsonc
{
  "run_id": "est_77_n3",               // 요청 run_id 에코
  "status": "done",                    // done | failed
  "error": null,                       // failed일 때만 사유
  "kpi": {
    // 완료도
    "orders_total": 50, "orders_completed": 50,
    "inbound_total": 48, "inbound_completed": 48,
    // 시간 [초]
    "makespan_s": 1740,
    "lead_time_mean_s": 210.5, "lead_time_p90_s": 402.0,
    "queue_time_mean_s": 87.3,
    // 처리량
    "throughput_orders_per_h": 96.4, "throughput_tasks_per_h": 182.0,
    // 로봇
    "amr_utilization": 0.63,           // 0~1
    "conflict_wait_ratio": 0.004,      // 0~1, 혼잡 신호
    "distance_total_m": 12480,         // × consumption = 배터리 소모 검산
    "charge_downtime_s": 0             // 배터리 모델 구현 전 0 고정
  }
}
```
   규약: snake_case, 단위는 접미사(_s/_m/_per_h), ratio 0~1 실수, 문자열 숫자 금지.
   같은 요청(seed 포함) = 같은 응답(결정론). failed 시 부분 KPI 없음.
2. **주문 도착 시각 규칙**: orders[]에 도착 시각이 없음. outbound 창 안 분포
   (균등? 포아송?)를 명시하거나 주문별 `arrival_time` 필드 추가.
3. **입고 상세**: 출고는 라인 단위인데 입고는 `inbound_avg` 하나. 입고 물건의
   랙 분포 규칙(무작위 균등 등) 명시 필요.
4. **`rack_id` ↔ 시뮬 좌표 매핑**: 시뮬 픽업 지점은 통로 입구버퍼(aisle_buf).
   "A2 → aisle_buf[?]" 매핑 테이블이 계약의 일부여야 함.
5. **speed 2필드화**: AI입출력명세서 §7과 일치하도록 `speed_loaded`/`speed_empty`
   (V1은 같은 값 입력).
6. **타입/단위**: `inbound_avg`가 문자열 → 숫자로, 단위(건/일) 명시.
   시각은 창고 로컬 "HH:MM"임을 명시.
7. **입출고 시간대 비중첩**: 초안은 오전 입고/오후 출고로 분리 — 이 경우 필요
   대수는 두 페이즈 중 피크가 결정. 겹침 허용 여부만 확인 (스키마는 그대로 수용 가능).

## 4. 실험용 시뮬과의 관계

- 실험용(sim_v2, fleet_sweep)은 이 계약과 무관하게 CLI/CSV로 계속 진행.
- 서빙 시뮬은 sim_v2 엔진을 재사용하되, 이 계약의 어댑터(요청 파싱 → 시나리오
  구성 → θ 모델 호출 → KPI 응답)를 별도 층으로 얹는다.
- battery/capacity/worker 모델은 실험 트랙 종료 후 서빙 준비 단계에서 추가.
