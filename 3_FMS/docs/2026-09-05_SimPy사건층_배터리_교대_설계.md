## 1. 고정 시간 실행과 교대 (`order_stream.py`, 셸)

### 1-1. 고정 시간 모드

| | 유한 모드 (현행, 기본) | 고정 시간 모드 (`--horizon=<틱>`) |
|---|---|---|
| 도착 | 주문 `n_orders`건 + 입고 같은 수, 지수 간격 | **T 안에서 생기는 만큼**, 교대 창 안에서만 |
| 종료 | 주문·입고 전부 완료 (배차 뒤·이동 전 판단) | `t == T` (마지막 틱 T−1의 move까지) |
| 처리량 분모 | makespan(마지막 완료 틱) | **T** |
| 리드타임 표본 | 전 태스크 | T 안에 완료된 태스크만. 미완료 수는 `open_tasks`로 |
| 위치 인자 `n_orders` | 의미 있음 | **무시**(명시하면 `[WARN]`). SUMMARY `n_orders` = 실제 생성된 주문 수 |

### 1-2. 교대 규칙 — `--shifts=in,out,out` (기본), 고정 시간 모드에서만

- 토큰 수 k로 T를 **k등분**하고, i번째 창 `[i·T/k, (i+1)·T/k)`에는 그 토큰 종류의 도착만 생긴다. 연속된 같은 토큰은 한 창으로 합친다(기본값 = `in [0,T/3)`, `out [T/3,T)`).
- **도착이 안 생기는 것**이지 큐에 쌓아두는 것이 아니다. 창 밖에서 그 종류의 도착 0건 — 검증 항목.
- 창 안 도착은 창 시작 시각부터 지수 간격(`--order-gap` 출고 / `--inbound-gap` 입고, 기본 = order_gap, 둘 다 양수)으로 뽑고 창 끝에서 절단한다. rng는 **출고 창 전부 → 입고 창 전부** 순으로 소비(유한 모드의 "주문 → 입고" 관례 유지).
- 부하 해석 주의: 유한 모드는 주문·입고가 동시에 각각 1/gap 비율로 오므로 합계 2/gap인데, 교대 모드는 어느 창에서나 **한 종류만** 1/gap이다. 같은 `--order-gap`이면 순간 부하가 절반이다. 유한 모드의 고부하(간격 15)와 맞추려면 간격 7.5 정도가 대응.
- 교대 경계: 커널은 교대를 모른다. 진행 중 태스크는 끝까지, 대기 큐도 그대로 소진된다.
- `--horizon` 없이 `--shifts`만 주면 `[WARN]` 후 무시.

## 2. 배터리·충전 도크 (`fms_kernel.py`)

### 2-1. 파라미터와 수치 (-143 §2-2 표를 틱 단위로 환산)

| 파라미터 | 기본 | 플래그 | 틱 환산 |
|---|---|---|---|
| 가동 시간 | 8.0 h (iw.hub 스펙) | `--runtime-h` | 주행 1틱 소모 = 1 / (8·3600 · (0.7 + 0.3·0.25)) = **1/22,320** SoC — "주행 70 %·유휴 30 % 혼합에서 8 h" 정규화 |
| 충전 시간 | 1.5 h (**가정**, 48 V 산업용 관례 — Isaac/하드웨어 파트 확인 요청) | `--charge-h` | 충전 1틱 = 1 / (1.5·3600) = **1/5,400** SoC. 20 → 95 % = 4,050틱 = 67.5 분 |
| 소모 비율 주행 : 회전 : 정지 | 1.0 : 1.0 : 0.25 | (고정) | 정지 = 대기·서비스·유휴 전부. 회전(방향 변화 틱) = 주행 |
| `soc_low / soc_go / soc_leave` | 20 / 80 / 95 % | `--soc=20,80,95` | 강제 충전 / 유휴 기회 충전 진입 / 충전 종료. 퇴거 가능선 `soc_yield`는 `(low+go)/2`(기본 50 %) |
| 충전기 수 | 6 | `--chargers=<1..6>` | `stations.json` `charger[0..k)` 칸 = 동쪽 존 안 (50·53·56·59·62·65행, 108열) |
| 초기 SoC | 30 ~ 100 % 균등(시드) | (고정) | 전원 100 %면 3 h 안에 사건이 없다. **별도 rng**(시드 `[seed, 0x145]`)로 뽑는다 — 주문 구성 난수는 도착 틱마다 실행 중에 소비되므로 스트림 rng 를 쓰면 배터리 on/off 가 같은 시드에서 다른 주문을 받는다(2026-09-06 검토에서 수정). 따라서 배터리 on/off 는 **같은 주문 스트림**으로 짝지은 비교가 된다 |

### 2-2. 상태·우선순위

```
IDLE/FREED/TO_HOME ──(soc < low, 또는 유휴이고 soc < go 이고 빈 도크)──> TO_CHARGE ──(도크 도착)──> CHARGING ──(soc ≥ leave)──> FREED
```

| 상태 | RANK | 이동 | 지표 |
|---|---|---|---|
| `TO_CHARGE` | 2 (= TO_PICK) | NAV — 주행 카운터·visit_count에 포함(TO_HOME과 동일 취급) | `charge_events` +1 (진입 시) |
| `CHARGING` | 0 (= 서비스) | stay 고정(밀리지 않음), `_stag` 0 | `charging_steps` +1/틱, SoC += 충전율 |

짐 든 로봇(TO_DROP 1)보다는 낮고, 주차·유휴(3)보다는 높다 — 저전력 로봇이 존 앞에서 유휴 로봇에 밀려 못 들어가는 일을 막는다.

### 2-3. 배차 순서 (`dispatch(t)` 안, 매 틱)

1. **서비스 만료** — 현행.
2. **충전 종료**: `CHARGING`이고 `soc ≥ leave` → `FREED`, 도크 해제.
3. **강제 충전**: 상태 ∈ {IDLE, FREED, TO_HOME}이고 `soc < low`인 로봇을 SoC 오름차순으로 빈 도크(맨해튼 최근접)에 예약 → `TO_CHARGE`. 빈 도크가 없으면 **퇴거**: 충전 중 로봇 가운데 `soc ≥ soc_yield`인 것 중 SoC 최고를 `FREED`로 내리고 그 도크를 넘긴다(`charge_evictions`). `soc_yield=(low+go)/2`(기본 50 %)로 두어 막 충전을 시작한 로봇의 반복 퇴거를 막는다. 그래도 없으면 대기 — 이 로봇은 배차 대상에서 빠지고 `dock_wait_steps` +1.
4. **태스크 배차** — 현행 FIFO × 최근접. 단 `soc < low`인 로봇은 후보에서 제외.
5. **기회 충전**: 남은 IDLE/FREED/TO_HOME 중 `soc < go`이고 빈 도크가 있으면 → `TO_CHARGE`. 대기 태스크가 있어 배차된 로봇은 이미 4에서 빠졌으므로 "정말 놀고 있는 로봇"만 해당.
6. **FREED → TO_HOME** — 현행(존 최근접 빈 칸).

배터리 꺼짐(기본)이면 2·3·5는 no-op이고 4·6의 반복 순서는 현행과 같다 — 비트 동일의 근거.

### 2-4. 임무 중 저전력, 0 % 도달

임무 중(`TO_PICK`~`SVC_DROP`) SoC가 `low` 밑으로 가도 **현재 태스크는 끝낸다**(짐 든 채 멈추는 쪽이 더 비현실적). 그 뒤 FREED가 되면 3번에서 잡힌다.
SoC가 0에 닿아도 죽이지 않고(clamp 0) `soc_empty_steps`를 센다 — 이 값이 0이 아니면 "충전기 부족·임계 부적절"의 견적 신호다. STALL로 처리하지 않는다.

### 2-5. 도크와 존 주차의 관계

- 도크 칸은 **주차 후보(`zone_goal`)에서 제외**. 초기 배치(`make_homes_zone`)는 **그대로 둔다** — 도크 6칸을 초기 배치에서 빼면 간격 2 용량이 27칸으로 떨어져 28대가 안 된다(2026-09-05 실측). 28대일 때 도크 위에서 출발하는 로봇은 1대((56,108))이고, 충전하러 온 로봇(계급 2)이 밀어낸다(IDLE 3).
- 도크 위에서 출발한 로봇은 밀려나도 `goal=home=도크`가 남아 첫 태스크까지 도크 옆을 맴돈다 — 그 도크를 다른 로봇이 예약하면 존 빈 칸으로 **재선택**(`_unpark_docks`, `zone_retargets`에 집계. 2026-09-06 검토).
- 도크 칸은 이미 `station_cells`에 들어 있어 도킹 칸 이탈 최우선(장치 ⑤)이 그대로 적용된다.
- 도크 옆 칸에 주차한 로봇 때문에 어떤 방향으로는 도킹 자세(뒤 칸)가 안 나올 수 있다 — 다른 방향(남/북, 108열은 48~66행 전부 free)으로 도킹하거나 PIBT가 밀어낸다. 막히는지는 `dock_wait_steps`·STALL 유무로 본다.

### 2-6. 틱 소모 (`move(t)` 끝)

로봇별로 이번 틱의 (pos, h, 회전 busy)를 보고: 위치·방향이 바뀌었거나 여러 틱 회전 중이면 주행 소모, `CHARGING`이면 충전(1.0에서 clamp), 그 외(대기·서비스·유휴 정지)는 정지 소모. 초기값부터 `soc_min`을 갱신하고, 0 이면 `soc_empty_steps` +1.

### 2-7. 워치독

고정 시간 모드에서 "1500틱 완료 무변화"는 정상일 수 있다(입고 창 초반, 집단 충전). **고정 시간 모드에서만**(`stall_warn_only`) 대기 큐와 임무가 모두 없으면 진전 시각을 갱신하고, 그 밖에서 1500틱을 넘기면 경고 시각을 기록한 뒤 실행을 계속한다. 유한 모드는 워치독 규칙이 **v2.1과 완전히 같다** — "할 일 없음 = 진전" 조건은 유한 모드에서도 첫 도착 전(도착 틱 ≥ 1)에 참이 되므로 게이트 없이 두면 한가한 부하(간격 ≥ 1000)에서 STALL 시각·유무가 달라진다(2026-09-06 검토에서 재현 후 게이트 추가, 검사 [6]). 옛 규칙이 "주문이 아직 안 왔는데 STALL"이라는 오탐을 내는 것은 별도 이슈다.

## 4. SimPy 하네스 (`simpy_harness.py`)

- **도착 프로세스**: 스트림의 도착 시각표를 따라 `timeout` 후 `submit_task`. 같은 시각의 틱 프로세스보다 **먼저** 실행되어야 CLI(`arrivals → dispatch`)와 순서가 같다 — 도착 타임아웃을 `URGENT` 우선순위로 예약해 보장한다(같은 시각 NORMAL 타임아웃인 틱보다 먼저 pop).
- **틱 프로세스**: `dispatch(t)` → (유한 모드 종료 판단) → `move(t)` → `timeout(DT)`.
- **고정 시간 실행**: `env.run(until=T·DT)`. 틱 루프도 `t < T`로 이중 보호.
- 배터리는 커널 안(§0-4)이라 하네스에 별도 프로세스 없음.
- 검증 = CLI와 SUMMARY 동일(유한·고정 시간·배터리 각 1벌).

### 6-3. 읽는 법

- **간격 15의 교대 모드는 수요 제약이다.** 유한 모드 24대·간격 15가 465 tasks/h(θ 감도 실험 중립)인데 여기선 340 — 한 창에 한 종류만 오므로 순간 도착률이 절반(§1-2). 처리 용량을 보려면 간격 7.5(→ 410 tasks/h, 큐 폭주)처럼 부하를 올려야 한다. θ 탐색을 고정 시간 모드로 옮길 때 이 점을 계약 조건에 반영할 것.
- **간격 15에서 배터리 처리량 영향은 없다.** 같은 24대·6 h·**같은 주문 스트림**(초기 SoC 별도 rng)에서 2024 → 2021 완료, 337.3 → 336.8 tasks/h(**−0.1 %**). 로봇이 자주 놀아 기회 충전으로 SoC가 70~80 %에 유지되고 강제 충전(<20 %)은 두 번(퇴거 2회)뿐이다. 도크 6개 가동률 81 %(24대)·95 %(28대) — **28대에서는 6개가 거의 포화**다.
- **과부하(간격 7.5)에서 배터리 경로가 실제로 작동한다**: 로봇이 놀지 않아 기회 충전이 안 되고 20 % 아래에서 강제로 들어가며 퇴거 3회. 종료 평균 SoC 54.5 %로 하강 중 — 6 h 실행은 정상 상태가 아니고, 8 h 이상에서 "충전기 몇 개가 필요한가"가 갈린다. 견적 레버 실험은 실행 시간 ≥ 8 h·`--chargers` 스윕으로.
- 초기 SoC 30~100 % 균등은 워밍업 편향을 만든다(초반 낮은 로봇이 몰려 충전). 정상 상태 지표가 필요하면 앞 1~2 h 를 버리는 워밍업 절단이 다음 후보다.
- 실행 시간은 설정한 고정 시간에 비례(28대 6 h 90 s). 배터리 계산은 거의 공짜(24대 3 h 40 s vs 6 h 배터리 60 s의 차이는 실행 시간).
