## 1. 왜 새 파일인가

v1의 이벤트 루프는 `drive()`가 도착시각을 미리 반환한다는 계약 위에 서 있다
(배차·스테이징·재시도 알람 전부). PIBT는 틱 단위로만 진행되어 이 계약이 성립하지
않으므로, 수술이 아니라 **시간 진행 방식 자체를 틱 루프로 바꾼 별도 구현**이 맞다.
그 대가로 v1의 복잡한 장치 다수가 필요 없어진다:

| v1 장치 | v2에서 |
|---|---|
| `vertex_res`/`edge_res` 시공간 예약 장부 | 삭제 — PIBT가 틱마다 한 칸만 예약 |
| `parked` (정차 점유) | 삭제 — 정차 로봇도 매 틱 PIBT 에이전트 (stay 결정) |
| `RETRY_GAP` 재시도 알람 | 삭제 — 매 틱이 곧 재시도 |
| 대기 슬롯(staging)·APRON·MAX_STAGERS | 삭제 — 도킹 칸 점유 시 PIBT 밀림으로 자연 대기 |
| STALL 워치독 | 유지 (형태만 변경, §8) |

## 2. 파일 구성

```
sim_engine/
├── map_loader.py        # [신규] 맵 로드+다운샘플+스테이션 매핑 공용 모듈

├── sim_v2_tasks.py      # [신규] 틱 루프 본체 (이 문서의 대상)
```

CLI는 v1과 동일: `python sim_v2_tasks.py [태그] [로봇수] [주문수] [시드] [통로차단]`
+ 추가 옵션 `--flow main|v1compat` (기본 main, §6).

## 3. 틱 루프 구조

```
초기화: 맵/스테이션 로드, 로봇 N대를 홈(충전존)에 배치, 주문 도착 시각표 생성
        (v1과 동일 규칙: rng.exponential(ORDER_MEAN_GAP), 홈 배정 로직 동일)

for t in 0, 1, 2, ...:
    1. 주문 도착      : order_times[i] == t 인 주문의 1레그 태스크 생성
    2. 서비스 완료    : 서비스 타이머가 0이 된 로봇 → 상태 전이 (§4)
    3. 배차           : waiting 태스크 FIFO × 배차 가능 로봇 최근접 매칭 (§5)
    4. PIBT 스텝      : 우선순위 정렬(§5) → pibt_core.step() 1회 → 전 로봇 이동
    5. 도착 감지      : TO_* 상태 로봇이 자기 목표 칸에 서 있으면 상태 전이 (§4)
    6. 지표 누적      : visit_count, drive/wait, 회전 카운트(방향 변화)
종료: 전 주문 체인 완료 (또는 워치독 발동)
```

순서 근거: 배차(3)를 이동(4) 앞에 두어 새 태스크가 같은 틱에 이동을 시작할 수 있게
한다. 도착 감지(5)는 이동 후에 해야 그 틱의 최종 위치 기준이 된다. 서비스 타이머
감소는 (2)에서 처리하므로 도착 틱에는 감소하지 않는다.

**틱 인덱싱 규약 (v1 등가성의 근거 — 반드시 이대로 구현):**
- 틱 t의 스텝 1~3은 위치 `pos(t)` 기준. 스텝 4는 `pos(t) → pos(t+1)`을 계산.
  스텝 5의 도착 감지는 `pos(t+1)` 기준 — 즉 도착 시각 = t+1.
- 도착 시각 t_arr에 타이머 = SERVICE_STEPS 설정. 이후 틱의 스텝 2에서 감소,
  틱 t_arr+SERVICE_STEPS의 스텝 2에서 0 도달 → 상태 전이, 그 틱 스텝 4부터 이동.
- **워크드 예제** (무장애, 홈→픽업 거리 d₁, 픽업→하역 d₂):
  배차 t → 픽업 도착 t+d₁ → 서비스 t+d₁+1 ~ t+d₁+S → 하역 출발 t+d₁+S
  → 하역 도착 t+d₁+S+d₂ → 완료 t+d₁+d₂+2S.
  v1 검산: assign(t)→t₁=t+d₁, depart2(t₁+S)→t₂=t₁+S+d₂, done=t₂+S = **동일**.

## 4. 로봇 상태머신

```
IDLE_HOME ──배차──> TO_PICKUP ──도착──> SERVICING_PICKUP(타이머)
    ^                                        │ 만료
    │                                        v
    └──도착── TO_HOME <──배차없음── ┌── TO_DROPOFF ──도착──> SERVICING_DROPOFF(타이머)
                        (완료 후)   └────────────────────────────┘ 만료 → 태스크 완료
```

| 상태 | 목표 칸 | 비고 |
|---|---|---|
| `IDLE_HOME` | 자기 홈 | 배차 가능. stay 선호, 밀리면 다시 돌아옴 |
| `TO_PICKUP` | 태스크 frm 도킹 칸 | 배차 시점 = task.assigned 기록 |
| `SERVICING_PICKUP` | 현재 칸 (고정) | SERVICE_STEPS 틱. 밀리지 않음 (§5) |
| `TO_DROPOFF` | 태스크 to 도킹 칸 | 적재 상태 |
| `SERVICING_DROPOFF` | 현재 칸 (고정) | 만료 시 task.completed = t, 체인 진행 (§6) |
| `TO_HOME` | 자기 홈 | v1 패리티: 배차 불가 (§7). 도착 시 IDLE_HOME |

전이 규칙 상세:
- **도착 감지** = `상태가 TO_* && 현재 칸 == 목표 칸`. 도킹 칸 소유권 락은 두지 않는다
  — 같은 도킹 칸을 노리는 로봇이 여럿이어도 PIBT가 한 대만 그 칸에 세우므로,
  칸에 선 로봇이 곧 서비스 로봇이다. 나머지는 인근에서 밀리며 자연 대기.
  (지나가다 도킹 칸에 멈춘 로봇은 목표가 그 칸이 아니므로 서비스로 오인되지 않음)
- **SERVICING → 다음 상태**: 픽업 서비스 만료 → TO_DROPOFF (목표를 to 도킹 칸으로).
  하역 서비스 만료 → 태스크 완료 처리 후 즉시 배차 시도(§7), 태스크 없으면 TO_HOME.
- **pack 태스크의 frm**: v1과 동일하게 직전 태스크의 to (consol). 하역을 마친
  로봇이 그 자리에서 pack 태스크를 받으면 frm == 현재 칸이므로 TO_PICKUP 도착
  감지가 보통 그 틱에 즉시 성립한다 (상위 계급 밀어내기에 밀려난 경우만 지연 —
  PIBT가 자연 복귀시키므로 별도 특례 불필요).

## 5. PIBT 우선순위 체계

매 틱 `priority_order = sort(로봇, key=(계급, -대기누적, id))`:

| 계급 | 상태 | 이유 |
|---|---|---|
| 0 (최우선) | SERVICING_* | 먼저 resolve → stay 확정 → **밀리지 않음** (도킹 중 이탈 방지) |
| 1 | TO_DROPOFF | 적재 이동 — 짐 실은 로봇이 길을 얻는다 |
| 2 | TO_PICKUP | 픽업하러 가는 중 |
| 3 | TO_HOME / IDLE_HOME | 복귀·유휴 — 항상 양보 |

- pibt_core의 resolve 순서 = 우선순위이므로, 먼저 resolve한 로봇의 결정(stay 포함)은
  이후 로봇이 침범할 수 없다 (occ_next 예약 + `k not in next_of` 재귀 차단).
- **단, "계급 0 = 도킹 고정"은 uniform 비용에서만 성립.** candidates가 score 순이라
  θ 적용 후 wait_cost가 크거나 edge_cost가 싸지면 SERVICING 로봇이 서비스 중
  걸어 나갈 수 있다. 따라서 SERVICING 에이전트에는 **강제 stay dist 맵**(현재 칸만
  0, 나머지 전부 -1)을 공급한다 — candidates가 stay 단일 후보만 반환하므로
  θ와 무관하게 고정 보장.
- 같은 계급 내 `-대기누적`은 starvation 방지 (MVP와 동일), `id`는 결정론 보장.
  대기누적 갱신 규칙: 매 틱 이동 후, TO_* 상태에서 제자리면 +1, 이동했거나
  목표 도달이면 0으로 리셋 (pibt_core.run과 동일 규칙을 v2 루프 스텝 6에서 수행).
- 알려진 트레이드오프: SERVICING 로봇은 절대 안 밀리므로, 도킹 칸이 유일 통로 위에
  있으면 그 SERVICE_STEPS 동안 길이 막힌다. v1도 parked로 동일하게 막았으므로
  v1 대비 악화는 아님. (도킹 칸은 스테이션 인접 칸이라 본선 통로와는 대부분 분리)

**dist 맵 공급 규칙** (pibt_core.step의 `dists` 인자):
- pibt_core.dist_map은 캐시가 없으므로 v2가 **목표 칸 키 캐시**를 둔다 (v1의
  `_dist_cache` 상당). 목표 칸 집합은 유한: 도킹 칸 ~22곳 + 홈 N곳.
- 상태별: TO_PICKUP/TO_DROPOFF → 캐시된 dist_map(목표 도킹 칸),
  TO_HOME/IDLE_HOME → 캐시된 dist_map(자기 홈), SERVICING_* → 강제 stay 맵(위).

## 6. 태스크 흐름 — 두 가지 모드

구현 범위 결정([2026-08-31_구현범위_입고출고체인.md](2026-08-31_구현범위_입고출고체인.md))에
따라 흐름 모드를 플래그로 나눈다.

**기본 모드 (`--flow main`)** — 입고 + 출고(렉→패킹 직행):
- **입고**: `inbound_buf[i] → aisle_buf[a]` 1태스크. 주문과 독립인 지수분포 도착
  스트림 (`INBOUND_MEAN_GAP` 기본 50틱, `N_INBOUND` 기본 = 주문수).
- **출고**: 주문 1건 = 통로 k곳 (k ∈ {1,2,3}, 분포 기본 P=[0.5, 0.3, 0.2]),
  라인마다 `aisle_buf[aᵢ] → packing[p]` 1태스크. **packing은 주문당 1곳 고정.**
  주문 완료 = k개 태스크 전부 완료 (별도 pack 태스크 없음). 주문당 태스크 수 = k.
  같은 틱 다중 완료는 잔여 카운터로 판정 (§AND-join 주의사항은 완료 판정에만 적용).
- induction·consol·qc·vas·returns는 이 모드에서 미사용.

**v1 호환 모드 (`--flow v1compat`)** — B-1e 벤치마크 전용:
- 주문 1건 = `spawn_chain` v1과 동일한 3태스크 직렬 체인 (supply → retrieve → pack).
  입고 스트림 없음. A* vs PIBT 이동계층만 비교하기 위한 모드.

**rng 패리티 성립 조건 (전부 지켜야 주문 내용이 v1과 동일):**
v1의 rng 소비는 딱 두 곳 — ① 초기화 시 `order_times = cumsum(rng.exponential(
ORDER_MEAN_GAP, N_ORDERS)).astype(int) + 1` 단일 배치 호출 (int 캐스트까지 동일
수식이어야 함 — 동일 틱 중복 도착도 그대로 재현), ② 주문 도착 시점에 spawn_chain이
**4회 draw를 일괄 소비** (aisle → induction → consol → packing. 태스크는 나중에
lazy 생성돼도 draw는 도착 틱에 선불). v2도 도착 틱에 4 draw 전부 하고 체인 정의만
저장할 것 — 체인 진행 시점으로 draw를 미루면 주문 간 인터리브로 순서가 어긋난다.
- 동일 틱 다중 주문은 oid 오름차순으로 spawn (v1의 이벤트 push 순서와 동일).
- 홈 배치는 v1이 rng를 쓰지 않는 결정적 스캔이므로 초기화 순서는 무관 (각주).
- v2 본체(우선순위, PIBT, 배차)는 rng를 일절 쓰지 않는다 (§9.1 결정론의 전제).

공통 단순화 (명시적 한계): 피커 작업 시간 0 (출고 태스크는 주문 도착 즉시 배차
가능), 빈 토트 공급 생략, 입고 검수 생략. 지표는 주문당 태스크 수가 가변(k)이므로
tasks/h와 orders/h를 반드시 병기.

## 7. 배차 (v1 패리티 규칙)

B-1e에서 이동 계층 외 변인을 통제하기 위해 v1의 배차 의미를 그대로 따른다:
- waiting FIFO 순회, 태스크별 frm 최근접(맨해튼) 배차 가능 로봇 배정.
  동률이면 최소 rid (v1 `min()`의 동작과 동일).
- **배차 가능 = `IDLE_HOME` ∪ 하역 완료 직후(TO_HOME 전이 전) 로봇.**
  후자는 현재 칸(도킹 칸) 기준 최근접 계산 — v1의 free 이벤트가 `idle=True` 직후
  `dispatch(t)`를 호출해 도킹 칸에 선 채로 아무 waiting 태스크나 받는 것과 등가
  (자기 체인 후속에 한정되지 않음). 이 규칙이 §4의 "하역 만료 → 즉시 배차 시도"의
  근거이며, pack 승계도 이 경로로 성립한다.
- `TO_HOME` 중 재배차는 **금지** (v1에서 홈 주행 시작 후 idle=False인 것과 동일).
  개선 여지가 있으나 벤치마크 공정성을 위해 봉인, 이후 별도 실험 레버로 남긴다.
  각주: v1은 go_home 경로계획 실패 시 idle=True인 채 제자리 재시도 대기하며 그동안
  배차 가능했다. v2는 경로계획 실패 개념이 없어 이 상태 자체가 없음 (미세 차이).
- v1의 "배차 실패 → 태스크 유지" 케이스는 v2에서 발생하지 않는다 (v1은 경로계획
  실패가 배차 실패였지만, v2는 배차 = 목표 설정일 뿐이고 이동은 PIBT가 알아서).
  단, frm까지 정적으로 도달 불가(dist_map < 0)면 배차하지 않고 경고 (맵 오류 감지).

## 8. 지표 / 종료 / 워치독

- **[SUMMARY] JSON**: v1 필드 전부 유지(variant, n_robots, …, util, conflict_wait)
  + 신규 `turns_per_task`(태스크당 방향 전환 수), `orders_per_h`, `pushed_steps`.
  fleet_sweep 연동 3요소도 유지: `[SUMMARY] ` 접두 stdout 한 줄, `SIM_NO_PLOT=1`
  환경변수, 위치 인자 순서 (fleet_sweep은 stdout에서 이 줄만 파싱).
- **drive/wait 집계 — v1 정의 주의**: v1의 busy는 서비스 시간을 포함하지 않고
  **대기를 이중 계산**한다 (`drive_steps = len(path)-1`이 경로 내 제자리 스텝을
  이미 포함 + `wait_steps`가 같은 스텝을 또 더함 → busy = 이동+2×대기,
  conflict_wait = 대기/(이동+2×대기)). B-1e 비교를 위해 v2는 두 벌을 낸다:
  - `util` = **v1 호환 정의**: (이동틱 + 2×대기틱) / (N×makespan), 서비스 제외.
  - `util_incl_service` = (이동+대기+서비스 틱) / (N×makespan), 참고용 신규 필드.
  여기서 이동틱/대기틱은 TO_* 상태의 틱만 센다 (IDLE_HOME/SERVICING 제외).
- **conflict_wait**: v1 호환 = 대기틱 / (이동+2×대기). PIBT에서는 "밀려서
  후퇴한 틱"도 손실이므로 `목표 dist가 증가한 틱`을 별도 카운트
  (`pushed_steps`, 신규 지표 — conflict_wait에는 불포함, v1 정의 보존).
- **종료**: 전 주문의 최종 pack 태스크 완료 시. makespan = 그 틱.
- **워치독**: 최근 완료가 1500틱 이상 없으면 v1 STALL 덤프와 동일한 정보 출력 후 중단.
  + PIBT 특유의 라이브락(전원이 계속 움직이는데 아무도 도착 못 함) 감지를 위해
  "완료 없음" 기준을 유지 (이동 여부와 무관).
- **visit_count**: 틱마다 현재 칸 +1 (제자리 포함). v1은 계획 경로 점 단위 증가라
  사실상 동일 의미 — 히트맵 비교 가능.

## 10. 리스크 / 미해결

- **도킹 칸 혼잡**: 대기 슬롯 제도가 없어졌으므로 인기 도킹 칸(consol 등) 주변에
  로봇이 뭉칠 수 있다. PIBT 밀림으로 교착은 없겠지만 혼잡 비용은 지표로 관찰 후
  필요 시 "도킹 대기열 상한"(v1 MAX_STAGERS 상당)을 배차 단에서 복원.
- **우선순위 진동**: 같은 계급끼리 정면충돌 시 MVP에서 관찰된 밀치기 왕복.
  계급 분리로 완화 기대하나, 같은 계급 대치는 잔존 — 관찰 후 필요 시
  "직전 틱 전진자 우선" 타이브레이크 추가 검토.
- **rng 소비 순서**: v1 호환 모드에서 주문 내용(통로/스테이션 선택)이 v1과 완전히
  같으려면 rng 호출 순서를 v1과 맞춰야 함. 구현 시 v1의 spawn_chain 호출 시점
  (주문 도착 이벤트 시)과 동일하게 주문 도착 틱에 생성.
- **A트랙 미결**: 멀티라인 k 분포는 task_profile에 영향 → θ 스키마 합의 시 공유.
