## 0. 요지

1. `sim_v2_tasks.py`의 틱 루프를 **`fms_kernel.FmsKernel`** 클래스로 뽑는다. 커널 = 로봇 상태·배차·PIBT 이동·충전 존 복귀·도착/서비스 처리·지표 카운터. **시계·난수·I/O 없음.**
2. **주문 생성·분해는 커널 밖** (`order_stream.OrderStream`) — 02 시뮬 WMS 역할. 커널은 `submit_task()`로 태스크만 받는다.
3. 실행 셸 2종 중 첫째: **`sim_v2_tasks.py`는 얇은 CLI 셸**로 남아 CLI·SUMMARY·산출물·**결과 비트 동일**. 둘째: **`simpy_harness.py`**(선택, `import simpy` 지연) — 같은 커널을 SimPy 시계로 돌려 같은 결과가 나오는지 패리티 검사. MQTT 데몬은 이 구조 위에 나중에.
4. **이 이슈는 동작 불변 리팩터링.** 기준값 3개·CSV 80행·Isaac 내보내기 파일이 전부 비트 동일해야 끝난다. 배터리·충전 도크·고정 시간 실행(`--horizon`)은 **다음 이슈**(-143 설계 §2-2)에서 이 커널 위에 얹는다.

## 1. 왜 지금 이 순서인가

- MQTT 데몬(실행 계층·Isaac T4)도, 배터리 SimPy 사건도, 견적 엔진 바깥 루프도 전부 "커널을 함수처럼 부를 수 있어야" 시작된다. 지금은 스크립트 최상위에서 전역 변수로 돈다.
- 배터리를 먼저 넣으면 커널화 때 두 번 옮긴다(-143 설계 §2-2 "왜 SimPy 단계인가").
- 리팩터링과 새 모델을 한 MR에 섞으면 결과 변화의 원인을 못 가른다 → -144(불변) / 다음 이슈(배터리) 분리.

## 3. 커널 인터페이스

```python
cfg = KernelConfig(heading=True, zone=True, fixed_homes=False, check=False, dock_prio=True,
                   export=False, turn_ticks=TURN_TICKS, service_steps=SERVICE_STEPS,
                   dock_clear=3, stall_ticks=1500)
k = FmsKernel(free, st_cell, edge_cost, wait_cost, homes, zone_mask, n_robots, cfg)

k.submit_task(task)          # task = dict(id, order, kind, frm_name, to_name, frm, to, created, assigned=None, completed=None)
events = k.step(t)           # pos(t) → pos(t+1). 반환: [("task_completed", task), ("robot_idle", rid), ...]
k.robots, k.tasks_done, k.waiting, k.visit_count, k.dir_flow, k.zone_stats, k.export_log   # 셸이 읽는 상태
k.summary(n_orders, sim_hours) -> dict  # 지금의 [SUMMARY] dict 와 키·값 동일
```

### 3-1. `step(t)` 안의 순서 = 현행 틱 루프 (패리티)

현행 루프의 (1)~(6)을 그대로 옮기되, (1) 주문 도착은 셸이 `step` 호출 **전에** `submit_task`로 넣는다.

```
step(t):
  (2) 서비스 만료 처리 → task_completed 이벤트. **콜백 on_task_completed(task, t) 를 동기 호출**
      — v1compat 체인의 다음 태스크가 같은 틱 배차 전에 waiting 에 들어가야 한다(현행 complete_task 안의 chains.pop 과 동일 순서).
  (3) 배차 try_assign_all(t)                  (FIFO × 최근접, FREED → 존 복귀)
  (4) PIBT 한 스텝 (헤딩 tick_heading / 칸 step)
  (5) 존 지표·재선택                            (zone 이면)
  (6) 도착 감지 → 서비스 시작 / IDLE
  워치독: 1500틱 무진전 → StallError(덤프 문자열 포함) raise. 셸이 잡아 출력·exit 1 (계약 §3 불변)
```

콜백을 쓰는 이유: 이벤트 리스트만 돌려주면 셸이 다음 태스크를 넣는 시점이 "이번 틱 배차 후"가 되어 v1compat 패리티(2317/186.4)가 깨진다. 콜백은 kernel 생성 시 주입(`on_task_completed=stream.on_completed`).

### 3-2. 셸이 소유하는 것

- **시계**: `t`를 셸이 증가시키고 `step(t)`에 넘긴다 (SimPy 하네스는 `env.now`).
- **난수**: `OrderStream`만 rng를 갖는다. 커널은 rng를 만지지 않는다 (현행도 그렇다 — zone_goal·배차 전부 결정론).
- **종료 조건**: `stream.outstanding == 0` (현행 `outstanding_orders + outstanding_inbound > 0`). 고정 시간 실행이 들어오면 여기만 바뀐다.
- **I/O**: SUMMARY 출력, 히트맵, DIRFLOW npz, Isaac 내보내기(커널의 `export_log`를 파일로), STALL 덤프 출력.

### 3-3. 커널 안에 남는 것 (FMS 코어 책임)

배차(태스크 → 로봇), 이동(PIBT), 충전 존 복귀 목표(`zone_goal`), 도킹 이탈 우선(장치 ⑤), 서비스 타이머, 지표 카운터(drive/wait/svc/pushed/turns/rot/rev/replan/idle_moves), visit_count·dir_flow, `_trace`(STALL 덤프용), export_log.

배차가 커널에 남는 이유: "누가 어느 태스크를 하나"는 FMS의 결정이고 MQTT 데몬에서도 동일하게 필요하다. WMS는 태스크(from→to)만 준다.

## 4. 이동 규칙 — 코드 이동만, 로직 변경 0

- `tick_heading`, 칸 모델 분기, `zone_goal`, `try_assign_all`, `begin_service`, `_body_cells`, `dmap/dmap_h/staymap` 캐시, `_stag/_replan`, `DOCK_PRIO/DOCK_CLEAR`, `RANK/NAV/STATION_CELLS` → 메서드/속성으로. 전역 참조를 `self.`로 바꾸는 기계적 작업.
- 로봇 dict 구조·키 이름·초기화 순서(헤딩 초기 방향 결정 포함) 그대로.
- 반복 순서(`rids`, `robots.items()`)와 정렬 키 그대로 — 동률 결정이 바뀌면 결과가 바뀐다.
- **기대 검증: 결과 비트 동일.** 다르면 이동 실수다.

## 5. `OrderStream` (커널 밖)

```python
s = OrderStream(rng, flow, n_orders, n_inbound, order_gap, inbound_gap, stations, k_line_p, st_cell)
s.arrivals(t) -> [task, ...]        # 이 틱에 도착한 주문·입고를 태스크로 (주문 oid순 → 입고 순, 현행 (1) 과 동일)
s.on_completed(task, t)             # 커널 콜백: 주문 카운터, v1compat 체인 다음 태스크 → 반환값을 커널이 submit
s.outstanding                       # 남은 주문 + 입고
s.orders                            # oid -> dict(created, remaining, completed)
```
- `order_times`/`inbound_times`는 생성자에서 현행과 같은 순서로 뽑는다(패리티: main은 주문 → 입고 순 `rng.exponential` 두 번; v1compat은 주문만).
- `spawn_order`의 rng 소비 순서(v1compat 4 draw / main `choice` → `integers`×k → `integers`) 그대로.
- `task_seq` 카운터는 스트림이 갖는다 (id 연속성).

## 6. SimPy 하네스 (선택 셸)

```python
import simpy
env = simpy.Environment()
def ticker():
    t = 0
    while stream.outstanding > 0:
        for task in stream.arrivals(t): kernel.submit_task(task)
        kernel.step(t)
        t += 1
        yield env.timeout(1.0)          # DT
env.process(ticker()); env.run()
```
- 지금은 "SimPy 시계 위에서 같은 커널이 같은 답"을 보이는 것이 목적. 결과 = `sim_v2_tasks.py`와 SUMMARY 비트 동일(검증 항목).
- 다음 이슈에서 배터리(로봇별 SimPy 프로세스 → `kernel.request_charge(rid)`), 주문 도착을 별도 프로세스로, `env.run(until=horizon)`으로 고정 시간 실행.
- **의존성**: `simpy`는 `sim_engine` 필수 의존이 아니다. `infra/requirements.txt`에 넣지 않는다(워커는 CLI 셸만 쓴다). 하네스 파일 안에서 `try: import simpy except ImportError: 안내 후 exit 2`.
