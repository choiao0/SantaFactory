# 주문 생성기

우리 WMS 마스터(매장·상품·랙)에 공개 창고 데이터의 분포를 적용해 **하루치 합성 출고 주문**을 만드는 도구.
이슈 S15P21A106-153. 2026-09-08 구현. 생성기 산출물을 시뮬·백엔드에 연결하는 작업은 후속 이슈다.

기존 결정은 유지한다: **입고 보류**(`inbound_gap_s` 유지), **릴리스 기본 wave**(`smooth` 선택 가능), **ABC는 인기 순위 라벨만**(랙 재배치 보류).
산출물은 [큐 명세 §1-1](../../5_Docs/Web/시뮬엔진연동API명세서.md)의 `outbound[]` 구조와 메타데이터를 담은 JSON이다. 시뮬 소비와 DB 적재는 별도 연결 작업이 필요하다.

## 계획 평가

**독립 CLI로 프로파일과 마스터를 조합하는 방향은 적절하다. 다만 현재 마스터의 제약 때문에 원본 분포의 완전 재현이나 견적 정확도 향상을 바로 보장할 수는 없다.**

| 검토 사항 | 문제 | 반영할 결정 |
|---|---|---|
| 라인 수의 긴 꼬리 | 매장당 상품 6개에서 중복 없이 뽑으면 7라인 이상은 불가능 | `min(k, 상품 수)`로 제한하고 제한 전후 통계·잘린 주문 수 공개 |
| SKU 인기 비율 | 매장을 먼저 선택하고 매장 안에서 추출하면 전역 상위 20 % 점유율(약 74 %)이 보존되지 않음 | **상품을 먼저 뽑고 매장은 그 상품의 소속으로 정한다**(모델 가정: 3PL 에서 출고는 상품 인기가 결정하고 매장 출고량은 그 합). outbound_count 를 곱하므로 전역 점유율은 원본보다 높거나 낮아질 수 있고 `--check`로 측정한다 |
| 매장 의미 | 외부 고객과 우리 상품 소유 매장은 같은 개념이라고 단정할 수 없음 | 한 주문에 한 매장 상품만 넣는 것은 우리 마스터의 제약으로 명시 |
| 웨이브 검증 | wave와 smooth는 같은 시간대 비중을 사용하므로 07시 비중의 대소 비교는 잘못됨 | 시간대별 기대 비중과 시간대 내부의 분 단위 집중도 검증 |
| 재현성 | 실행 시각인 `generated_at`을 넣으면 같은 인자여도 JSON이 바뀜 | 실행 시각 제외, 키 정렬·들여쓰기 고정, 시드 분리 |
| 시뮬 효과 | 현재는 같은 통로 라인을 태스크 하나로 합치며 qty도 운반량에 반영하지 않음 | 주문 분포와 AMR 태스크 분포를 구분하고 매핑·용량 효과는 후속 검증 |
| 백엔드 적재 | orders/outbounds의 필수 필드와 task 관계가 빠져 있음 | 생성 파일 완성과 DB 적재 완료를 별도 완료 조건으로 구분 |

## 왜 필요한가

현재 [OrderStream](../sim_engine/order_stream.py)은 지수분포 간격으로 주문을 생성한다. `main` 흐름은 라인 수 1~3(확률 0.5/0.3/0.2, 평균 1.7)을 뽑고 통로를 균등 선택한다.
고정 시간 모드에서는 출고 교대 창 안에서만 생성한다. 버퍼 수는 맵에서 읽으며 현재 구성은 22개다.

고정된 주문 파일이 있으면 같은 부하로 AMR 대수·배차 정책을 비교하고 백엔드 샘플 주문에도 재사용할 수 있다.
다만 [현재 워커](../infra/worker/estimate_worker.py)는 명시 리스트를 경고 후 무시한다. 생성기만 완성해도 견적에 반영되는 것은 아니다.

## 참조 데이터와 확인 수준

Furlan de Assis, R. (2024). *Order Picking Dataset from a Warehouse of a Footwear Manufacturing Company*.
[Mendeley Data V1](https://data.mendeley.com/datasets/pf2w725pw3/1), DOI `10.17632/pf2w725pw3.1`, CC BY 4.0.
공개 설명에서 신발 제조 창고의 WMS 추출 자료이며 시각·피킹 웨이브 정보가 포함된다는 점을 확인했다. 익명화·무작위화가 적용된 자료이므로 우리 창고의 실측으로 취급하지 않는다.

**아래는 2026-09-08 원본 `Customer_Order.csv` 재집계값이다**(122,370행 / 주문 32,634 / SKU 208 / 고객 588 / 2023-01~10 / 영업일 178).
라인 = **주문별 고유 Reference**(사이즈 합침 — 우리 상품에 사이즈 축이 없음). 행 단위로 세면 평균 3.75·1라인 59 %로 크게 달라지므로 정의를 바꾸지 않는다.
추출 스크립트가 같은 값을 재현하면 확정값이 되고, 그때까지 테스트 정답으로는 쓰지 않는다.
**표의 분포는 비양수 수량 제외 → 완전 중복 제거 → 주문·Reference별 사이즈 합산을 완료한 데이터 기준이다**(122,370행 → 119,782행 → 라인 61,272).
제외 후 유효 라인이 없는 주문(2건)은 분포 집계에서 빼고 그 수를 프로파일 메타에 기록한다.

| 추출 항목 | 초안 참고값 | 프로파일 규칙 |
|---|---|---|
| 주문당 라인 수 | 1: .73, 2: .11, 3: .05, 4: .03, 평균 1.88, p90 4, **6 초과 4.2 %** | 주문별 고유 Reference 수의 전체 정수 히스토그램. `30+`는 보고서 표시용으로만 사용 |
| 라인당 수량 | qty=1: .52, 2: .20, 3: .08, 평균 3.5, p90 6 | (주문, Reference) 단위로 qty 합산 후 양의 정수 히스토그램 |
| SKU 인기 곡선 | 상위 20 % → 출고 수량 73.8 %, 50 % → 95.4 % | SKU별 qty 합 내림차순의 누적 곡선 |
| ABC 구성비 | A/B/C = 21/34/45 % | V1의 상품 개수 비율. 누적 출고량 기준 ABC와 구분 |
| 분·시간별 비중 | 07시 38 %(60분 중 43분에 분산, 최다 1분 10 %), 11~12시 25 %, 15~16시 18 % | 주문당 시각 1개로 집계한 1440칸 분포와 그 24칸 합계 |

확인된 원본 상태(2026-09-08): 주문 ID 충돌 없음(고객·시각이 둘인 orderNumber 0건), 시각은 분 단위, 비정수 qty 없음.
처리 순서: (1) qty ≤ 0 인 33행 제외, (2) **모든 열이 완전히 같은 중복 행 제거** — 원본 기준 2,559행이나 그중 4행은 (1)에서 이미 빠져 **2,555행 추가 제거**(122,370 − 33 − 2,555 = 119,782). 추출 중복인지 구분할 근거가 없어 보수적으로 제거하며, 총수량 5.6 %(12,735) 감소·건수를 프로파일 메타에 기록,
(3) 남은 같은 (주문, Reference, 사이즈) 행은 합산. 이 그룹 3,034개 중 2,813개는 웨이브 번호가, 1,896개는 수량이 달라 다른 웨이브에서 다시 피킹한 분할 기록으로 본다.
필수 값 누락·잘못된 날짜는 조용히 제거하지 않고 보고 후 실패한다. 날짜별 평균은 주문이 있는 날 기준이라 참고값이다.

07시 집중은 WMS 배치 릴리스로 보이지만(밤새 누적 주문의 아침 투입은 가설), 단일 폭발은 아니다 — 07시 안에서도 43분에 걸쳐 퍼져 있다.
`wave`는 관측된 분 단위 분포를 그대로 쓰고, `smooth`는 시간대 내부를 평활화하는 비교 시나리오다. 실제 고객 도착 과정을 복원했다고 표현하지 않는다.

```text
3_FMS/order_gen/

  generate_orders.py               profile + master + N + seed → JSON
  profiles/order_rules.json         집계 분포·출처·추출 규칙(원본 주문 행은 없음)
```

Python 표준 라이브러리 `csv`, `json`, `random`, `argparse`로 시작한다. sim_engine이나 DB 접속에 의존하지 않는다.
원본 CSV는 저장소에 넣지 않는다. `order_rules.json`은 개별 주문·고객·상품을 담지 않고 라인 수·수량·인기 순위·시각의 집계 분포만 생성 규칙으로 보관한다.
다운로드와 추출을 분리해 생성·테스트는 오프라인에서 실행한다.
프로파일에는 출처·라이선스, 원본/유효 행 수, 주문·SKU·고객 수, 집계 기간, 전처리 규칙(중복 합산·제외 건수)을 기록한다. 실행 시각은 재현 대상 파일에 넣지 않는다.

샘플 마스터의 기준은 백엔드 Flyway 시드 [R__seed_demo.sql](../../4_Web/SantaFactoryBE/src/main/resources/db/seed/R__seed_demo.sql)이다(2026-09-08 -168 에서 `santafactory_data.sql` 이 이 위치로 옮겨짐).
`stores(store_id, zone_id, outbound_count)`, `products(product_id, store_id, rack_id)`, `rack(rack_id, zone_id, field)`, `zones(zone_id, warehouse_id, facility_id)`, `facilities(facility_id, type, x, y)`(존 좌표 = 통로 버퍼 스테이션 좌표, 랙 매핑 입력)를 담는다. 변환은 `extract_master.py` 가 SQL 의 INSERT 를 정규식으로 파싱해 만들고(2026-09-08, 4개 표 22/132/132/22행 SQL 과 일치 확인), 백엔드 시드가 바뀌면 다시 돌려 교체한다.
현재 샘플은 매장·존 각 22개, 상품·랙 각 132개이며 매장당 상품 6개다. 생성 로직에 이 숫자를 고정하지 않는다.

## 입력과 오류 처리

| 입력 | 규칙 |
|---|---|
| `--profile` | 위 스키마의 프로파일 경로, 필수 |
| `--master` | 단일 창고의 마스터 JSON 경로, 필수 |
| `--orders N` | 하루 주문 수, 0 이상의 정수, 필수. `outbound_avg`가 같은 기간의 주문 건수임을 확인한 호출자가 전달 |
| `--seed` | 정수, 기본 42 |
| `--release wave\|smooth` | 기본 `wave` |
| `--check` | 생성 JSON은 stdout, 분포 비교·진단은 stderr |
| `--output`, `-o` | UTF-8 주문 JSON 저장 경로. 생략하면 stdout |

입력 배열은 ID순으로 정규화하고 ID 중복, 끊어진 참조, 중복 랙 `field`, 매장과 상품 랙의 존 불일치를 검사한다.
빈 마스터, 양의 정수가 아닌 라인 수·qty 값을 거부한다. 분포 가중치는 비음수이고 합이 양수, 누적 곡선은 단조 비감소여야 한다. 시간 분포는 분 분포의 합계로 유도한다.
N=0도 입력 검증 후 빈 `outbound`와 0건 통계를 출력한다. 오류는 비정상 종료하며 성공 JSON을 출력하지 않는다.

```bash
cd 3_FMS/order_gen
python generate_orders.py --profile profiles/order_rules.json --master master/santafactory_sample.json --orders 800 --seed 42 --output orders.json
python generate_orders.py --profile profiles/order_rules.json --master master/santafactory_sample.json --orders 500 --seed 42 --check --output orders.json
python -m unittest -v
```

## 생성 절차

1. **상품 인기 순위.** ID순 상품 목록을 시드로 섞어 인기 순위를 배정한다. 상품 수 M, 보간된 누적 곡선 C에 대해 순위 i의 인기 가중치는 `C(i/M) - C((i-1)/M)`이다.
   A/B/C 는 인기 순위 순으로 `A = round(0.21·M)`, `B = round(0.34·M)`, `C = M − A − B` 개로 라벨만 붙인다. M=132이면 28/45/59. `meta.abc`에 상품 ID 목록을 기록한다(생성 후 실적 재분류가 아님).
2. **전역 상품 가중치.** `가중치 = 인기 가중치 × 소속 매장의 outbound_count 비율`. 모델 가정: 3PL 에서 출고는 상품 인기가 결정하고 매장(고객사) 출고량은 그 합이며,
   outbound_count 는 "이 브랜드가 전체적으로 더 나간다"는 보정값이다. 매장 선택 확률은 `b_s × Σ(그 매장 상품 p_i)` 에 비례하고, 첫 라인 분포는 p 가 아니라 p × b 이므로
   **전역 상위 20 % 점유가 원본(73.8 %)으로 보존된다는 보장은 없다**(같은 p 라도 b 에 따라 위아래로 크게 움직인다). 원본 점유를 첫 라인에서 그대로 쓰려면 b 를 곱하지 않는 경로를 쓴다:
   모든 매장의 outbound_count 가 누락이면 곱하지 않는다(상품 인기만, 매장 비중은 결과).
   일부 누락·음수·전체 0이면 입력 오류. 가중치가 양수인 상품이 하나도 없는 매장은 주문을 받지 않는다.
   선택 가능한 매장마다 양의 가중치 상품 수가 생성 가능한 최대 `k_effective` 이상인지 사전 검증하고, 부족하면 실패한다(예: 가중치 `[1,0,0,0,0,0]` 은 2라인부터 뽑을 수 없다).
3. **주문 내용 N건.** 원본 라인 수 k를 뽑는다. **첫 라인은 전역 가중치로 상품을 뽑고, 그 상품의 매장이 이 주문의 매장이다**(매장을 따로 뽑지 않는다).
   나머지 라인은 그 매장의 남은 상품에서 인기 가중치로 하나씩 뽑고 제거한다(비복원). 매장 상품 수 m에 대해 `k_effective = min(k, m)`.
   중복 상품이나 다른 매장 상품으로 k를 채우지 않는다. 각 라인의 qty는 별도 히스토그램에서 뽑는다. `clipped_orders`와 `dropped_lines = Σ(k-k_effective)`를 기록한다.
   잘림의 영향은 잘린 주문 비율과 제거된 라인 비율(`dropped_lines`)로 평가한다. 원본에 상한 6 을 걸면 주문 4.2 %가 잘리지만 **라인은 10.3 %가 사라지고**(6,301/61,272) 평균 라인 수가 1.88 → 1.68 로 내려간다.
   라인 수·qty·시각은 독립 추출이므로 원본의 변수 간 상관관계는 보존하지 않는다.
4. **릴리스.** 공통 시간대 분포에서 시간을 선택한다. `wave`는 해당 시간의 조건부 분 분포로 분을 선택하고 0~59초를 균등 추가한다. 이는 분 내부 지터라는 모델 가정이며 정확한 동시 배치 재현은 아니다.
   `smooth`는 해당 시간 안 0~3599초를 균등 선택한다. 같은 초의 주문은 허용하며 강제로 시각을 모두 다르게 만들지 않는다.
   `ordered_at_s` 는 **자정 기준 초**(0~86399)로 고정한다. 시간창 자르기·시작 시각 이동은 후속 연결 이슈의 `[a,b)` 규칙이 맡고, 여기서는 필터링이나 압축을 하지 않는다.
5. **정렬·출력.** `(ordered_at_s, 원래 생성 순번)`으로 정렬하고 파일 안에서만 유효한 `order_id`를 1부터 부여한다. 라인은 product_id순으로 정렬하고 실제 lines·units 합계를 meta에 넣는다.
   내용 생성과 릴리스의 난수는 구분한다(예: `Random(seed)`, `Random(seed + 1)`). release만 바꿔도 주문 내용·인기 순위는 유지한다. 정렬 후 order_id는 달라질 수 있다.

결정론 규칙 네 가지: 같은 입력·인자 → 같은 JSON, 키 정렬·들여쓰기·끝 개행 고정, meta 에 실행 시각·절대 경로를 넣지 않음, 내용 난수와 릴리스 난수 분리. meta 에는 유효 인자(profile 이름·seed·release·orders)와 생성 통계(lines·units·abc·clipped_orders·dropped_lines)를 기록한다.

### 마스터 제약과 통계

상품이 m개인 매장의 라인 수는 `j < m`에서 `P(k_effective=j)=P(k=j)`, j=m에서 `P(k_effective=m)=P(k≥m)`이다.
전체 기대 분포는 이 분포를 매장 선택 확률로 가중 평균한다. 검증은 원본과 이 **제약 적용 후 기대 분포**를 구분한다.

상품을 먼저 고르므로 존별 주문 편중은 상품 인기 × outbound_count 의 합으로 나오는 결과값이다. 전역 상위 20 % 점유는 b 의 곱과 2라인 이후의 매장 안 추출 때문에 원본보다 높거나 낮아질 수 있으며, 값은 `--check`로 측정한다.
한 매장의 랙이 같은 버퍼로 매핑되면 현재 태스크 묶음 규칙에서는 다라인 주문도 출고 태스크 하나가 된다. 여러 버퍼로 매핑되는 경우도 있으므로 확정 매핑 후 주문당 고유 버퍼 수를 측정한다.

## 출력 계약

아래는 필드 설명용 축약 예시다. 실제 meta에는 전체 상품 ABC 목록과 제약 통계(clipped_orders·dropped_lines)도 포함한다.

```json
{
  "meta": {
    "profile": "order_rules",
    "seed": 42,
    "release": "wave",
    "orders": 1,
    "lines": 2,
    "units": 3
  },
  "outbound": [
    {
      "order_id": 1,
      "store_id": 3,
      "ordered_at_s": 25212,
      "lines": [
        {"product_id": 14, "rack_id": "C2", "qty": 1},
        {"product_id": 17, "rack_id": "C5", "qty": 2}
      ]
    }
  ]
}
```

`store_id`는 백엔드 적재용 추가 키다. 큐 명세 §1-3의 모르는 필드 무시 규칙을 따르되 실제 소비 DTO에서 허용되는지는 연결 시 확인한다.
출력 `rack_id`는 DB 숫자 PK가 아니라 참조 랙의 `field` 문자열이며 product_id로 찾은 랙과 일치해야 한다.
이 파일은 완전한 `sim.request`가 아니다. 호출자가 `outbound` 배열을 꺼내 `run_id`, `amr`, `horizon_s` 등 요청 필수 필드와 조합한다.

## 시뮬·백엔드 연결

**시뮬 연결은 S15P21A106-156 에서 완료**(계약 v2.5). 규칙은 [커널·시뮬 구조의 명시 주문 모드](커널_시뮬_구조.md#명시-주문-모드), 랙 매핑은 [맵·충전 존](맵_충전존.md#랙--통로-버퍼-매핑).

- 시뮬: `python sim_v2_tasks.py exp 6 0 101 1 --horizon=7200 --shifts=in,in,out,out,out,out --inbound-gap=48 --orders-file=win.json [--capacity=8]`
- 시간창: `python order_gen/slice_orders.py day.json --start 07:00 --end 09:00 -o win.json` → horizon_s = 7200. 창 밖 주문은 시뮬이 버리고 `orders_skipped` 에 센다.
- 견적 워커(-158): 백엔드가 outbound[] 를 비워 보내므로 워커가 `generate()` → `rescale_orders()`(창고 출고 시간대로 비례 매핑) → `slice_orders()` 로 만든다. 견적_워커.md "주문 자체 생성".
- 워커: 요청 `outbound[]` 가 비어 있지 않으면 `--orders-file`, `amr.capacity` 가 정수면 `--capacity`(단위 = 상품 개수). 비어 있으면 간격 모드.
- **시뮬은 상품이 아니라 버퍼만 본다.** 매장 = 버퍼라 한 주문의 라인은 토트 하나로 합쳐지고(적재량 없으면 1왕복), §분포 진단의 전체 라인 점유율 저하는 시뮬 결과에 영향이 없다.
- DB 적재(orders/outbounds)는 아직 없다. 아래 남은 항목.

### 남은 연결 (백엔드)

- **시간창 해석:** `slice_orders.py` 는 창 시작에 미처리 주문이 없는 초기 상태로 잘라 낸다(이전 부하를 이어받지 않음). 피크 창 결과를 하루 전체 대표값으로 해석하지 않는다.
- **DB 적재:** [DDL](../../4_Web/SantaFactoryBE/src/main/resources/db/migration/V1__init_schema.sql)과 엔티티 기준 orders는 `status`, `order_code`가, outbounds는 `store_id`, `status`, `task_id`가 추가로 필수다. 유효한 task와 그 참조를 만드는 정책 또는 스키마 조정이 먼저 필요하다. 어댑터가 시나리오 날짜를 받아 `order_at = 기준 날짜 00:00 + ordered_at_s`로 변환한다. 파일 order_id는 새 DB ID로 매핑하고 트랜잭션·재적재 중복 처리도 정의한다.

V1 생성기는 재고를 차감하거나 부족분을 보충하지 않는다. 출력은 재고 가용성과 무관한 수요 시나리오이며 실제 출고 실행 가능성을 보장하지 않는다.

## 검증과 완료 조건

통계 비교는 모델의 한계를 보여 주는 진단이고, 구조·결정론 검사는 자동 통과/실패 기준이다. N=500 한 번의 임의 허용 오차로 원본 재현을 판정하지 않는다.

| 검증 | 기준 |
|---|---|
| 추출 | 작은 CSV에서 qty ≤ 0 제외 → 완전 중복 제거 → 합산 순서, 고유 주문 집계, 잘못된 입력 처리 검증. 원본 CSV 로 재추출한 프로파일이 저장본과 일치 |
| 구조 | 주문 수=N, 연속 ID, 시각 오름차순 및 `[0,86400)`, 양의 정수 qty, 매장 소속·상품-랙 참조 일치, 라인 중복 없음 |
| 결정론 | 동일 입력 두 번 실행의 JSON 문자열 동일. release만 바꾸면 order_id·시각을 제외한 주문 내용의 다중집합과 ABC 동일 |
| 제약 | 상품 1개·6개인 고정 마스터에서 라인 상한, clipped_orders·dropped_lines·실제 합계 검증. N=0·잘못된 가중치·깨진 참조 검증 |
| 시간 | 07:00에만 질량이 있는 작은 프로파일에서 wave는 `[07:00,07:01)`, smooth는 `[07:00,08:00)`. 고정 시드의 충분한 표본으로 smooth가 첫 1분 밖에도 분산되는지 확인 |
| ABC | 모든 상품이 한 등급에만 포함되며 누락 없음. 132개에서 28/45/59, 작은 상품 수에서도 합계 보존 |
| 분포 진단 | 원본·제약 적용 후 기대값·생성 결과의 라인 분포 비교. qty·매장 비중·분/시간 비중·상위 20 % SKU의 qty 점유율(상위 상품 수 `ceil(0.2*M)`) 을 **전체 라인**과 **첫 라인만** 두 값으로 출력. 첫 라인 값은 전역 가중치(p×b)의 효과, 둘의 차이는 2라인 이후 매장 안 추출의 희석분이다 |

wave와 smooth의 **시간대별 기대 비중은 같다**. 분 단위 집중도 차이는 원본 분포가 시간 안에서 불균등할 때만 나타난다.
상위 20 % 점유율 73.8 %는 참고값이며 합격 기준이 아니다(outbound_count 곱과 매장 안 추출로 원본보다 높거나 낮아질 수 있다). 여러 고정 시드의 큰 표본 진단으로 모델 왜곡의 크기를 확인한다.

2026-09-08 실측(현재 마스터, 목표 0.742):

| 실행 | 첫 라인만 | 전체 라인 |
|---|---:|---:|
| N=500 시드 42 | 0.724 | 0.526 |
| N=2000 시드 1 / 2 / 3 | 0.738 / 0.816 / 0.748 | 0.562 / 0.738 / 0.572 |

첫 라인은 목표 근처(b 곱으로 시드마다 ±0.08)이고, 전체 라인이 0.15~0.2 낮은 것은 **2라인 이후의 매장 안 추출** 때문이다. 상위 20 % 상품 26개가 매장 22곳에
평균 1.2개씩 흩어져 있어 같은 매장의 나머지 5개는 대부분 비인기 상품이고, 다라인 주문의 추가 라인이 점유를 희석한다. 모델 가정에 따른 예상된 결과이며 결함이 아니다.
전역 점유를 더 지키려면 매장별 상품 수를 늘린 마스터(미룬 것 3)나 추가 라인도 전역에서 뽑는 다른 모델이 필요하다.

구현 순서는 다음과 같다.

1. **추출 기준 확정:** CSV 열·주문/SKU/시각 의미를 확인하고 재현 가능한 프로파일과 작은 추출 검증을 만든다. 참고 수치와 다르면 문서·프로파일을 실제 집계값으로 갱신한다.
2. **생성기 구현:** 마스터 스냅샷 검증, 가중치·라인 제한·릴리스·결정론 출력을 구현한다.
3. **생성 검증:** 고정 입력 검증과 N=500 샘플·큰 표본 분포 진단을 수행하고 실행 명령·제약 영향을 남긴다.
4. **이슈 완료:** CSV 없이 저장된 profile/master로 JSON을 생성·검증할 수 있으면 S15P21A106-153 완료. 실제 시뮬 반영·DB 화면 표시는 후속 연결 이슈의 완료 조건이다.

## 미룬 것

1. **입고 생성·재고 보충:** 현재 `inbound_gap_s` 유지. 재고 연동이 필요할 때 별도 정책으로 설계한다.
2. **ABC 랙 재배치:** 지금은 순위 라벨만 출력한다. A 상품을 포장대 근처로 옮기는 배치는 별도 견적 레버("재배치 시 N 대 절감")로 분리한다.
3. **7라인 이상 주문(4.2 %):** 매장별 상품 수를 늘린 별도 마스터가 필요하다. 현재 마스터에서 주문 분할·중복 SKU로 통계를 맞추지 않는다.
4. **일별 변동·요일·변수 간 상관관계:** 대표일의 주변 분포부터 구현한다. 추출 가능한 요약은 메타데이터로만 보관한다.
5. **다른 업종:** 동일한 프로파일 스키마면 생성기를 재사용한다. 원본 CSV 스키마가 다르면 추출·정제 로직은 별도로 맞춰야 한다.
