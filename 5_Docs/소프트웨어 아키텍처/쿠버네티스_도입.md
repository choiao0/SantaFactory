# 쿠버네티스 도입

## 한 줄 결론

서버가 EC2 1대 + GPU 박스 1대 + GCP 워커 3대, 총 5대다. 각 서버를 compose 로 따로 관리하는 대신 **k3s(경량 쿠버네티스)로 하나로 묶고, 상태 없는 컨테이너부터 옮긴다.** 데이터를 가진 것(DB·브로커·저장소)은 compose 에 둔다.

## 1. 지금 구조

| 서버 | 무엇이 도는가 | 어떻게 올리는가 |
|---|---|---|
| EC2 (t3.xlarge, 4코어 16 GB, 사설 IP 172.26.3.57) | k3s 서버. compose: 백엔드·프런트·PDF 변환기·DB·RabbitMQ·Redis·MinIO·fms-core·host-orch·EMQX. 운영 도구: 레지스트리·Portainer·SonarQube·GitLab Runner | Jenkins 가 release 브랜치를 받아 compose 5개를 순서대로. 운영 도구는 수동 |
| GCP Spot VM 3대 (c4-highcpu-8, 물리 4코어 15.6 GB, 인스턴스 그룹 `des-workers`) | k3s 노드. 시뮬 워커 `sim-worker` 4개씩 12개 (2026-09-23 Ready 확인). EC2 보다 런당 2배 빠름(70 s → 30 s) | 부팅 때 `start.sh` 가 공인 6443 으로 k3s 에 합류. Jenkins 가 이미지를 바꾸면 k3s 가 교체 |
| GPU 박스 | Isaac Sim 러너(물리 검증 영상) | compose. 사람이 접속해 손으로 |

```
브라우저 ─▶ [EC2] host nginx(443) ─┬─ /     ─▶ frontend
                                   └─ /api ─▶ backend ─▶ db · rabbitmq · redis · pdf
[GCP ×3] sim-worker ×4 ─ Cloud NAT ─ 인터넷 TLS 5671 ─▶ [EC2] nginx ─▶ rabbitmq
[GPU]    러너 ───────── tailnet ────────────────────▶ [EC2] emqx 1883 · minio 9002
```

**문제.** compose 는 서버 한 대 안만 관리한다. 5대 중 Jenkins 가 배포하는 건 EC2 하나였고, 나머지는 사람이 접속해 올렸다. 한 곳을 빠뜨리면 옛 코드가 새 코드와 섞여 돌고(fms-core 배포 누락, S15P21A106-234), 백엔드는 배포마다 30~60초 끊긴다.

## 2. 쿠버네티스가 하는 일

**여러 대의 서버를 한 덩어리로 묶어, 컨테이너를 규칙대로 배치하고 죽으면 되살리는 관리자.** "워커 12개는 GCP 노드에, 백엔드는 EC2 노드에" 라고 적어 두면 어디에 올릴지·죽으면 어떻게 할지를 시스템이 정한다.

| | compose (지금) | 쿠버네티스 |
|---|---|---|
| 범위 | 서버 1대 | 서버 여러 대를 하나로 |
| 코드 배포 | 서버마다 빌드·재기동. 새 버전이 안 뜨면 내려간 채 남음 | 한곳에서 이미지 갱신. 새 버전이 준비될 때까지 옛 버전 유지, 실패 시 되돌림 |
| 컨테이너가 죽으면 | 그 서버에서만 재시작 | 다른 서버로 옮겨서라도 개수 유지 |
| 배우는 비용 | 파일 1개 | 개념 6~7개(Pod·Deployment·Service·Secret·Volume·Ingress), 관리자 메모리 약 1 GB |

**k3s 를 고르는 이유.** k8s 정식판과 명령·파일·개념이 같고 포장만 가볍다. 서버 1~5대에 맞고, 무료이며, 관리자 메모리가 1/3(0.7 GB)이다. 팀 문서와 러너 매니페스트(`2_Simulation/t3_amr/deploy/k8s/`)가 이미 k3s 전제다.

## 3. 무엇을 옮기고 무엇을 남기나

기준은 하나다. **상태(데이터)를 갖고 있는가, 옮겨서 얻는 것이 위험보다 큰가.**

| 서비스 | 판단 | 이유 |
|---|---|---|
| 시뮬 워커 (GCP) | **옮김** (1단계, 완료) | 상태 없음. 3대에 흩어져 관리 부담이 가장 컸다 |
| backend | **옮김** (3단계) | 상태 없음. 배포마다 끊기는 유일한 사용자 노출 서비스 → 롤링 배포로 무중단, 준비 확인 후 교체, 응답 없으면 재시작 |
| pdf 변환기 | **옮김** (3단계) | 상태 없음. backend 와 같은 배포 경로, 자원 상한을 매니페스트로 |
| frontend | **옮김** (3단계) | 정적 파일. 가장 단순 |
| Isaac 러너 (GPU) | 나중에 (2단계) | 매니페스트 있음. GPU 박스를 노드로 합류시키는 별도 작업 |
| fms-core, host-orch | 나중에, 선택 | 인스턴스 1개, 얻는 것이 작다. backend 가 안정된 뒤 같은 패턴으로 |
| DB, RabbitMQ, Redis, MinIO, EMQX | **남김** | 데이터가 EC2 한 대에 있다. "다른 서버에 살리기" 를 쓸 서버가 없고 볼륨 이전 위험만 생긴다. EMQX 1883·MinIO 9002 는 GPU 박스 접속점 |
| 레지스트리 | 남김 | k3s 가 이미지를 받는 곳. 안에 넣으면 순환 의존 |
| Portainer, SonarQube, GitLab Runner | 남김 | 운영 도구, docker.sock 사용 |
| host nginx | 남김 | TLS·certbot·Jenkins·Sonar·`/v2/`·5671 까지 맡는 입구. 컨테이너 쪽 주소만 바꾼다 |

**파드가 compose 서비스에 닿는 길(3단계).** compose 의 DB·브로커·Redis 는 `127.0.0.1` 에만 열려 있어 파드에서 안 닿는다. 파드를 EC2 네트워크에 얹는 방법(hostNetwork)은 포트를 독점해 두 개를 동시에 못 띄우므로 무중단 배포가 안 된다. 그래서 **포트를 EC2 사설 IP 에도 열고, 클러스터 안에 같은 이름의 안내판(headless Service + EndpointSlice)을 둔다**(2026-09-22 결정).

```
backend 파드 ─▶ "db" (Service) ─▶ 172.26.3.57:5432 ─▶ compose db 컨테이너
host nginx   ─▶ 10.43.0.80:8080 (고정 ClusterIP) ─▶ backend 파드
```

## 5. 결정과 주의

- **브로커 연결은 A 방식.** k3s 워커도 GCP compose 워커와 같은 공인 5671 + `sim-worker` 계정을 쓴다(2026-09-18). 바뀌는 것을 "워커를 올리는 주체" 하나로 묶어 문제 원인을 가리기 쉽게 했다.
- **NodePort 를 쓰지 않는다.** 보안그룹이 전 포트 개방이라 30000번대가 인터넷에서 닿는다. 고정 ClusterIP 는 EC2 안 프로세스만 닿는다.
- **사설 IP 바인딩도 밖에서 닿는다.** 공인 IP 가 1:1 NAT 라 5432·5672·6379 를 `172.26.3.57` 에 열면 인터넷에 노출된다. 245 와 같은 DOCKER-USER 규칙으로 막고, compose 바인딩보다 먼저 적용한다.
- **health 는 probes 경로만.** 기본 health 는 SMTP 까지 검사해 메일 서버 장애로 파드가 재시작될 수 있다. `readiness`·`liveness` 그룹을 쓰고 mail 은 뺀다.
- **SSE 는 종료 때 닫는다.** 35분짜리 SSE 가 열려 있으면 graceful 대기 30초를 매번 채운다. 종료 훅으로 닫고 브라우저가 새 파드에 다시 붙는다.
- **파괴적 마이그레이션은 롤링 금지.** 컬럼 삭제 등을 내는 release 는 `maxSurge 0` 으로 한 번 내리고 올린다. V1~V9 는 추가·분리형이라 롤링 가능.
- **워커 메모리 3 GiB.** 로봇 12·13대가 2 GiB 한도에 닿았다(+70 MB/로봇). 로봇 28대·주문 6,000 건은 넘칠 수 있다.
- **tailnet 은 GPU 박스 경로만 남았다.** GCP 는 249 에서 공인 경로로 바꿨다. GPU 박스를 노드로 합류시킬 때 같은 방식(공인 + TLS + 출발지 제한)으로 바꾸면 걷어낼 수 있다.

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 레지스트리 | 이미지를 올려 두는(push) 창고. 여러 서버가 같은 이미지를 받아(pull) 간다 |
| 노드 | 클러스터에 합류한 서버 한 대 |
| Pod(파드) | 컨테이너를 감싼 실행 단위. 보통 컨테이너 1개 = 파드 1개. 죽으면 새 이름으로 다시 생긴다 |
| Deployment | "이 이미지로 파드 N개 유지" 규칙. 이미지가 바뀌면 준비된 것부터 하나씩 교체 |
| Service | 파드들에 붙는 고정 이름·주소. compose 의 서비스 이름과 같은 역할. ClusterIP 는 클러스터 안 주소, NodePort 는 노드 포트로 밖에 여는 것 |
| Secret | 비밀번호·설정 묶음. 지금 `.env` 파일 |
| taint / toleration | 노드에 "여기 올리지 마" 표시와, 그 표시를 넘는 파드 쪽 허가 |
| tailnet | Tailscale 사설망. 지금은 GPU 박스 → EC2 접속에만 쓴다 |
