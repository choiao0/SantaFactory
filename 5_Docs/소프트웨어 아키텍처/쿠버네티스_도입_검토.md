# 쿠버네티스 도입

## 한 줄 결론

서버가 EC2 1대 + GPU 박스 1대 + GCP 워커 3대, 총 5대가 되었다. 각 서버를 compose 로 따로 관리하는 대신 **k3s(경량 쿠버네티스)로 하나로 묶고, 시뮬 워커부터 옮긴다.** DB·메시지 브로커·파일 저장소는 지금처럼 compose 로 둔다.

## 1. 지금 구조와 문제

| 서버 | 무엇이 도는가 | 어떻게 올리는가 |
|---|---|---|
| EC2 (t3.xlarge, 4코어 16 GB) | 백엔드·프런트·DB·RabbitMQ·Redis·MinIO·PDF 변환기, fms-core, EMQX, host-orch. 시뮬 워커 2개는 GCP 보다 느려 내림 | docker compose 4개. Jenkins 가 release 브랜치를 받아 순서대로 빌드·기동 |
| GCP Spot VM 3대 (c4-highcpu-8, 물리 4코어 15.6 GB, 관리형 인스턴스 그룹 `des-workers`) | 시뮬 워커 4개씩, 총 12개. EC2 보다 런당 2배 이상 빠름(70 s → 30 s) | compose(`infra/compose.estimate.gcp.yml`). 담당자 PC 의 `infra/gcp/deploy_gcp.sh` 가 tailnet SSH 로 3대에 코드를 복사해 각자 빌드·재기동. VM 이미지 `des-worker-v1` + 시작 스크립트 `start.sh`(부팅 때 tailnet 가입·compose 기동) |
| GPU 박스 | Isaac Sim 러너(물리 검증 영상) | compose. 사람이 접속해 손으로 |

시뮬 워커는 GCP 12개(2026-09-18 브로커 consumers=12 확인, S15P21A106-246). RabbitMQ 가 큐에서 한 건씩 나눠 주므로 서버가 늘어도 워커 코드는 같다. GCP 워커는 공인 주소의 AMQPS 5671(EC2 nginx 가 TLS 를 풀어 브로커로 넘김)에 전용 계정 `sim-worker` 로 붙고, 출발지는 Cloud NAT 고정 IP 하나로 ufw 에서 제한한다. Spot 이라 구글이 VM 을 회수할 수 있고, 그러면 그룹이 새 VM 을 만들어 `start.sh` 로 다시 올린다.

**문제.** compose 는 "서버 한 대 안"만 관리한다. 5대 중 Jenkins 가 배포하는 건 EC2 하나뿐이고, 나머지 4대는 코드가 바뀔 때마다 사람이 다시 올려야 한다(GCP 는 담당자 PC 에서 스크립트로, GPU 박스는 접속해서). 워커 이미지를 바꾸면 VM 이미지도 새로 굽고 템플릿을 갈아야 Spot 재생성 뒤에도 새 코드가 뜬다. 한 곳을 빠뜨리면 옛 코드 워커가 새 코드 워커와 섞여 돌고, 결과가 조용히 어긋난다. 실제로 fms-core 가 Jenkins 에 안 들어가 있어 배포가 빠진 적이 있다(S15P21A106-234).
지금은 반대 방향의 어긋남도 있다. 실제 워커는 전부 GCP 에 있는데 Jenkins 는 여전히 EC2 워커 2개를 올리고 그 기동을 확인한다. release 를 돌리면 내려 둔 EC2 워커가 다시 뜬다.

## 2. 쿠버네티스가 하는 일

**여러 대의 서버를 한 덩어리로 묶어, 컨테이너를 규칙대로 배치하고 죽으면 되살리는 관리자.**
"시뮬 워커 12개는 GCP 서버에, GPU 러너는 GPU 있는 서버에" 라고 적어 두면 어느 서버에 올릴지·죽으면 어떻게 할지를 시스템이 정한다.

### 그림으로 보는 전후

**지금** — 서버 5대를 각자 따로 관리한다.

```
[GCP 1] docker  worker×4 ─┐  Spot, 외부 IP 없음
[GCP 2] docker  worker×4 ─┼─ Cloud NAT ─ 인터넷 TLS 5671 ─▶ [EC2] nginx ─▶ rabbitmq
[GCP 3] docker  worker×4 ─┘                                     backend·db·redis·minio·pdf·fms-core·emqx
[GPU]   docker  러너 ─────── tailnet ─────────────────────────▶      (compose 4개, Jenkins 는 여기만)
       ▲ 코드가 바뀌면 담당자 PC 에서 deploy_gcp.sh 로 3대에 복사·빌드, GPU 는 접속해서 up
```

**k3s 를 붙인 뒤(1단계)** — 5대가 클러스터 하나가 되고, 워커 배치는 관리자가 한다.

```
                    ┌──────────── k3s 클러스터 (tailnet 사설망) ────────────┐
                    │                                                        │
[EC2]  k3s 서버(관리자)                                                       │
       ├ compose 그대로: rabbitmq · db · redis · minio · emqx                │
       ├ compose 그대로(1단계): backend · pdf · fms-core · nginx              │
       └ 레지스트리(이미지 창고) ◀── Jenkins 가 빌드해서 push                 │
                    │                                                        │
[GCP 1] 노드 ─ worker worker worker worker ┐                                 │
[GCP 2] 노드 ─ worker worker worker worker ┼─ Deployment "sim-worker" 12개  │
[GCP 3] 노드 ─ worker worker worker worker ┘  배치 규칙: GCP 노드에만        │
                    │                                                        │
[GPU]   노드 ─ 러너  (2단계에서 합류)                                          │
                    └────────────────────────────────────────────────────────┘
```

| 흐름 | 지금 | k3s 뒤 |
|---|---|---|
| 워커 → 큐 연결 | 인터넷으로 nginx 5671(TLS)을 거침 | 사설망 안에서 `rabbitmq:5672` 이름으로 직접. 공인 포트·중계 없음 |
| 코드 배포 | 담당자 PC 에서 3대에 복사해 각자 빌드. 그 PC 와 SSH 키에 묶임 | Jenkins 가 한 번 빌드 → 레지스트리 push → "새 이미지로" 한 줄. 관리자가 노드마다 갈아 끼움 |
| 워커 개수 | VM 마다 `WORKER_REPLICAS=4` | Deployment 에 12 하나. 노드 추가는 합류 한 줄 + 숫자 변경 |
| Spot 회수·서버 장애 | 그룹이 VM 을 다시 만들고 `start.sh` 가 그 VM 의 워커 4개를 올림. 그동안은 8개 | 회수 즉시 남은 노드에 다시 띄워 12개 유지. 새 VM 은 합류만 하면 됨 |
| Jenkins 의 EC2 워커 | compose up 으로 내려 둔 워커가 다시 뜸 | "빌드 → push → 교체" 라 EC2 에 워커가 생기지 않음 |

3단계까지 가면 backend·pdf·fms-core 도 Deployment 로 들어가고 nginx 자리를 인그레스가 맡는다. DB·브로커·Redis·MinIO 는 끝까지 compose 로 EC2 에 남는다.

### compose 와 비교

| | compose (지금) | 쿠버네티스 |
|---|---|---|
| 범위 | 서버 1대 | 서버 여러 대를 하나로 |
| 서버 늘리기 | 서버마다 접속해 저장소·설정·`up -d` | 합류 명령 한 줄, 개수는 숫자 하나 |
| 코드 배포 | 서버마다 다시 빌드·재기동 (지금 5대 중 4대가 사람 손) | 한곳에서 이미지 갱신 → 전 서버 자동 교체 |
| 컨테이너가 죽으면 | 그 서버에서만 재시작 | 다른 서버로 옮겨서라도 개수 유지 |
| 배포 실패 | 새 버전이 안 뜨면 서비스가 내려간 채로 남음 | 새 버전이 정상 응답할 때까지 옛 버전 유지, 실패 시 자동 되돌림 |
| 설정·비밀번호 | `.env` 파일을 서버마다 복사 | 한곳(Secret)에 두고 필요한 컨테이너만 받음 |
| 배우는 비용 | 파일 1개, 개념 거의 없음 | 개념 6~7개(Pod·Deployment·Service·Ingress·Secret·Volume), 파일 4~5개 |
| 상시 자원 | 없음 | 관리자 자체가 메모리 0.7~1 GB, CPU 반 개 |
| 문제 추적 | `docker logs` | `kubectl` 로 여러 층(파드·서비스·인그레스) |

### 우리 서비스에서의 장단점

**장점**
- 워커 서버 3대(GCP)를 한곳에서 배포·증감한다. 지금은 담당자 PC 의 스크립트와 VM 이미지 굽기에 묶여 있고, Jenkins 는 실제와 다른 EC2 워커를 올린다.
- Spot 회수로 VM 이 빠지면 남은 서버로 워커 수를 유지한다. GCP 크레딧이 끝나 노드가 전부 사라져도 규칙만 남아 있으면 EC2 에서 가능한 만큼 돈다.
- GPU 박스 러너도 같은 방식으로 배포·복구된다.
- 서버 간 통신이 사설망 안에서 이뤄져 공인 포트를 열 필요가 줄어든다(지금은 도커가 방화벽을 우회해 열려 따로 막았다, S15P21A106-245).

**단점**
- 배울 게 많고 파일이 늘어난다. 전환에 약 1주.
- EC2 한 대에만 있는 DB·브로커는 옮겨도 이득이 없다. 서버가 하나라 "다른 서버로 살리기"가 불가능하고 데이터 이전 위험만 생긴다.
- 이미지 레지스트리가 새로 필요하다(6. 용어). SSAFY GitLab 은 컨테이너 레지스트리가 꺼져 있어(Package Registry 만 있음) EC2 에 직접 둔다.
- Spot VM 이 재생성될 때 k3s 노드로 다시 합류하는 절차를 `start.sh` 에 넣어야 한다. 지금 tailnet 가입을 처리하는 것과 같은 자리이고, 템플릿만 바꾸면 되므로 VM 이미지는 그대로다.
- 속도 자체는 이미 워커 12개로 얻었다. 쿠버가 더해 주는 것은 속도가 아니라 **관리**다.

## 3. k8s 와 k3s

같은 쿠버네티스다. 명령·설정 파일·개념 전부 같다. 차이는 포장.

| | k8s (정식판, 또는 AWS EKS) | k3s (경량판) |
|---|---|---|
| 설치 | 구성 요소를 따로 설치·연결. 관리 서버 3대 권장 | 프로그램 하나, 명령 한 줄. 서버 1대로 시작 |
| 관리자 메모리 | 약 2 GB | 약 0.7 GB |
| 딸려 오는 것 | 저장소·로드밸런서·인그레스 따로 설치 | 내장 |
| 비용 | EKS 는 관리 서버만 월 약 70달러 | 무료 |
| 규모 | 수십 대 이상 | 서버 1~5대 |

**k3s 를 고르는 이유.** 서버 5대 규모에 맞고, 무료이며, 메모리를 1/3 만 쓴다. 팀 문서가 이미 k3s 를 전제로 하고 러너용 매니페스트(`2_Simulation/t3_amr/deploy/k8s/`)가 저장소에 있다. 배운 내용은 k8s 와 같아 나중에 큰 환경으로 가도 그대로 쓴다.

## 4. 진행 순서

| 단계 | 내용 | 얻는 것 | 공수 |
|---|---|---|---|
| 0 | **이미지 레지스트리** 준비 — EC2 에 `registry` 컨테이너, tailnet 주소 `100.100.149.68:5000` 으로만 열기(GitLab 은 컨테이너 레지스트리 없음). 각 노드에는 이 주소를 평문으로 받는 설정 파일(`registries.yaml`)이 필요하다 | 다른 서버가 이미지를 받아 갈 수 있음. 지금 GCP 3대는 각자 빌드하고 있어 이것부터 필요 | 반나절 |
| 1 | EC2 에 k3s 서버 설치. GCP 3대를 노드로 합류(tailnet). `start.sh`(템플릿 시작 스크립트)에 합류 절차 추가, 메타데이터 2개 넣은 새 템플릿으로 교체. 시뮬 워커를 Deployment 로 옮기고 개수 12, 배치는 GCP 노드로 한정. Jenkins FMS 단계를 "빌드 → 푸시 → 교체" 로 | 워커 3대 한곳 배포, 서버 빠져도 개수 유지, Jenkins 가 실제 배치와 일치 | 2일 |
| 2 | GPU 박스를 노드로 합류. NVIDIA 플러그인, 기존 러너 매니페스트 적용 | 러너 자동 배치·복구 | 1~2일 |
| 3 | 백엔드·프런트·PDF 변환기·fms-core·host-orch 이전. nginx → 인그레스 | 안전한 배포, 설정 한곳 | 3~4일 |
| 하지 않음 | Postgres·RabbitMQ·Redis·MinIO·EMQX | 얻는 것 없음, 데이터 이전 위험만 | — |

워커를 먼저 하는 이유: 이미 4대에 흩어져 있어 관리 부담이 가장 큰 곳이고, 특수 설정이 없어 가장 쉽고, 노드가 늘어도 코드 변경이 없다.

## 5. 주의할 것

- RabbitMQ 5672 는 지금 EC2 의 `127.0.0.1` 에만 열려 있다(tailnet 리스너는 09-18 닫음). GCP 워커는 AMQPS 5671 + 전용 계정으로 붙는다. k3s 워커도 **처음에는 같은 5671 경로와 계정을 그대로 쓴다**(2026-09-18 결정). 바뀌는 것을 "워커를 올리는 주체" 하나로 묶어 문제 원인을 가리기 쉽게 하려는 것이다. 안정된 뒤 tailnet 으로 직접 붙는 방식은 접속 주소 한 줄 수정이라 나중에 논의한다.
- Jenkins 의 `WORKER_REPLICAS=0` 만으로는 안 된다. FMS 단계의 기동 확인이 `total > 0` 을 요구해 워커 0개면 스테이지가 실패한다. k3s 전까지 임시로는 확인 루프를 고쳐야 한다.
- 도커용 방화벽 규칙(`DOCKER-USER`)은 k3s 에 적용되지 않는다. 공인 포트를 없애고 남는 것은 NetworkPolicy 로 막는다.
- 스윕 조기 종료(견적_스윕_얼리스탑_설계.md)를 구현할 때 배치 크기는 워커 2개가 아니라 12개 기준으로 잡아야 한다. 2로 두면 워커 10개가 논다.
- GCP 크레딧이 끝나 노드가 사라져도 EC2 워커로 기능은 유지된다. 속도만 돌아간다.
- 워커 메모리는 GCP 실측으로 3 GiB 로 올렸다(로봇 12·13대가 2 GiB 한도에 닿음, +70 MB/로봇). Deployment 의 메모리 상한도 3 GiB 이상으로 맞추고, 로봇 28대·주문 6,000 건은 그것도 넘을 수 있다.

## 5-1. tailnet 을 없앨 때 바꿀 것

tailnet 은 임시 구성이라 나중에 걷어낼 예정이다. 지금 k3s 설계는 EC2↔GCP 통신을 전부 tailnet 위에 두었으므로, 걷어내면 아래를 함께 바꾼다. GCP VM 은 외부 IP 가 없어 EC2→GCP 방향은 불가, GCP→EC2 방향만 공인 주소로 가능하다는 제약에 맞춘 것이다.

| 지금 | 바꿀 것 |
|---|---|
| 노드 합류 주소 `https://100.100.149.68:6443` | `https://j15a106.p.ssafy.io:6443`. ufw 로 GCP NAT IP(34.47.111.62)만 허용. k3s 는 노드→서버 연결 하나로 로그 조회 등을 역방향 터널로 처리해 EC2→GCP 가 막혀도 된다 |
| EC2 k3s 설치 옵션 `--node-ip/--advertise-address/--tls-san 100.100.149.68 --flannel-iface tailscale0` | `--tls-san j15a106.p.ssafy.io` 로 재설치(설치 스크립트 재실행, 만든 객체는 유지) |
| 파드 DNS 가 EC2 의 CoreDNS 경유 | EC2 로 못 가니 Deployment 에 `dnsPolicy: Default`(노드 DNS 사용) 추가 |
| 레지스트리 tailnet 주소 평문 + 노드 `registries.yaml` | nginx 443 뒤 `/v2/` 경로로 두고 nginx 에서 NAT IP 만 허용. 공인 CA 라 `registries.yaml` 불필요. Jenkinsfile 의 노드용 주소를 `j15a106.p.ssafy.io/fms-estimate-worker` 로 |
| Jenkins 접속 파일 서버 주소 100.100.149.68 | `127.0.0.1:6443`(Jenkins 가 EC2 안) |
| EC2↔GCP 파드 통신 | 없어진다. 워커는 브로커에 밖으로 붙기만 하므로 영향 없음 |

새로 열리는 공인 포트는 6443(k3s 자체 TLS)과 443 `/v2/` 두 개, 둘 다 출발지 제한. 5671 브로커와 같은 원칙이다. 담당자에게 준 `start.sh` 블록도 `k3s-url` 값이 바뀌고 `registries.yaml` 부분이 빠진다.

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 컨테이너 이미지 | 프로그램과 실행 환경을 한 파일로 구운 것. `docker build` 결과물 |
| **레지스트리** | 이미지를 올려 두는 창고. Docker Hub 가 공개 레지스트리다. 지금은 서버마다 따로 빌드해 쓰므로 창고가 없어도 됐지만, 여러 서버가 같은 이미지를 받아 가려면 한곳에 올려 두고(push) 받는(pull) 창고가 필요하다 |
| 노드 | 클러스터에 합류한 서버 한 대 |
| Pod | 컨테이너를 감싼 실행 단위. 보통 컨테이너 1개 = Pod 1개 |
| Deployment | "이 이미지로 Pod N개 유지" 규칙. 죽으면 채우고, 이미지가 바뀌면 하나씩 교체 |
| Service | Pod 들에 붙는 고정 이름·주소. compose 의 서비스 이름(`rabbitmq`, `pdf`)과 같은 역할 |
| Ingress | 바깥 요청을 어느 Service 로 보낼지 정하는 입구. 지금 nginx 설정이 하던 일 |
| Secret / ConfigMap | 비밀번호·설정을 담는 객체. 지금 `.env` 파일 |
| 매니페스트 | 위 객체들을 적은 YAML 파일. compose 파일에 해당 |
| kubectl | 쿠버네티스 명령줄 도구. `docker compose` 자리 |
| tailnet | 서버들을 잇는 사설망(Tailscale). 노드 합류와 브로커 접속이 이 위로 간다 |
