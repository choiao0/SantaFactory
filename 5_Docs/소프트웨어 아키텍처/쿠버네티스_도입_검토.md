# 쿠버네티스 도입

## 한 줄 결론

서버가 EC2 1대 + GPU 박스 1대 + GCP 워커 3대, 총 5대가 되었다. 각 서버를 compose 로 따로 관리하는 대신 **k3s(경량 쿠버네티스)로 하나로 묶고, 시뮬 워커부터 옮긴다.** DB·메시지 브로커·파일 저장소는 지금처럼 compose 로 둔다.

## 1. 지금 구조와 문제

| 서버 | 무엇이 도는가 | 어떻게 올리는가 |
|---|---|---|
| EC2 (t3.xlarge, 4코어 16 GB) | 백엔드·프런트·DB·RabbitMQ·Redis·MinIO·PDF 변환기, fms-core, EMQX, host-orch. 시뮬 워커 2개는 GCP 보다 느려 내림 | docker compose 4개. Jenkins 가 release 브랜치를 받아 순서대로 빌드·기동 |
| GCP 3대 (각 4코어) | 시뮬 워커 4개씩, 총 12개 | compose. 서버마다 접속해 손으로. 저장소에는 배포 파일이 없고 방화벽 README 에 접속 경로(AMQPS 5671)만 기록 |
| GPU 박스 | Isaac Sim 러너(물리 검증 영상) | compose. 사람이 접속해 손으로 |

시뮬 워커는 GCP 12개(2026-09-18 브로커 consumers=12 확인). RabbitMQ 가 큐에서 한 건씩 나눠 주므로 서버가 늘어도 워커 코드는 같다.

**문제.** compose 는 "서버 한 대 안"만 관리한다. 5대 중 Jenkins 가 배포하는 건 EC2 하나뿐이고, 나머지 4대는 코드가 바뀔 때마다 접속해 다시 올려야 한다. 한 곳을 빠뜨리면 옛 코드 워커가 새 코드 워커와 섞여 돌고, 결과가 조용히 어긋난다. 실제로 fms-core 가 Jenkins 에 안 들어가 있어 배포가 빠진 적이 있다(S15P21A106-234).
지금은 반대 방향의 어긋남도 있다. 실제 워커는 전부 GCP 에 있는데 Jenkins 는 여전히 EC2 워커 2개를 올리고 그 기동을 확인한다. release 를 돌리면 내려 둔 EC2 워커가 다시 뜬다.

## 2. 쿠버네티스가 하는 일

**여러 대의 서버를 한 덩어리로 묶어, 컨테이너를 규칙대로 배치하고 죽으면 되살리는 관리자.**
"시뮬 워커 12개는 GCP 서버에, GPU 러너는 GPU 있는 서버에" 라고 적어 두면 어느 서버에 올릴지·죽으면 어떻게 할지를 시스템이 정한다.

### 그림으로 보는 전후

**지금** — 서버 5대를 각자 따로 관리한다.

```
[GCP 1] docker  worker×4 ─┐
[GCP 2] docker  worker×4 ─┼─ 인터넷 TLS 5671 ─▶ [EC2] nginx ─▶ rabbitmq
[GCP 3] docker  worker×4 ─┘                            backend·db·redis·minio·pdf·fms-core·emqx
[GPU]   docker  러너 ─────── tailnet ────────────────▶      (compose 4개, Jenkins 는 여기만)
       ▲ 코드가 바뀌면 4대 각각 접속해서 git pull → build → up
```

**k3s 를 붙인 뒤(1단계)** — 5대가 클러스터 하나가 되고, 워커 배치는 관리자가 한다.

```
                    ┌──────────── k3s 클러스터 (tailnet 사설망) ────────────┐
                    │                                                        │
[EC2]  k3s 서버(관리자)                                                       │
       ├ compose 그대로: rabbitmq · db · redis · minio · emqx                │
       ├ compose 그대로(1단계): backend · pdf · fms-core · nginx              │
       └ 레지스트리(이미지 창고) ◀── Jenkins 가 빌드해서 push                 │
                    │                                                        │
[GCP 1] 노드 ─ worker worker worker worker ┐                                 │
[GCP 2] 노드 ─ worker worker worker worker ┼─ Deployment "sim-worker" 12개  │
[GCP 3] 노드 ─ worker worker worker worker ┘  배치 규칙: GCP 노드에만        │
                    │                                                        │
[GPU]   노드 ─ 러너  (2단계에서 합류)                                          │
                    └────────────────────────────────────────────────────────┘
```

| 흐름 | 지금 | k3s 뒤 |
|---|---|---|
| 워커 → 큐 연결 | 인터넷으로 nginx 5671(TLS)을 거침 | 사설망 안에서 `rabbitmq:5672` 이름으로 직접. 공인 포트·중계 없음 |
| 코드 배포 | 4대에 접속해 각자 빌드 | Jenkins 가 한 번 빌드 → 레지스트리 push → "새 이미지로" 한 줄. 관리자가 노드마다 갈아 끼움 |
| 워커 개수 | VM 마다 `WORKER_REPLICAS=4` | Deployment 에 12 하나. 노드 추가는 합류 한 줄 + 숫자 변경 |
| 서버가 죽으면 | 그 VM 의 워커 4개가 사라짐 | 남은 노드에 다시 띄워 12개 유지 |
| Jenkins 의 EC2 워커 | compose up 으로 내려 둔 워커가 다시 뜸 | "빌드 → push → 교체" 라 EC2 에 워커가 생기지 않음 |

3단계까지 가면 backend·pdf·fms-core 도 Deployment 로 들어가고 nginx 자리를 인그레스가 맡는다. DB·브로커·Redis·MinIO 는 끝까지 compose 로 EC2 에 남는다.

### compose 와 비교

| | compose (지금) | 쿠버네티스 |
|---|---|---|
| 범위 | 서버 1대 | 서버 여러 대를 하나로 |
| 서버 늘리기 | 서버마다 접속해 저장소·설정·`up -d` | 합류 명령 한 줄, 개수는 숫자 하나 |
| 코드 배포 | 서버마다 다시 빌드·재기동 (지금 5대 중 4대가 수동) | 한곳에서 이미지 갱신 → 전 서버 자동 교체 |
| 컨테이너가 죽으면 | 그 서버에서만 재시작 | 다른 서버로 옮겨서라도 개수 유지 |
| 배포 실패 | 새 버전이 안 뜨면 서비스가 내려간 채로 남음 | 새 버전이 정상 응답할 때까지 옛 버전 유지, 실패 시 자동 되돌림 |
| 설정·비밀번호 | `.env` 파일을 서버마다 복사 | 한곳(Secret)에 두고 필요한 컨테이너만 받음 |
| 배우는 비용 | 파일 1개, 개념 거의 없음 | 개념 6~7개(Pod·Deployment·Service·Ingress·Secret·Volume), 파일 4~5개 |
| 상시 자원 | 없음 | 관리자 자체가 메모리 0.7~1 GB, CPU 반 개 |
| 문제 추적 | `docker logs` | `kubectl` 로 여러 층(파드·서비스·인그레스) |

### 우리 서비스에서의 장단점

**장점**
- 워커 서버 3대(GCP)를 한곳에서 배포·증감한다. 지금은 손으로 맞추고, Jenkins 는 실제와 다른 EC2 워커를 올린다.
- 서버가 하나 빠지면 남은 서버로 워커 수를 유지한다. GCP 크레딧이 끝나 노드가 사라져도 규칙만 남아 있으면 EC2 에서 가능한 만큼 돈다.
- GPU 박스 러너도 같은 방식으로 배포·복구된다.
- 서버 간 통신이 사설망 안에서 이뤄져 공인 포트를 열 필요가 줄어든다(지금은 도커가 방화벽을 우회해 열려 따로 막았다, S15P21A106-245).

**단점**
- 배울 게 많고 파일이 늘어난다. 전환에 약 1주.
- EC2 한 대에만 있는 DB·브로커는 옮겨도 이득이 없다. 서버가 하나라 "다른 서버로 살리기"가 불가능하고 데이터 이전 위험만 생긴다.
- 이미지 레지스트리가 새로 필요하다(6. 용어).
- 속도 자체는 이미 워커 12개로 얻었다. 쿠버가 더해 주는 것은 속도가 아니라 **관리**다.

## 3. k8s 와 k3s

같은 쿠버네티스다. 명령·설정 파일·개념 전부 같다. 차이는 포장.

| | k8s (정식판, 또는 AWS EKS) | k3s (경량판) |
|---|---|---|
| 설치 | 구성 요소를 따로 설치·연결. 관리 서버 3대 권장 | 프로그램 하나, 명령 한 줄. 서버 1대로 시작 |
| 관리자 메모리 | 약 2 GB | 약 0.7 GB |
| 딸려 오는 것 | 저장소·로드밸런서·인그레스 따로 설치 | 내장 |
| 비용 | EKS 는 관리 서버만 월 약 70달러 | 무료 |
| 규모 | 수십 대 이상 | 서버 1~5대 |

**k3s 를 고르는 이유.** 서버 5대 규모에 맞고, 무료이며, 메모리를 1/3 만 쓴다. 팀 문서가 이미 k3s 를 전제로 하고 러너용 매니페스트(`2_Simulation/t3_amr/deploy/k8s/`)가 저장소에 있다. 배운 내용은 k8s 와 같아 나중에 큰 환경으로 가도 그대로 쓴다.

## 4. 진행 순서

| 단계 | 내용 | 얻는 것 | 공수 |
|---|---|---|---|
| 0 | **이미지 레지스트리** 준비(GitLab 컨테이너 레지스트리, 안 되면 EC2 에 `registry` 컨테이너) | 다른 서버가 이미지를 받아 갈 수 있음. 지금 GCP 3대는 각자 빌드하고 있어 이것부터 필요 | 반나절 |
| 1 | EC2 에 k3s 서버 설치. GCP 3대를 노드로 합류(tailnet). 시뮬 워커를 Deployment 로 옮기고 개수 12, 배치는 GCP 노드로 한정. Jenkins FMS 단계를 "빌드 → 푸시 → 교체" 로 | 워커 3대 한곳 배포, 서버 빠져도 개수 유지, Jenkins 가 실제 배치와 일치 | 2일 |
| 2 | GPU 박스를 노드로 합류. NVIDIA 플러그인, 기존 러너 매니페스트 적용 | 러너 자동 배치·복구 | 1~2일 |
| 3 | 백엔드·프런트·PDF 변환기·fms-core·host-orch 이전. nginx → 인그레스 | 안전한 배포, 설정 한곳 | 3~4일 |
| 하지 않음 | Postgres·RabbitMQ·Redis·MinIO·EMQX | 얻는 것 없음, 데이터 이전 위험만 | — |

워커를 먼저 하는 이유: 이미 4대에 흩어져 있어 관리 부담이 가장 큰 곳이고, 특수 설정이 없어 가장 쉽고, 노드가 늘어도 코드 변경이 없다.

## 5. 주의할 것

- RabbitMQ 는 EC2 의 `127.0.0.1` 과 tailnet 에만 열려 있고, GCP 워커는 방화벽 README 기준 AMQPS 5671(nginx stream) 경로로 붙는다. k3s 안에서는 서비스 이름 `rabbitmq` 로 닿게 하면 이 경로가 필요 없어진다.
- 도커용 방화벽 규칙(`DOCKER-USER`)은 k3s 에 적용되지 않는다. 공인 포트를 없애고 남는 것은 NetworkPolicy 로 막는다.
- 스윕 조기 종료(견적_스윕_얼리스탑_설계.md)를 구현할 때 배치 크기는 워커 2개가 아니라 12개 기준으로 잡아야 한다. 2로 두면 워커 10개가 논다.
- GCP 크레딧이 끝나 노드가 사라져도 EC2 워커로 기능은 유지된다. 속도만 돌아간다.

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 컨테이너 이미지 | 프로그램과 실행 환경을 한 파일로 구운 것. `docker build` 결과물 |
| **레지스트리** | 이미지를 올려 두는 창고. Docker Hub 가 공개 레지스트리다. 지금은 서버마다 따로 빌드해 쓰므로 창고가 없어도 됐지만, 여러 서버가 같은 이미지를 받아 가려면 한곳에 올려 두고(push) 받는(pull) 창고가 필요하다 |
| 노드 | 클러스터에 합류한 서버 한 대 |
| Pod | 컨테이너를 감싼 실행 단위. 보통 컨테이너 1개 = Pod 1개 |
| Deployment | "이 이미지로 Pod N개 유지" 규칙. 죽으면 채우고, 이미지가 바뀌면 하나씩 교체 |
| Service | Pod 들에 붙는 고정 이름·주소. compose 의 서비스 이름(`rabbitmq`, `pdf`)과 같은 역할 |
| Ingress | 바깥 요청을 어느 Service 로 보낼지 정하는 입구. 지금 nginx 설정이 하던 일 |
| Secret / ConfigMap | 비밀번호·설정을 담는 객체. 지금 `.env` 파일 |
| 매니페스트 | 위 객체들을 적은 YAML 파일. compose 파일에 해당 |
| kubectl | 쿠버네티스 명령줄 도구. `docker compose` 자리 |
| tailnet | 서버들을 잇는 사설망(Tailscale). 노드 합류와 브로커 접속이 이 위로 간다 |
