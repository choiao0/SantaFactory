# 견적 대수 스윕 — 워커 병렬화 + 얼리스탑 (설계 검토, 미구현)

## 지금 상태

`EstimateService.create()`가 대수 범위(예: 1~28대) 전체를 `sim.request`에 한 번에 다 발행한다. 워커(`estimate-worker`)는 몇 대로 스케일하든 경쟁 소비(work queue)로 나눠 받는다 — 대수 하나가 곧 run 하나, 순서 무관하게 결과가 오는 대로 `applyResult()`가 반영한다.

## 하고 싶은 것

워커를 2대로 병렬 처리하면서, 목표를 만족하는 **최소 대수**를 찾으면 그 이상은 계산하지 않고 멈추기(얼리스탑). 지금처럼 전부 한 번에 큐에 던지면, 이미 큐에 들어간 뒤로는 워커가 계속 집어가서 계산해버려 "그만 돌려"가 안 먹는다 — 그래서 **워커 수만큼(2개)씩 배치로 발행하고, 배치 결과를 보고 다음 배치를 보낼지 판단**하는 방식이 필요하다.

## 짚어야 할 것 두 가지

### 1. 순서 보장 — 배치는 반드시 오름차순, 배치 안에서는 다 기다렸다가 판단

"최소 대수"를 찾는 거라, 배치 [5,6]을 동시에 보냈을 때 6번이 먼저 끝나서 만족한다고 바로 확정하면 안 된다 — 5번이 아직 안 왔으면 5번도 만족할 가능성이 있고, 그럼 진짜 답은 5다. **배치 안의 모든 결과가 도착한 뒤에만** "이 배치에서 만족하는 것 중 최소"를 판정해야 한다.

### 2. 무릎(knee) 판정 및 차트와의 충돌

QuoteStep이 그리는 처리율·비용 곡선은 최소 대수 이후로도 몇 대 더 돌린 데이터가 있어야 "더 늘려도 처리율이 안 오르는 지점(무릎)"을 보여줄 수 있다. **답을 찾자마자 완전히 멈추면 그 뒤 곡선이 없어져서 지금 화면 기능이 깨진다.** 최소 대수를 찾은 뒤에도 무릎 판정에 필요한 만큼(예: 배치 1~2개, 숫자는 미정) 더 돌리고 나서 멈추는 절충이 필요하다.

## 미결 (다음에 정할 것)

- 배치 크기 — 워커 수(2)로 고정할지, 별도 설정값으로 뺄지
- "답 찾은 뒤 몇 배치 더 돌릴지"의 정확한 기준 (배치 개수? 처리율 변화율 임계값?)
- 워커 수(2)를 배포 설정에서 어떻게 관리할지 — 백엔드가 워커 수를 알아야 배치 크기를 정할 수 있는데, 지금은 백엔드와 워커가 그런 정보를 공유하지 않음
