# 리플레이 조회 최적화 기록 (S15P21A106-255)

2026-09-22. 브랜치 `feature/S15P21A106-255-이산-시뮬-리플레이-조회-최적화`. 데이터 형식은 [시뮬엔진연동API명세서.md](시뮬엔진연동API명세서.md) §1-2 "리플레이".

견적 화면에서 run 카드를 누르면 그 대수의 주행을 재생한다. 이 리플레이가 뜨기까지 걸리는 시간을 4단계로 줄인 기록이다.

## 0. 결과 요약

측정 대상: **28대 = 최대 대수**, **11대 = 중간 규모 예시**(처음 측정할 때 로컬 DB 에 있던 데이터를 그대로 썼다. 1~28 의 중간값 14 가 아니다). 시간은 3~5회 중앙값. 같은 PC 에서 잰 값은 20~30 % 흔들리므로 **크기는 확정치, 시간은 배수로** 읽는다.

## 1. 문제와 원인

**증상**
- run 완료 직후 "주행 데이터를 불러오는 중…" 에 오래 머문다. 대수가 많을수록 길다.
- run 이 하나 끝날 때마다 더 느려진다.

**원인이 아니었던 것**
- 영상 저장소(MinIO): 리플레이는 거치지 않는다.
- 화면 그리기: 파싱 85 ms, 변환 41 ms, 캔버스는 배경 1회 + 프레임마다 로봇만.

**데이터 경로**

```
시뮬 워커 ─(결과 메시지에 실어)─▶ RabbitMQ ─▶ 백엔드 ─(DB 저장)─▶ Postgres
브라우저 ◀─(JSON 응답)─ 백엔드 ◀─(문자열 읽어 응답)─────────────────┘
```

**원인 4가지**

| # | 원인 | 근거 |
|---|---|---|
| 1 | 로봇 1대당 약 765 KB, 대수에 비례하는 JSON 을 **압축 없이** 전송 | 6대 4.7 / 11대 8.6 / 28대 21.5 MB. `Accept-Encoding: gzip` 을 보내도 그대로 |
| 2 | 방향(헤딩) 기록이 매 샘플 저장돼 **95 % 가 직전 값 반복** | 28대 로봇 0: 19,441개 중 값이 바뀐 것 1,036개. 헤딩이 전체의 45 % |
| 3 | run 목록 조회가 엔티티 전체를 읽어 **리플레이 컬럼까지 함께** 가져옴 | 상세 조회·SSE 스냅샷·결과 도착 시 완료 판정에서 호출마다 수십 MB. 응답은 1~3 KB |
| 4 | 리플레이 API 가 12~21 MB 문자열을 **JSON 트리로 파싱한 뒤 다시 직렬화** | 28대 첫 바이트 0.39 s, 메모리 부족 시 1.5 s |

**완료될 때마다 느려지는 이유** — 견적 진행 중엔 권장 대수가 없어 리플레이 영역이 "완료된 것 중 마지막 대수" 를 자동 선택한다. run 이 끝날 때마다 더 큰 파일을 새로 받는다.

## 2. 측정 방법

**준비**: 로컬 백엔드(`./gradlew bootRun`) + Docker Postgres·RabbitMQ·워커. 28대 run 만 돌리려면 견적 요청에 `"fleet_min":28,"fleet_max":28` (약 2분).

| 무엇을 | 어떻게 |
|---|---|
| 로그인 쿠키 | `curl -s -c cj -H "Content-Type: application/json" -d '{"email":"…","password":"…"}' …/api/auth/login` |
| 크기·시간 | `curl -s -b cj -o /dev/null -w "bytes=%{size_download} ttfb=%{time_starttransfer} total=%{time_total}\n" …/api/estimates/{id}/runs/{n}/replay` |
| 압축 여부 | 위 명령에 `-H "Accept-Encoding: gzip" -D -` 를 붙여 `Content-Encoding: gzip` 확인 |
| 회선 재현 | `--limit-rate 2500k`(≈20 Mbps), `6M`(≈50 Mbps). 같은 PC 에선 전송 시간이 0 에 가까워 이게 없으면 압축 효과가 보이지 않는다 |
| 브라우저 | 개발자도구 Network 탭 replay 요청의 Size(전송/원본)·Time. Throttling 으로 회선 재현 가능 |

- `ttfb` = 첫 바이트까지 ≈ 백엔드 처리 시간, `total` = 전체.
- 값이 흔들리므로 3회 이상 재고 중앙값. 단계 간 비교는 같은 날 같은 상태의 값끼리.
- 이 문서의 값은 개발 PC 에서 백엔드·Postgres·RabbitMQ·워커 2개를 함께 띄운 상태에서 잰 것이다.

## 3. 단계별 기록

### 3-1. 응답 압축 — `b857128`

| | |
|---|---|
| 변경 | `application.yml` `server.compression.enabled: true` 세 줄. 압축 대상은 Spring 기본 목록 그대로 |
| 왜 백엔드에서 | 로컬(Vite 프록시)·배포(nginx 뒤) 모두 설정 하나로 동작. 서버 nginx 는 서버에서 직접 관리하는 파일이라 저장소로 배포되지 않음 |
| SSE 영향 | 없음. 기본 목록에 `text/event-stream` 이 없어 압축되지 않는다. 압축하면 버퍼가 생겨 이벤트가 늦어질 수 있어 그대로 둔다 |
| 프론트 | 변경 없음. 브라우저가 `Accept-Encoding` 을 붙이고 자동으로 푼다 |

| 28대 | 적용 전 | 적용 후 |
|---|---|---|
| 응답 크기 | 21.5 MB | 3.49 MB (16 %) |
| 같은 PC 전체 시간 | 3.1 s | 4.2 s (압축 CPU 약 1 s 만 보임) |
| 50 Mbps 재현 | 5.0 s | 4.5 s (편차 큼) |
| 20 Mbps 재현 | 9.7 s | 1.9 s |

- 회선이 느릴수록 이득이 크고, 같은 PC 에선 CPU 비용만 보여 오히려 늘어난다. 압축만으로 끝내지 않고 데이터를 줄이는 2단계가 필요했던 이유.
- 확인: gzip 헤더 응답, SSE 는 `Content-Encoding` 없음, Vite 프록시 통과, 컨트롤러 테스트 10건.
- 배포 서버 실측(브라우저, 28대, 같은 견적 조건): 적용 전 21,558 kB / 6.49 s → 4단계 적용 후 1,540 kB / 0.33 s. 배포 서버 run 의 크기는 로컬 run(2.04 MB)과 다른데, 주문·주행이 달라 궤적 길이가 다르기 때문이다.

### 3-2. 헤딩 중복 제거 — `8b39d92`

| | |
|---|---|
| 변경 | 워커 `_read_replay` 가 헤딩을 4틱마다 솎던 것을, 솎기 전 원본에서 **값이 바뀐 시점만** 담도록(`_changes`). 첫 기록은 항상 남김 |
| 호환 | 프론트 `buildModel` 은 헤딩을 "그 시각 이하의 마지막 기록" 으로 읽어 다음 기록까지 유지 → 그림 동일. 백엔드·큐 형식 변경 없음. 옛 데이터도 재생됨 |
| 추가로 좋아진 것 | 4틱 사이의 회전이 늦게 기록되거나 빠지던 것이 틱 단위로 정확해짐 |

후: [0.0, 1.5708], [1.111, 3.1416], [6.667, -1.5708]

### 3-4. 파싱·재직렬화 생략 — `f6debdc`

| | |
|---|---|
| 변경 | 궤적 문자열의 마지막 `}` 앞에 `,"scene":` + 맵 문자열을 이어 붙여 그대로 응답. 컨트롤러는 Jackson `RawValue` 로 감싸 `result` 자리에 원문으로 넣음(일반 String 이면 따옴표로 감싸져 나감) |
| 왜 원래 파싱했나 | Spring 에서 JSON 두 개를 합치는 표준 방식. 리플레이 도입 당시 4대 0.67 MB 라 비용이 보이지 않았다 |
| 잃는 것 → 대신 | 파싱 검증 → 두 문자열이 `{…}` 모양인지 검사, 아니면 404. 저장 시점에 이미 파싱을 거치므로 깨진 데이터 경로는 없음 |

```
{"dt_s":1.11,"robots":{…},"headings":{…}}  +  {"grid":[…],"stations":{…}}
→ {"dt_s":1.11,"robots":{…},"headings":{…},"scene":{"grid":[…],"stations":{…}}}
```

| 28대 | 적용 전 | 적용 후 |
|---|---|---|
| 첫 바이트 | 0.37~0.41 s | 0.26 s |
| 전체 (압축 없이) | 0.61 s | 0.49 s |
| 응답 크기 | 12.49 MB | 12.49 MB (동일) |

- 남은 0.26 s 는 DB 에서 12 MB 를 읽어 응답으로 복사하는 시간. 메모리가 부족할 때 1.5 s 였던 것은 파싱이 만드는 수백만 개 객체 때문이라 서버가 바쁠수록 차이가 커진다.
- 확인: 변경 전 저장해 둔 11대 응답과 파싱 후 깊은 비교로 내용 동일, 단위 테스트 2건 추가.
