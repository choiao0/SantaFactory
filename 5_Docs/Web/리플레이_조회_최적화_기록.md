# 리플레이 조회 최적화 기록 (S15P21A106-255)

2026-09-22. 브랜치 `feature/S15P21A106-255-이산-시뮬-리플레이-조회-최적화`. 리플레이 데이터 형식은 [시뮬엔진연동API명세서.md](시뮬엔진연동API명세서.md) §1-2 "리플레이" 참고.

견적 화면에서 run 카드를 누르면 그 대수의 주행을 재생하는 리플레이가 뜬다. 이 리플레이가 뜨기까지 걸리는 시간을 줄인 과정을 단계별로 기록한다. 각 단계는 **변경 내용 → 적용 전·후 수치 → 확인한 것** 순서로 적는다.

## 0. 요약 표

측정 대상은 로컬 DB 의 두 run 이다. 11대(견적 3, 6시간)와 최대 대수인 28대(견적 4, 6시간). 모든 단계를 같은 데이터로 다시 측정한다. 시간은 20 Mbps 회선을 재현한 값(측정 방법 §3)이며 3회 중앙값이다.

| 단계 | 변경 내용 | 응답 크기 11대 / 28대 | 응답 시간 11대 / 28대 (20 Mbps) | 커밋 |
|---|---|---|---|---|
| 시작점 | — | 8.6 MB / 21.5 MB | 3.3 s / 9.7 s | — |
| 1. 응답 압축 | 백엔드 gzip 설정 추가 | 1.44 MB / 3.49 MB | 0.7 s / 1.9 s (같은 날 재측정 1.8 s) | `b857128` |
| 2. 헤딩 중복 제거 | 워커가 방향이 바뀐 시점만 남김 | (28대만 측정) / 2.04 MB | (28대만 측정) / 0.95 s | `8b39d92` |
| 3. run 목록 조회에서 리플레이 분리 | 궤적을 별도 테이블로(V9) | 변화 없음 | 변화 없음. 상세 조회 0.46 → 0.012 s, SSE 스냅샷 0.50 → 0.018 s | `7eeda0f` |
| 4. 백엔드 파싱·재직렬화 생략 | 저장된 문자열을 이어 붙여 그대로 내보냄 | 변화 없음 | 첫 바이트 28대 0.39 → 0.26 s | `f6debdc` |

배포 서버 실측(28대, 브라우저 개발자도구): 적용 전 **21.5 MB / 6.49 s**. 적용 후는 배포 뒤 같은 방법으로 기입한다(4-1 참고).

## 1. 문제

- run 이 완료된 직후 리플레이 영역이 "주행 데이터를 불러오는 중…" 에서 오래 머문다.
- 대수가 많은 run 일수록 더 오래 걸린다. run 이 하나씩 끝날 때마다 체감 지연이 늘어난다.
- 처음에는 영상 저장소(MinIO)에서 가져오는 과정이나 화면 그리기(렌더링)를 의심했지만, 둘 다 원인이 아니었다. 리플레이는 MinIO 를 거치지 않고, 그리는 데는 100 ms 도 걸리지 않는다.

## 2. 시간이 걸리는 구간

리플레이 데이터가 화면까지 오는 길은 아래와 같다.

```
시뮬 워커 ──(결과 메시지에 실어)──▶ RabbitMQ ──▶ 백엔드 ──(DB TEXT 컬럼에 저장)──▶ Postgres
                                                                                  │
브라우저 ◀──(JSON 응답)── 백엔드 ◀──(문자열 읽어 파싱·재직렬화)────────────────────────┘
```

크기가 문제다. 로봇 1대당 약 765 KB 이고 대수에 정비례한다.

| 대수 | 응답 크기 |
|---|---|
| 6대 | 4.7 MB |
| 8대 | 6.3 MB |
| 11대 | 8.6 MB |
| 28대(최대) | 21.5 MB |

내용을 보면 로봇마다 1.1초 간격 위치 샘플이 19,441개 들어 있고(6시간분), 여기에 같은 개수의 방향(헤딩) 기록이 붙는다. 11대 기준 위치가 2.8 MB, 방향이 2.3 MB 다. 방향 기록은 대부분 직전 값과 같은 숫자의 반복이라(로봇 0 기준 19,441개 중 실제로 값이 바뀐 것은 962개) 2단계에서 정리할 대상이다.

구간별 소요는 다음과 같다. 같은 PC 안에서 잰 값이라 전송 시간은 거의 들어 있지 않다.

| 구간 | 11대 | 28대 | 판단 |
|---|---|---|---|
| 백엔드: DB 읽기 + JSON 파싱 + 재직렬화 | 약 0.4 s | 약 1.5 s(첫 바이트까지) + 이후 직렬화 포함 약 3 s | 대수가 많으면 무시할 수 없다 |
| 전송: 압축 없이 그대로 | 20 Mbps 에서 약 3 s | 20 Mbps 에서 약 8 s | **주원인** |
| 브라우저: JSON 파싱 | 85 ms | (미측정) | 무관 |
| 브라우저: 재생용 데이터 변환 | 41 ms | (미측정) | 무관 |
| 브라우저: 캔버스 그리기 | 배경은 한 번, 프레임마다 로봇만 | | 무관 |

**완료될 때마다 더 느려지는 이유.** 견적이 진행 중일 때는 권장 대수가 아직 없어서 리플레이 영역이 "완료된 것 중 마지막 대수" 를 자동으로 고른다. run 이 하나 끝날 때마다 그 대수의 리플레이를 새로 내려받는데, 대수가 클수록 파일도 커서 매번 더 오래 걸린다.

**함께 발견한 것.** 백엔드가 run 목록을 읽을 때 엔티티 전체를 가져오므로 리플레이 컬럼도 함께 읽는다. 이 조회는 SSE 접속, 상세 조회, 결과 도착 시 완료 판정에서 쓰이므로 화면에는 KPI 몇 개만 나가는데도 호출마다 수십 MB 를 DB 에서 읽는다. 3단계의 대상이다.

## 3. 측정 방법

누구나 같은 방식으로 다시 측정할 수 있게 적어 둔다.

**준비.** 로컬 백엔드(`./gradlew bootRun`)와 Docker 의 Postgres 가 떠 있고, 리플레이가 저장된 견적이 있으면 된다. 28대 run 은 견적 요청에 `fleet_min`·`fleet_max` 를 28 로 주면 그 대수 하나만 돈다(약 2분).

```bash
curl -s -b cj -H "Content-Type: application/json" \
  -d '{"warehouse_id":4,"fleet_min":28,"fleet_max":28}' http://127.0.0.1:8080/api/estimates
```

**로그인 쿠키 받기.**

```bash
curl -s -c cj -H "Content-Type: application/json" \
  -d '{"email":"<관리자 이메일>","password":"<비밀번호>"}' http://127.0.0.1:8080/api/auth/login
```

**응답 크기와 시간 재기.** `size_download` 가 실제로 내려온 바이트 수, `time_starttransfer` 가 첫 바이트까지(백엔드 처리 시간에 가깝다), `time_total` 이 전체 시간이다. 값이 흔들리므로 3회 이상 재고 중앙값을 쓴다.

```bash
curl -s -b cj -o /dev/null \
  -w "bytes=%{size_download} ttfb=%{time_starttransfer}s total=%{time_total}s\n" \
  http://127.0.0.1:8080/api/estimates/4/runs/28/replay
```

**압축 여부 확인.** 브라우저처럼 압축을 받겠다고 알리고(`Accept-Encoding: gzip`) 응답 헤더에 `Content-Encoding: gzip` 이 있는지 본다.

```bash
curl -s -b cj -H "Accept-Encoding: gzip" -D - -o /dev/null \
  -w "bytes=%{size_download}\n" http://127.0.0.1:8080/api/estimates/4/runs/28/replay | grep -i "content-encoding\|bytes="
```

**회선 속도 재현.** 같은 PC 안에서는 전송이 거의 0 초라 압축 효과가 보이지 않는다. curl 의 수신 속도 제한으로 회선을 흉내 낸다. `--limit-rate 2500k` 가 약 20 Mbps, `6M` 이 약 50 Mbps 다.

```bash
curl -s -b cj --limit-rate 2500k -H "Accept-Encoding: gzip" -o /dev/null \
  -w "total=%{time_total}s\n" http://127.0.0.1:8080/api/estimates/4/runs/28/replay
```

**브라우저에서.** 개발자도구 Network 탭에서 `replay` 요청을 고르면 Size 열에 전송된 크기와 원본 크기가 함께 나온다. 압축이 되면 전송 크기가 원본보다 작다. Network 탭의 속도 제한(Throttling)으로도 회선을 재현할 수 있다.

**측정 환경 주의.** 이 기록의 값은 개발 PC 에서 백엔드·Postgres·RabbitMQ·시뮬 워커 2개를 함께 띄운 상태로 잰 것이다. 메모리가 부족한 상태여서 같은 요청도 편차가 컸다. 단계 간 비교는 같은 날 같은 상태에서 잰 값끼리만 한다.

## 4. 단계별 기록

### 4-1. 응답 압축

**변경 내용.** 백엔드 설정 파일 `application.yml` 의 `server` 항목에 세 줄을 추가했다.

```yaml
server:
  compression:
    enabled: true
```

gzip 은 텍스트를 압축해서 보내고 브라우저가 받는 쪽에서 자동으로 푸는 방식이다. JSON 처럼 같은 글자와 숫자가 반복되는 데이터에 효과가 크다. 브라우저는 요청할 때 "압축해서 보내도 된다" 는 헤더(`Accept-Encoding`)를 항상 붙이므로 프론트 코드는 바꿀 것이 없다.

**왜 백엔드에서.** 로컬 개발(Vite 프록시)과 배포 서버(nginx 뒤) 어디서나 같은 설정 하나로 동작한다. 배포 서버의 nginx 설정은 서버에서 직접 관리하는 파일이라 저장소를 바꿔도 배포되지 않는다.

**SSE 는 압축하지 않는다.** 진행 상황을 실시간으로 밀어주는 SSE(`text/event-stream`)를 압축하면 중간에 버퍼가 생겨 이벤트가 늦게 도착할 수 있다. Spring Boot 의 압축 대상 기본 목록에는 JSON 은 있고 `text/event-stream` 은 없으므로, 목록을 따로 지정하지 않고 기본값을 그대로 쓴다.

**적용 전·후 — 크기.**

| 대수 | 적용 전 | 적용 후 | 비율 |
|---|---|---|---|
| 6대 | 4.7 MB | 0.82 MB | 17 % |
| 11대 | 8.6 MB (8,582,023 B) | 1.44 MB (1,443,609 B) | 17 % |
| 28대 | 21.5 MB (21,525,651 B) | 3.49 MB (3,486,172 B) | 16 % |

**적용 전·후 — 시간 (3회 중앙값).**

| 조건 | 11대 전 → 후 | 28대 전 → 후 |
|---|---|---|
| 같은 PC (전송 시간 없음) | 1.3 s → 1.8 s | 3.1 s → 4.2 s |
| 50 Mbps 재현 | 1.4 s → 0.6 s | 5.0 s → 4.5 s |
| 20 Mbps 재현 | 3.3 s → 0.7 s | 9.7 s → 1.9 s |

읽는 법. 같은 PC 안에서는 압축에 드는 CPU 시간(11대 약 0.5 s, 28대 약 1 s)만 보여서 오히려 늘어난다. 회선이 느릴수록 줄어든 전송량이 그 비용을 넘어서고, 20 Mbps 에서는 28대가 9.7 s 에서 1.9 s 로 줄었다. 50 Mbps 의 28대 값(4.5 s)은 편차가 커서 참고만 한다. 사용자 회선이 빠르고 서버 CPU 가 바쁠 때는 이득이 작아지므로, 압축은 데이터 자체를 줄이는 2단계와 함께 가야 한다.

**배포 서버 실측 (28대, 브라우저 개발자도구 Network 탭, 2026-09-22).**

| | Size(전송) | Time | 비고 |
|---|---|---|---|
| 적용 전 | 21,558 kB | 6.49 s | 전송 크기와 원본 크기가 같다 = 압축 없음. 21.5 MB ÷ 6.49 s ≈ 27 Mbps 회선 |
| 적용 후 | (배포 뒤 기입) | (배포 뒤 기입) | 같은 견적·같은 대수·같은 자리에서 다시 캡처 |

curl 재현값과 맞춰 보면 20 Mbps(9.7 s)와 50 Mbps(5.0 s) 사이에 들어온다. 같은 화면에서 첫 replay 요청이 401 로 실패하고 refresh 뒤 다시 성공한 것은 15분짜리 접속 토큰이 만료돼 갱신한 정상 동작이다. 적용 후 캡처에서는 Size 칸에 마우스를 올려 "전송 크기 / 원본 크기" 두 값을 함께 적는다.

**28대에서 새로 보인 것.** 압축과 무관하게 첫 바이트까지 약 1.5 s 가 걸린다. 백엔드가 21 MB 문자열을 JSON 트리로 파싱한 뒤 다시 문자열로 만드는 시간이다. 저장된 문자열을 그대로 내보내면 이 시간을 없앨 수 있다. 4단계 후보로 적어 둔다.

**확인한 것.**
- `Accept-Encoding: gzip` 을 붙인 요청에 `Content-Encoding: gzip` 응답 헤더가 온다. 붙이지 않으면 예전처럼 원본 그대로 온다.
- SSE 응답(`GET /api/estimates/{id}`, `Accept: text/event-stream`)에는 `Content-Encoding` 이 없고 첫 이벤트가 바로 온다.
- Vite 개발 프록시(5173)를 거쳐도 `Content-Encoding: gzip` 이 유지된다.
- 응답 헤더에 `Vary: accept-encoding` 이 붙는다. 프록시가 압축본과 원본을 섞어 캐시하지 않게 하는 표준 헤더로, Spring Boot 가 자동으로 넣는다.
- 컨트롤러 테스트(SSE 헤더 검증 포함) 10건 통과.

### 4-2. 헤딩 중복 제거

**변경 내용.** 워커(`3_FMS/infra/worker/estimate_worker.py` `_read_replay`)가 방향(헤딩) 기록을 위치와 같이 4틱마다 솎아 담던 것을, 솎기 전 원본에서 **값이 바뀐 시점만** 골라 담도록 바꿨다(`_changes`). 첫 기록은 항상 남기고, 그 뒤로는 직전에 남긴 값과 다를 때만 남긴다.

헤딩은 로봇이 바라보는 방향(라디안)이다. 시뮬은 이 값을 틱마다 기록하지만 로봇은 통로를 직진하는 시간이 대부분이라 같은 숫자가 계속 반복된다. 28대 run 의 로봇 0 을 세어 보면 19,441개 기록 중 값이 바뀐 것은 1,036개다.

```
변경 전: [0.0, 1.5708], [1.111, 3.1416], [2.222, 3.1416], [3.333, 3.1416], [4.444, 3.1416], [5.556, 3.1416], [6.667, -1.5708]
변경 후: [0.0, 1.5708], [1.111, 3.1416], [6.667, -1.5708]
```

**프론트·백엔드는 바꾸지 않았다.** 화면(`replay/model.js` `buildModel`)은 헤딩을 "그 시각 이하의 마지막 기록" 으로 읽고 다음 기록 전까지 그 방향을 유지한다. 반복 값이 있어도 없어도 같은 그림이 나온다. 백엔드는 JSON 을 저장·전달만 하고 헤딩 내부를 해석하지 않는다. 옛 워커가 만든 리플레이도 그대로 재생된다.

**덧붙여 정확해진 것.** 예전에는 4틱마다 하나만 남겨 그 사이의 회전이 최대 1초 늦게 기록되거나, 연속 두 번 회전 중 하나가 빠졌다. 지금은 원본에서 뽑으므로 회전 시각이 틱 단위로 정확하다.

**적용 전·후 (28대 run, 로컬. 같은 창고·같은 주문으로 새로 돌린 견적 6 과 견적 4 비교).**

| | 헤딩 기록 수(로봇 0) | 헤딩 배열 | 위치 배열 | DB 저장 크기 | 응답 크기(압축 없이) | 응답 크기(gzip) |
|---|---|---|---|---|---|---|
| 적용 전 | 19,441 | 10.6 MB | 13.4 MB | 21.4 MB | 21.5 MB | 3.49 MB |
| 적용 후 | 1,036 | 0.58 MB | 13.4 MB | 12.3 MB | 12.5 MB | 2.04 MB |

| 시간 (3회 중앙값, 같은 시점에 두 견적을 번갈아 측정) | 적용 전 | 적용 후 |
|---|---|---|
| 20 Mbps 재현, 압축 없이 | 8.6 s | 4.4 s |
| 20 Mbps 재현, gzip | 1.8 s | 0.95 s |

DB 저장량과 큐 메시지 크기가 함께 42 % 줄었다. 압축과 합치면 28대가 21.5 MB → 2.04 MB(약 10분의 1)다. 남은 것은 위치 배열 13.4 MB 이고, 이는 샘플 간격이나 좌표 자릿수를 조정해야 줄어든다.

**확인한 것.**
- 워커 테스트: 내내 같은 방향이면 첫 기록 하나만 남는다. 4틱 솎기 사이(틱 5·6)의 연속 회전이 정확한 시각(2.5 s, 3.0 s)으로 남고 같은 값 반복(틱 12)은 빠진다. 위치 배열은 여전히 4틱 간격이다.
- 새 워커로 돌린 28대 run 이 정상 완료(89.8 s)됐고 위치 샘플 수는 19,441개로 변경 전과 같다.
- 프론트에서 헤딩을 읽는 곳은 `model.js` 한 곳뿐이고 이벤트 목록 방식이라 변경 없이 호환된다.

### 4-3. run 목록 조회에서 리플레이 분리

**변경 내용.** 리플레이 궤적을 `simscenarios.replay_json` 컬럼에서 떼어 새 테이블 `simscenario_replays`(scenario_id, replay_json)로 옮겼다(마이그레이션 V9, 기존 데이터는 복사 후 컬럼 삭제). 백엔드는 새 엔티티 `RunReplay` 와 리포지토리로 리플레이 API 에서만 id 로 직접 읽고, 결과가 도착하면 그 테이블에 한 행을 넣는다. run 엔티티(`SimScenario`)에는 리플레이 관련 필드가 없다.

**왜.** JPA 는 엔티티를 읽을 때 모든 컬럼을 함께 가져온다. run 목록을 읽는 조회(상세 조회, SSE 접속 스냅샷, 결과 도착 시 완료 판정, 발행 실패 처리)는 KPI 몇 개만 쓰는데도 run 마다 수 MB 짜리 리플레이 문자열을 DB 에서 옮겨 왔다. 28대 run 하나가 12 MB 이므로 1~28대가 다 끝난 견적은 조회 한 번에 약 180 MB 를 읽는다. 결과가 도착할 때마다 이 조회가 돌기 때문에, run 이 끝날수록 결과 반영이 느려지는 구조였다. 컬럼 하나만 지연 로딩하는 방법은 JPA 에서 바이트코드 처리 없이는 동작하지 않아, 테이블을 나누는 쪽을 택했다.

**적용 전·후 (로컬, 상세 조회 `GET /api/estimates/{id}` JSON 응답 시간, 5회 중앙값).**

| 견적 | run 수 / 리플레이 합계 | 적용 전 | 적용 후 |
|---|---|---|---|
| 6 | 1 / 12 MB | 0.18 s | 0.027 s |
| 4 | 1 / 20 MB | 0.31 s | 0.021 s |
| 3 | 6 / 37 MB | 0.40 s | 0.019 s |
| 5 | 2 / 40 MB | 0.46 s | 0.012 s |

응답 본문은 1~3 KB 인데 시간이 리플레이 합계에 비례했다. SSE 접속 스냅샷(견적 5) 첫 이벤트까지 0.50 s → 0.018 s.

리플레이 합계와 상관없이 20 ms 안팎으로 같아졌다. 결과가 도착할 때마다 도는 완료 판정도 같은 조회를 쓰므로, 28대까지 다 끝난 견적에서 마지막 결과를 반영하는 시간이 함께 줄어든다. 리플레이 API 자체는 같은 데이터를 읽으므로 크기(12.5 MB, gzip 2.04 MB)와 시간이 변경 전과 같다.

**확인한 것.**
- 마이그레이션 V9 가 Testcontainers Postgres 위에서 돌아 통합 테스트(`EstimateFlowIT`)가 통과한다.
- 단위 테스트: 결과 도착 시 궤적이 새 테이블에 저장되고(맵은 견적에 한 벌), 리플레이 API 가 둘을 합쳐 내보내며, 없으면 404.
- 리플레이 API 응답 내용과 크기는 변경 전과 같다.

### 4-4. 백엔드 파싱·재직렬화 생략

**변경 내용.** 리플레이 API(`EstimateService.replay`)가 저장된 궤적 문자열을 JSON 트리로 파싱해 맵(scene)을 끼운 뒤 다시 문자열로 만들던 것을, 궤적 문자열의 마지막 `}` 앞에 `,"scene":` 과 맵 문자열을 이어 붙여 그대로 내보내도록 바꿨다. 컨트롤러는 그 문자열을 Jackson 의 `RawValue` 로 감싸 응답 껍데기의 `result` 자리에 원문 그대로 넣는다(일반 String 이면 따옴표로 감싸져 "글자" 로 나간다).

```
{"dt_s":1.11,"robots":{…},"headings":{…}}      ← 궤적 문자열 (run 마다)
{"grid":[…],"stations":{…}}                      ← 맵 문자열 (견적마다 한 벌)
→ {"dt_s":1.11,"robots":{…},"headings":{…},"scene":{"grid":[…],"stations":{…}}}
```

**왜 원래는 파싱했나.** Spring 에서 JSON 두 개를 합치는 표준 방법이 "파싱 → 키 추가 → 반환" 이고, 반환 타입을 JsonNode 로 두면 직렬화와 응답 껍데기 처리를 프레임워크가 알아서 한다. 파싱이 저장 데이터 검증 역할도 했다. 리플레이 기능이 들어올 때 데이터가 4대 0.67 MB 였어서 그 비용이 보이지 않았고, 28대 12~21 MB 를 재 보고 나서야 드러났다. 12 MB 문자열을 트리로 만들면 숫자 하나하나가 객체가 되어 수백만 개가 생긴다.

**잃는 것과 대신 둔 것.** 파싱 단계의 검증이 없어진다. 대신 두 문자열이 `{` 로 시작하고 `}` 로 끝나는지만 확인하고, 아니면 예전처럼 404 를 준다. 저장 시점에 워커가 보낸 JSON 을 한 번 파싱해서 넣으므로 깨진 데이터가 들어올 경로는 사실상 없다.

**적용 전·후 (28대 run, 로컬, 5회 중앙값. 같은 날 같은 상태에서 3단계 뒤에 측정한 값과 비교).**

| | 첫 바이트까지 | 전체(압축 없이) | 응답 크기 |
|---|---|---|---|
| 적용 전 | 0.37~0.41 s | 0.61 s | 12.49 MB |
| 적용 후 | 0.26 s | 0.49 s | 12.49 MB (동일) |

첫 바이트 시간이 약 3분의 1 줄었다. 남은 0.26 s 는 DB 에서 12 MB 문자열을 읽어 오고 응답으로 복사하는 시간이다. 처음 이 후보를 적을 때 본 1.5 s 는 PC 메모리가 부족한 상태에서 잰 값으로, 파싱이 만드는 수백만 개 객체가 메모리 압박에서 특히 느려진 것이었다. 지금은 그 객체 자체가 생기지 않으므로 서버가 바쁠 때 차이가 더 벌어진다.

**확인한 것.**
- 견적 3 의 11대 리플레이를 변경 전에 저장해 둔 응답과 파싱 후 깊은 비교(키 정렬)로 대조해 내용이 완전히 같다. 키는 `dt_s, model, seconds, stride, robots, headings, outbound_done, scene`.
- 단위 테스트: 이어 붙인 결과가 온전한 JSON 으로 파싱되고 맵과 궤적이 모두 들어 있다. 저장 문자열이 객체 모양이 아니면 404.
- 프론트는 변경 없음. 같은 텍스트를 받아 `JSON.parse` 한다.

## 5. 최종 전후 비교 (4단계 모두 적용, 2026-09-22)

같은 창고·같은 주문으로 새 워커가 돌린 run(11대 견적 7, 28대 견적 6)을 4단계가 모두 들어간 백엔드에서 측정했다. 시간은 3~5회 중앙값이고, 같은 PC 안에서 잰 값이라 기기 상태에 따라 20~30 % 흔들린다. **크기는 상태와 무관한 확정값이고, 시간은 방향과 배수만 보면 된다.**

| 항목 | 28대 최적화 전 | 28대 최적화 후 | 11대 최적화 전 | 11대 최적화 후 |
|---|---|---|---|---|
| 리플레이 응답 크기 (브라우저가 받는 양) | 21.5 MB | **2.04 MB** (−91 %) 원본 12.5 MB 를 gzip | 8.6 MB | **0.87 MB** (−90 %) 원본 4.9 MB |
| DB 저장 크기 (run 1개) | 21.4 MB | 12.3 MB (−43 %) | 8.4 MB | 4.8 MB (−43 %) |
| 20 Mbps 회선 재현, 전체 시간 | 9.7 s | 0.6~0.9 s (−91 %) | 3.3 s | 0.27 s (−92 %) |
| 50 Mbps 회선 재현, 전체 시간 | 5.0 s | 0.57 s (−89 %) | 1.4 s | 0.25 s (−82 %) |
| 백엔드 첫 바이트까지 (같은 PC) | 0.39 s (부하 시 1.5 s) | 0.16~0.26 s (−45 %) | 0.36 s | 0.08 s (−78 %) |
| 견적 상세 조회 (KPI 몇 개, 1~3 KB) | 0.46 s (리플레이 40 MB 견적) | 0.018 s (−96 %) | 0.40 s (37 MB 견적) | 0.018 s (−96 %) |
| SSE 접속 첫 이벤트 | 0.50 s | 0.026 s (−95 %) | — | 0.046 s |
| 배포 서버 실측 (브라우저, 약 27 Mbps) | 6.49 s | (배포 뒤 기입) | | |

**한 줄로.** 28대 리플레이는 받는 양이 21.5 MB 에서 2.04 MB 로 91 % 줄고, 20 Mbps 회선에서 9.7초 걸리던 것이 1초 안으로(−91 %) 들어온다. 리플레이와 무관한 상세 조회·SSE 접속은 리플레이 합계에 비례해 느려지던 것이 20 ms 안팎으로 고정됐다.

**각 단계의 기여 (28대).**

| 단계 | 줄인 것 | 효과 |
|---|---|---|
| 1. 응답 압축 | 전송량 | 21.5 → 3.49 MB (같은 원본 기준 약 1/6). CPU 약 1 s 추가 |
| 2. 헤딩 중복 제거 | 데이터 자체 | 원본 21.5 → 12.5 MB, gzip 3.49 → 2.04 MB. DB·큐도 함께 줄어듦 |
| 3. 리플레이 테이블 분리 | 리플레이와 무관한 조회의 DB 읽기 | 상세 0.46 → 0.018 s, SSE 0.50 → 0.026 s |
| 4. 파싱·재직렬화 생략 | 백엔드 CPU·메모리 | 첫 바이트 0.39 → 0.16~0.26 s. 서버가 바쁠 때 차이가 커짐 |

**남은 것.** 위치 배열(28대 12 MB 중 12 MB 대부분)은 손대지 않았다. 샘플 간격(지금 1.1초)이나 좌표 자릿수를 조정하면 더 줄어들지만 재생 품질과 맞바꾸는 일이라 이번 범위에서 뺐다. 배포 서버의 "적용 후" 값은 배포한 뒤 같은 자리에서 다시 캡처해 채운다.

## 6. 정리

- 지연의 원인은 렌더링이나 MinIO 가 아니라 전송 크기였다. 의심되는 곳을 고치기 전에 구간별로 시간을 재서 확인하는 것이 먼저다.
- 압축은 설정 세 줄로 전송량을 약 6분의 1 로 줄이지만 CPU 시간을 쓴다. 같은 PC 에서 재면 손해로 보이고 느린 회선에서 재면 이득이 크다. 어떤 조건에서 잰 값인지 함께 적어야 비교가 된다.
- 데이터를 줄이는 쪽은 압축과 달리 DB·큐·브라우저 메모리까지 함께 줄어든다. "매 틱 기록" 처럼 만들 때 편한 형식이 그대로 전송 형식이 되어 있지 않은지 살펴볼 가치가 있다.
- 최대 대수(28대)에서 재 보니 백엔드 처리 시간도 무시할 수 없었다. 작은 데이터로만 재면 놓치는 병목이 있다.
- 큰 컬럼을 엔티티에 두면 그 컬럼이 필요 없는 조회까지 비용을 물게 된다. 한 화면만 쓰는 대용량 데이터는 테이블을 나눠 조회 경로를 따로 두는 것이 맞다.
- 프레임워크의 표준 방식(파싱 → 객체 → 직렬화)은 작은 데이터에서는 안전하고 편하지만, 수 MB 를 그대로 흘려보내기만 하는 API 에서는 그 자체가 비용이다. 데이터가 커졌을 때 한 번 되돌아볼 지점이다.
- 실시간 스트림(SSE)처럼 압축하면 안 되는 응답이 섞여 있을 때는 대상 목록을 확인한 뒤 설정한다.
